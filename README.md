# 临床中心台 · SiteDesk

面向 CRO / SMO 经营者的运营管理系统。核心命题：**管人、管钱、管风险**，
不做受 GCP 监管的临床数据系统。

> CRO/SMO 卖的是人天。系统要回答的是"我的人有没有闲着、这个中心还赚不赚钱、
> 下次报价该报多少"—— 而不是"这个试验的数据干不干净"（那是 EDC 厂商的事）。

```
                     浏览器
                       │  只有这一个端口对外
                 ┌─────▼──────┐
                 │  前端托管   │  静态产物 + SPA 回退 + 安全响应头
                 │ (Node，零依赖)│  /v1 同源反代 ──┐  于是没有 CORS
                 └────────────┘                │
                                        ┌──────▼──────┐
                                        │  API (Nest) │  认证 · 三维权限 · 审计 · 幂等
                                        └──────┬──────┘
                                        ┌──────▼──────┐
                                        │ PostgreSQL  │  RLS 是最后一道闸，不是唯一一道
                                        └─────────────┘
```

## 一、这套系统做什么

| | |
|---|---|
| **做** | 项目·中心台账、中心启动与关闭、派工与产能、工时与差旅、里程碑与结算与**现金流预测**、质量事件与 CAPA、**审计轨迹**、经营看板、**客户与投标闭环**、报价模型 |
| **不做（第一阶段）** | EDC、ePRO、eConsent、IWRS、eTMF 主库、源数据 —— 受 GCP 监管，需完成 CSV 验证，自建风险过高 |
| **数据红线** | 不存任何受试者可识别信息，只存筛选号/随机号，优先只存计数 |

### 已经能用的功能

| 模块 | 一句话 |

| 中心损益 | I8' 收入口径四项逐条：启动费 / 入组 / 脱落扣减 / 筛败补偿 |

| 质量事件 | 事件与 CAPA |

| 立项与建档 | **在立项时就算账**；保本合同额比毛利率更能推动谈判；建档滞后的中心成本已经在发生 |
| 组织与权限 | 建号、分组、行 × 列 × 动作 × 模块。**改完立即生效**，每一次都要理由、都进审计 |
| 经营驾驶舱 | 只回答一句「现在要动手的是哪几件」—— 底下几页已经把表画全了，这里不画第四遍 |

| 成本与毛利 | 全部中心一张表，亏得最多的在最上面；合计是总量之比，不是各中心的平均 |

| 受试者 | 一行一个人（「今天」是一行一次访视）；预筛→知情→入组/筛败三步都在界面上 |
| 补偿 · 伦理 | 两者都是关闭闸门的项：补偿要有签收凭证，伦理看的是**批复**不是递交 |
| 启动清单 | 按**阻塞项**排不按完成度 —— 15/16 差的那项是阻塞项，中心一天都开不了工 |
| 药品 · 样本 | 在手数量是算出来的；样本闭环 = 收到**或**销毁，两个都没有就是丢了 |
| 待我审批 | 只列等你点头的（全量在工时台账）。审批不改金额，也不能审自己填的 |
| 我的日程 | 按天铺开，因为**撞车只有按天分组才看得出来**；访视落在整个窗口里 |
| 团队工作台 | 按**中心**排，不按问题类型 —— PM 要的是「SS-07 怎么样了」 |
| 离线发件箱 | 断网照做，联网重放；幂等键**在离线时就生成**，重放不会做两次 |

（随 `/v1/me` 下发），原型定义的 **45 个模块全部有入口、全部建好了页**。
详见 §七。

### 三条设计判断

**① 最小作业单元是 `StudySite`（项目 × 中心），不是项目。**
收入按中心计、成本按人落在中心上、进度按中心统计、核查风险按中心暴露。
"项目毛利 15%" 无经营价值，"A 医院 40% / B 医院 −20%" 才可据以行动。

**② 它既是管理系统，也是 CRA / CRC 干活的系统。**
管理层要的数全部来自一线的日常录入，而一线只会认真使用帮他干活的工具 ——
员工端做成管理端的只读切片，等于在源头上把整套系统架空。

**③ 收入口径有两处方向相反的修正，都必须做。**
筛败费把收入调高（漏算会误砍高筛败中心），脱落扣减把收入调低（漏算会误保高脱落中心）。
只做一个，比两个都不做更危险 —— 因为它看起来是对的。

### 权限是三维的

行（看得到哪些中心）× 列（哪些字段可见）× 动作（能做什么），三者同时成立。

- **范围之外一律 404，不是 403** —— 403 等于确认"它存在，只是你不能碰"，这个确认本身就是泄漏
- **无权字段是被删掉，不是置 null** —— null 会被前端渲染成"暂无数据"，那是另一种谎
- 外部方（医院机构办、研究者）的权限是**另一个维度的切片**，默认拒绝、白名单加回，不是内部权限的子集
- 判定有纯函数实现（`packages/policy`）与数据库实现（RLS）两份，由 300 组用例穷举比对

## 二、一键部署

### 需要什么

一台装了 **Docker Engine 24+**（含 compose 插件）的机器，和这个仓库。
数据库、迁移、种子、两个镜像都由脚本处理，不需要预装 Node 或 PostgreSQL。

### 部署

```sh
git clone <仓库地址> && cd Medical

./deploy/deploy.sh --demo     # 带演示数据，跑完直接给你一条登录链接
# 或
./deploy/deploy.sh            # 空库，之后自己建账号
```

脚本按顺序做七件事，任何一步失败就停在那里：

| | | |
|---|---|---|
| ① | 生成 `deploy/.env` | 三个数据库口令**随机生成**，只生成一次 |
| ② | 构建两个镜像 | 第一次要几分钟 |
| ③ | 起数据库 | 等到 `pg_isready` 真的应答 |
| ④ | **单独**跑一次迁移 | 不塞进服务启动 —— 多副本会同时迁移同一个库，而且迁移失败会伪装成"服务起不来" |
| ⑤ | 灌种子（仅 `--demo`） | |
| ⑥ | 起 API 与前端 | |
| ⑦ | **真的打一遍** | 首页、同源反代、数据库就绪、未认证 401 |

第 ⑦ 步是有意的：只看 `docker ps` 的话，"起来了但一个接口都打不通"
和成功长得一模一样 —— 那正是前后端分离部署最常见的失败。

常用参数：

```sh
./deploy/deploy.sh --port 9000     # 换对外端口（默认 8080）
./deploy/deploy.sh --help
```

### 第一次登录：出厂管理员

装完之后，用 **`admin` / `admin`** 登进去，**第一件事是改掉它的口令**。

> 这个口令是公开的（它就写在这份 README 里）。机器只要从外面连得上，
> 任何人都能以系统管理员身份进来 —— 看得到全部中心、改得动所有人的权限。
> 还没改的时候，API 每次启动会打一条 WARN，界面顶上挂一条改不掉的红条，
> 点一下就能改。改过之后这两处自己消失，而且**翻不回去**
> （`auth_password.is_initial` 在库里只能从 true 变 false）。

为什么要有这么个账号：建账号的接口要求调用方先登录，
而一次干净部署的库里**零个账号** —— 没有它，装完了没人打得开门。
它由迁移建（`0026_admin_role.sql`），不是种子建的，
所以不带 `--demo` 的正式部署一样有。

`admin` 的角色是**系统管理员**：45 个模块全给、18 个动作全给、行范围 all，
唯独 L3 受试者字段（`subject`）默认不给 —— 系统管理员管的是账号和权限，
不是受试者。要给可以在「组织与权限」里给自己加上，**那一下会进审计轨迹**。

### 日常登录：一次性链接

除了出厂管理员，日常入口是一次性链接 —— 不必记密码，也就没有写在便利贴上的密码。
链接 15 分钟有效、只能用一次、兑换在数据库里原子完成。
内部账号也可以各自设口令（登录页「用口令登录」那一栏），
但机构老师和 PI 这类一周登录两次的人不该走这条路：他们只会忘掉，然后走找回流程。

```sh
./deploy/login-link.sh lingyuan
#  ✓ 已为「lingyuan」签发登录链接（15 分钟内有效，只能用一次）：
#    http://localhost:8080/login?token=…
```

把链接交给本人，点开即登录。

### 让本人自己申请（配好通道之后）

上面那条路要求有人能进服务器。配好通道之后，本人在登录页填自己的登录名即可，
链接由邮件或短信直接送到他手里：

```sh
./deploy/login-address.sh lingyuan lingyuan@hengji.com   # 登记一次
#  ✓ 「lingyuan」的登录链接将投递到：lingyuan@hengji.com（走邮件通道）
```

通道在 `deploy/.env` 里配（`SITEDESK_SMTP_URL` / `SITEDESK_SMS_WEBHOOK_URL`）。
一个都不配也能跑，只是链接没人收得到 —— 启动自检会为此打一条告警。

> **收件地址只认库里登记的那个。** `POST /v1/auth/magic-link` 的请求体里有一个
> `sentTo` 字段（契约里写着"仅用于审计留痕"），它**不决定投递到哪里**。
> 拿它当收件地址的话，这个公开端点就是一键账号接管：
> `{"login":"lingyuan","sentTo":"我@攻击者"}`。
>
> 同理，"这个账号没登记地址"和"这个账号不存在"返回**完全一样的 202** ——
> 区别对待就是账号枚举器。差别只写进服务端日志。

`--demo` 的演示账号（种子数据）：

| 登录名 | 身份 | 看得到什么 |
|---|---|---|
| `lingyuan` | 凌远 · 经营层 | 全部中心、损益、费率卡 |
| `linmin` | 林敏 · CRA | 自己监查的中心 |
| `wutong` | 吴桐 · CRC | 自己负责的中心 |
| `zhanghm` | 张慧敏 · 机构办（外部） | 只有本院、且只有合规相关的列 |
| `chenguod` | 陈国栋 · PI（外部） | 同上，范围更窄 |

换个身份登录，同一个页面会**少掉一些列、点不动一些按钮** —— 那是权限模型在起作用，
不是页面做了两套。

## 三、一键更新

```sh
./deploy/update.sh                # 拉最新代码 → 重建 → 先迁移 → 再换服务
./deploy/update.sh --no-pull      # 用工作区当前的代码
./deploy/update.sh --rollback     # 回到上一个镜像标签
```

顺序是**先迁移，后换镜像**。反过来的话，新代码会打在旧 schema 上，第一个请求就炸。

> 这个顺序的前提是：**迁移必须向后兼容一个版本**。在迁移完成到镜像换完之间，
> 旧代码正打在新 schema 上。所以加列要可空、改名要分两步走。

换服务时 API 走的是三步停机 —— 先让就绪探针转 503、等 `SITEDESK_DRAIN_MS`
让负载均衡摘掉自己，再把在途请求做完才关。所以更新期间不掉请求。

更新完同样会**真的打一遍**（首页 / 反代 / 就绪 / 401），不只看容器状态。

### 「password authentication failed for user "sitedesk"」

数据卷比 `deploy/.env` 老。角色口令只在卷**第一次初始化**时写入
（`deploy/initdb/20-roles.sh`），之后再改 `.env` 不会同步过去 ——
`.env` 丢过、删过、或者是在另一台机器上生成的，就会撞上这个。

`deploy.sh` / `update.sh` 现在会在迁移**之前**分辨这件事并给出两条路
（那句 `28P01` 说的是"口令不对"，而实际要做的是换口令或重建卷，
两者解法完全相反）：

```sh
./deploy/reset-db-password.sh   # ① 数据还要 —— 把角色口令改成 .env 里这一份，不动数据
# ② 数据不要了（演示环境通常是这种）—— 连卷一起重来：
docker compose --project-directory deploy -f deploy/docker-compose.yml down -v
./deploy/deploy.sh
```

② 会**删掉全部数据**。所以 `deploy/.env` 请备份好 —— 这一点 §三 也说过。

### 回滚

每次更新把镜像打成 git 短 sha，旧标签留在本机，回滚就是切回去：

```sh
./deploy/update.sh --rollback
```

**数据库不回滚。** 上一版跑不了新 schema 的话，回滚救不了 —— 这也是
"迁移必须向后兼容一个版本"这条规矩存在的原因。

### 从投递通道之前的版本升上来

登录链接现在只会送到**库里登记过**的地址；没登记地址的账号申请链接时
服务端**不签发**（对外仍然是同一个 202，那个人永远收不到）。
所以升级之后要给每个人登记一次：

```sh
./deploy/login-address.sh lingyuan lingyuan@hengji.com
```

在此之前，运维代发那条路照常可用（`./deploy/login-link.sh <登录名>`）——
它不看收件地址，也就不受这条影响。谁还没登记，服务端日志里说得出来
（`reason=no-destination`）。

## 四、部署之后

### 端口与拓扑

只有前端那一个端口对外（默认 `8080`）。API 待在 compose 内网里，
浏览器永远打前端，`/v1` 由前端同源反代过去。于是：没有 CORS、
不用把 API 地址编译进产物（换个环境不必重新构建）、也不必再摆一台 nginx。

**TLS 握手**交给前面那层 ingress。其余三件这两个进程自己做了：

- **预压缩**：构建期就把 br / gz 压好（452 kB 的 js → **117 kB**），
  按 `Accept-Encoding` 协商。前面有 ingress 时它看到 `Content-Encoding: br`
  直接透传，省掉的正是它自己那次压缩。
- **HSTS 默认开**（两年），因为它只在这次请求**确实经 TLS 到达**时才发得出去
  （看 `X-Forwarded-Proto` 的最左段）—— 纯 http 的部署根本走不到那一行。
  想关就显式写 `SITEDESK_HSTS_MAX_AGE=0`。
  `includeSubDomains` 仍是 opt-in（`SITEDESK_HSTS_INCLUDE_SUBDOMAINS=1`）：
  它锁的是这套部署**并不拥有**的那些子域名，是唯一会误伤别人且无法回滚的部分。
- **强制 https 默认关**，而且应该保持关着，除非你确定前面有 TLS：
  它把明文请求 308 走，纯 http 的部署会当场变得打不开。
  TLS 握手本身仍然归 ingress；HSTS 只是一个响应头，
  而只有真正发响应的这一层知道该不该发它。
- **限流**：两个 `@Public()` 登录端点上，**跨实例共享**（进程内计数器挡洪水，
  数据库计数器定阈值）。**即使**跑成 3 个副本，阈值仍然是那一个阈值，
  不会跟着乘以副本数 —— 而这个 compose 本身仍然是单副本的（见第七节）。

### 配置

`deploy/.env`（由 `deploy.sh` 生成，**不进版本库**）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `SITEDESK_PORT` | `8080` | 对外端口 |
| `SITEDESK_PUBLIC_ORIGIN` | `http://localhost:8080` | 台的公开地址，签发登录链接时用它拼 URL |
| `SITEDESK_TAG` | `local` | 镜像标签；`update.sh` 每次改成新的 git 短 sha |
| `SITEDESK_DRAIN_MS` | 未设 → 5000 + 一条告警 | SIGTERM 后等多久再关。**必须比 LB 摘掉本实例所需的时间长** |
| `SITEDESK_LB_PROBE_MS` | 未设 | 不知道上面填几秒？填 LB 的探测间隔，进程自己乘 |
| `SITEDESK_LB_PROBE_FAILURES` | `2` | 连续几次探测失败才摘掉 |
| `SITEDESK_SMTP_URL` | 未设 | `smtp://用户:口令@主机:587`。配了就走邮件通道 |
| `SITEDESK_MAIL_FROM` | 未设 | 发件人。配了 SMTP 却没配它 → **拒绝启动** |
| `SITEDESK_SMS_WEBHOOK_URL` | 未设 | 短信网关，POST `{to, text}` + Bearer |
| `SITEDESK_HSTS_MAX_AGE` | `63072000`（两年） | 秒。只在 `X-Forwarded-Proto: https` 时发；`0` = 关 |
| `SITEDESK_HSTS_INCLUDE_SUBDOMAINS` | 未设（关） | `1` 打开。锁的是本部署不拥有的子域名，确认它们都有证书再开 |
| `SITEDESK_FORCE_HTTPS` | 未设（关） | 明文请求 308 到 https（探针除外） |
| `SITEDESK_LOG_LEVEL` | `info` | `debug` 会把静态产物与探针的访问日志也打出来 |
| `POSTGRES_PASSWORD` 等三个口令 | 随机生成 | **请备份 `deploy/.env`** —— 数据卷还在而口令丢了，库就打不开了 |

`SITEDESK_DRAIN_MS` 该填多少：**探测间隔 × 连续失败阈值 + 一点余量**。
k8s 默认 10s × 3 = 30 秒，ALB 默认 30s × 2 = 60 秒 —— 都远大于 5 秒。
短了不会报错，只会让每次发布漏掉一小撮请求。填不出来就填
`SITEDESK_LB_PROBE_MS`，让进程替你算。畸形的值（`5s`、`3o`）**拒绝启动** ——
它们会被解析成 NaN，把三步停机静默降级成"立刻关"。

### 日志

一行一条 JSON，字段固定 `ts / level / scope / msg`，并自动带上
`requestId / operationId / accountId / role`：

```sh
docker compose --project-directory deploy logs -f api
```

```json
{"ts":"…","level":"info","scope":"access","msg":"GET /v1/study-sites",
 "requestId":"5793b2fe-…","operationId":"listStudySites","role":"crc",
 "status":200,"ms":16.9,"queries":2}
```

响应体里的 `traceId`、响应头里的 `X-Request-Id`、日志里的 `requestId`
**是同一个值**，前端与 API 两跳也是同一个。用户报一个号，日志里就能捞出那一条。

### 探针

| | | |
|---|---|---|
| `GET /healthz` | 前端 | 进程活着 |
| `GET /v1/health` | API | 存活 —— **绝不碰数据库** |
| `GET /v1/health/ready` | API | 就绪 —— **必须探一次库**，探不通 503 |

存活接数据库是个代价很大的错误：库抖一下，所有实例的存活探针一起失败，
编排器**全部重启** —— 一次数据库故障放大成全站故障，重启风暴还让数据库恢复得更慢。

### 备份

数据全在 compose 卷 `sitedesk_pgdata` 里。

```sh
docker compose --project-directory deploy exec -T db \
  pg_dump -U sitedesk sitedesk | gzip > 备份-$(date +%F).sql.gz
```

连同 `deploy/.env` 一起备份 —— 只有数据没有口令，库打不开。

## 七、当前已知问题

这一节曾经是一份只增不减的清单。2026-08 把它整个过了一遍：
十个阶段末尾累计 61 条，其中 21 条其实早就做掉了、只是没人回头划掉，
剩下 40 条逐条判"修 / 不修"，**33 条判为要修，31 条已交付**
（逐条见 [Phase 11](docs/05-%E9%98%B6%E6%AE%B5%E4%BA%A4%E4%BB%98%E8%AE%B0%E5%BD%95.md)）。

之后又补了一条清单上没有、但比清单上任何一条都要命的：
**一次干净部署跑完，库里零个账号，而建账号要求先登录 —— 没有人打得开门。**
现在有出厂管理员 `admin` / `admin`（见 §三）。

一份只增不减的已知问题清单，读到第三页就没人读了 ——
它变成了免责声明，而免责声明的特点是：写下来那一刻它就完成了使命，
之后再没有人对它负责。所以下面这几条，每一条都写清楚了
**为什么现在不做**，而不只是"还没做"。

### 判为不修的（写明理由）

1. **单机 compose，仍然不是高可用** —— 数据库与两个服务在同一台机器上，
   机器没了就全没了。真正的高可用还差两样，两样都不是这个仓库能给的：
   一套带故障切换的 PostgreSQL，和一层真的会做负载均衡的 ingress
   （compose 内网那点 DNS 轮询遇上 keep-alive 长连接就会粘在同一个实例上，
   那不叫负载均衡）。代码层的那块绊脚石已经挪掉了：限流不再随副本数被放大。
2. **共享限流在数据库不可用时会退回单实例判定**（并打一条 warn）。
   刻意的取舍：库挂了的时候把登录端点再变成 500 只是放大故障。
3. **短信通道只定了一个最小形状**（POST `{to, text}` + Bearer）。
   真实网关字段名对不上时在中间摆一个十行的适配器 ——
   在这里长出一张厂商清单要贵得多。
4. **SMTP 客户端是自己写的最小实现**：纯文本、单收件人、PLAIN / LOGIN。
   没有附件、DKIM、连接复用，也不打算有 —— 它只发一种信。
5. **收件地址本人不能自助改**（管理员可以，见下面那条端点；运维那条
   `./deploy/login-address.sh` 也还在）。自助改要先回答"改地址要不要
   二次确认"—— 那是产品决定，不是存储问题。
6. **强制 https 默认关**（HSTS 已经默认开了，见 §四）。它把明文请求 308 走，
   而纯 http 的部署会当场打不开 —— 这条的失败方式是"整个站点无法访问"，
   不能靠默认值去赌。TLS 握手本身仍然归 ingress。
7. **启动清单没有「批量完成」。** 16 项要点 16 次。真实场景里 CRC 常常
   一次性勾完一整类，但批量完成会把"谁在什么时候确认了哪一项"
   变成一次点击 —— 而那正是这份清单存在的理由。
8. **E2E 只跑 Chromium。** Safari / 移动端真机未验；`devices` 里加一行即可，
   但要先有稳定的 CI 时间预算。

### 界面：45 / 45（2026-09）

原型（`prototype/index.html`）是冻结的需求基线，它定义了 **45 个模块**。
在此之前，界面的侧栏是六项写死的数组 —— 经营层在库里有 19 个模块，
界面上只给 6 个；45 个里有 33 个压根没有入口。

现在侧栏按 `role_module` 出（随 `/v1/me` 下发），
**45 个模块全部有导航、有路由、有页**（41 张页面 ——
`crc`/`cra` 同为「我的一天」、`mysite`/`mysites`/`sites` 同为中心台账、
`qa`/`capa` 同为质量事件台账，那是同一本账的两个说法，不是两张页）。

按角色全齐：CRC 14/14 · PM 13/13 · 经营层 19/19 · CRA 11/11 ·
QA 5/5 · DM 4/4 · 机构办 4/4 · PI 2/2。

最后补上的两个是**立项受理**与**中心文件与物资**：它们连表带契约一起补的
（迁移 0038 / 0039），不是只写了界面 —— 而补它们的过程里，
`irb_submit` 多了一道真闸门（机构未受理不能递伦理），
台账里十五个中心因此各多了一条**系统外受理的登记存根**。

一度存在的「有入口、页面待建」是刻意的，不是半成品堆在那里：

就必须一致 —— 藏起来的话，管理员在「组织与权限」里勾上一个模块，

`ComingSoon` 与 `modules.ts` 的 `todo` 字段**留着**：
下一个模块加进来时，它照旧有入口、有一句"这一页要回答什么"，
而不是一个点了没反应的链接。守这条不变量的断言也翻了个面 ——
`nav.test.ts` 断言待建清单为空，`org.spec.ts` 逐个点开侧栏里的每个入口，
断言没有一个落回说明页。

登记表在 `apps/web/src/shell/modules.ts`，标题与分组照抄原型 ——
两处对不上时错的是这边。

### 设计语言：从「只搬了色板」到组件层（2026-09）

「45/45 全部有页」是真的，但**页长得不像原型**。量过之后才知道差在哪：

`packages/ui/src/tokens.css` 的文件头写着「逐字取自 prototype」——
那句话只对了一半。取的是 `:root{}` 里的 28 个色值，
**后面 420 行组件样式一行都没跟过来**。于是各页各写各的 CSS：
原型 ~130 个类、web ~55 个，交集只有 `.btn` 和 `.card`，
而这两个的定义还是相反的 —— 原型的第一句话是
「界面是一个平面，不是一摞卡片」（`.card{background:none;border:0}`），
web 端把它写成了带边框圆角的盒子。

整整三类组件此前一个都没有：**图表**（全仓 0 个 `<svg>`）、
**抽屉与模态**（原型 33 处，web 0 处）、**吐司**。

这件事没有任何东西会报警：当时的护栏只有对比度测试（色值没变，照过）
与 390px 不横向溢出（布局塌成单列，照过）。结构走样一点感觉不到。

现在：

- **`packages/ui/src/components.css`** —— 原型组件层，类名与取值逐字移植；
- **`packages/ui/src/react/`** —— 补上缺的三类原语：`LineChart` / `HBars` /
  `Diverging` / `Spark` / `Legend`、`Drawer` / `Modal`、`ToastHost`。
  不引图表库：前端运行时依赖仍然只有 react / react-dom / react-router-dom，
  四种图加起来不到 200 行，而一个库换来的是一套对不上这份令牌的默认样式；
- **经营驾驶舱**是迁移样板（`grid g4` + `.kpi`、`.card-h`/`.card-b`、两张真图）。
  **图只画有真数的那两张** —— 原型那条"计划 vs 实际累计"折线要按月的
  入组时间序列，服务端目前给不出，为它编一份假数据等于在驾驶舱上
  放一个看起来最权威、实际上是假的东西；
- **`apps/web/test/design.test.ts`** 把这件事钉住：用了的类必须有人定义、
  原型定义的类必须移植过来或**写明豁免理由**、三类原语逐个点名、
  以及 `.card` 必须是平面。写这条测试时它立刻抓出了四个自己漏掉的类。

`components.css` 末尾有一段**桥接**：现存 41 个页面里 89 处 `.card` 用的是
web 自己那套写法（`.card.stack` + `.spread` 当卡头），桥接段把它映射到
这套语言上，所以迁移不必先改 89 处标记。每一条都写了删除条件，
逐页迁到 `.card-h`/`.card-b` 之后一段段删掉。

### 导航与操作可达性：两处"要费力气才够得着"（2026-09）

反馈是"左侧条目太多很难操作，右侧很多操作要下拉到最下面"。两件事都量了：

**① 侧栏对管理员是 41 条链接 + 11 个分组标题。**
侧栏内容 2093px，1440×900 上可视 900px —— **19 条看得见，22 条要滚才够得着，
还要再滚 1193px**。一条要滚动才够得着的导航，等于把"这个系统有哪些页"
变成一件要费力气才知道的事。

模块登记表接上 `role_module` 之后侧栏是"库里有多少给多少"，对大多数人这是
对的（CRC 14 条、PM 13 条，一屏放得下），**管理员是唯一真正撑破的那个**。

处置（`apps/web/src/shell/Rail.tsx`）：

- **多到看不完时才折叠。** 判据不是"会不会溢出"而是"溢出到什么程度" ——
  经营层 19 条超出 103px，滚一下就到；管理员 41 条超出 1193px，是另一回事。
  线画在约一屏半，换算是 `DENSE = 24`：九个身份里**只有管理员越线**，
  其余八个看到的侧栏与这次改动之前一模一样。
- **默认展开你当前所在的那一组** —— 导航先回答"我在哪"，再回答"还有什么"。
  手动开合记在 localStorage 里。那一组被手动收起来时标题上留一个记号，
  收起来不该把"我在哪"的答案也收走。
- **收起的分组按一行排版，不按"一段的标题"排版。** 那 18px 上留白是用来
  隔开标题与它下面的内容的；底下没内容时它只是在把后面十行往下推 ——
  十行推出去八十像素，正好是剩下要滚的那一段。
- **另给一个过滤框**（按 `/` 聚焦）。折叠解决"看不完"，解决不了
  "我知道那页叫什么，但它归哪一组"。过滤时忽略折叠，分组名也参与匹配。
- **手机上一切照旧**：那边侧栏是横着的一条，本来就靠横向滚动，
  折叠是给竖着那一列的答案，搬过去只会多一排点不明白的按钮。

结果：十一个分组连同当前组的八条，加身份区和登出，**一屏之内全看得完**。

**② 「操作在下面」的元凶不是主操作，是表单和矩阵。**
逐页量过 38 条路由：12 页有操作落在第一屏之外，共 94 个。但各页的主 CTA
其实都在第一屏内（建号 416px、提交立项 351px、登记 SAE 250px）——
落在下面的是**列表行、展开后的表单、以及权限矩阵的勾选框**。列表长是列表
该有的样子；另外两件是真问题：

- **展开的表单，提交按钮够不着。** 合同变更那张表 732px 高，提交按钮落在
  1213px；可行性 648px / 1144px。七张表里有三张这样，换到更常见的
  1366×768 是五张。处置：`.form-go { position: sticky; bottom: 0 }` ——
  **对矮表单是个空操作**，够得着的时候它就待在原地。所以这不是"给长表单
  开的特例"，是同一条规则的两端；两端各有一条 e2e 钉着。
- **动作权限矩阵是反着写的。** 角色在行、18 个动作当表头，于是 18 个中文
  表头把「角色」那列挤到只剩一个字宽 —— "系统管理员"竖着排成五行、
  每行高 90px，九行的表长到 810px，**而且那 18 列还是放不下，后八列
  要横向滚出去**。改成动作在行、角色在列：长标签在左、短标签在头，
  18 行各一行高，九列角色横着排得下。表格只占它需要的宽度（565px）不铺满 ——
  铺满时勾选框被推到最右边，离行首六百多像素的空白正是"串行"的来源。
- 台账那一格并排的四个按钮加 `nowrap`：换行会让每行长高一倍，十二行多出
  四百多像素，而"这一行能做什么"本来是一眼的事。

`/org` 从 1804px 降到 1453px，权限那一页的矩阵从"要横向滚"变成一屏排得下。

### 写端点：75 / 75 全部接线（2026-09）

契约里 132 个端点，其中 **75 个是写端点**。清点了一遍前端到底调了哪些 ——
**60 个已接，15 个在服务端跑着但界面上没有任何入口**。

漏掉的那 15 个有一条清楚的规律：**每条流程"处理/判定"那一端都接了，
"发起"那一端没接**。可以判定一份立项申请，但提不了；可以受理一份机构材料，
但交不了；可以确认、执行、交报告一次监查访视，但排不了。

先补的是**中心建档**（`createStudySite`）—— 它是中心状态机缺掉的前半截。
契约对它的说明写清了为什么要紧：「已建档 / 合同中心数」的差值 =
合同里写了但还没进系统的中心，**它们的成本已经在发生，收入却挂不上号**。
在此之前这个入口不存在，系统里的中心只进得来 seed 灌的那三个 ——
一个跑起来的系统没法把第 16 个中心建进去。

看不见价钱的人也能建档：单价与启动费那两栏在无列权限时**不出现**，
而不是出现一个禁用的输入框 —— 禁用的框在说"你本该填这个但不许"，
而事实是这件事不归他管。

建档出来的中心停在「**立项**」，与库里的 `state DEFAULT 'intake'`
（迁移 0004）一致。它的下一步是伦理递交，而那道闸门要机构先受理 ——
所以**递交立项材料的入口就摆在闸门拦下的地方**（中心详情页），
项目与医院都来自这个中心自己，不用再挑一遍：挑错了闸门照样不放行，
错得还很难看出来。

这个入口没有只放在立项受理页（`/inst/intake`），是因为那一页属于
`instac` 模块，而按迁移 0039 的授予，**只有管理员同时拿得到
`instac` 模块和 `advance` 动作** —— PM 有 advance 但没这个模块，
机构办有模块但没 advance。只放在那里，等于这个入口只有管理员按得到，
而真正需要它的是带项目的 PM。

其余 14 个按同一条思路补齐，每一条都把它那个**不显形的后果**
摆在按下去之前：

- **发起端**：`submitIntakeApplication`（提交前就把服务端会算出的毛利率
  说一遍，低于门槛时给的是**保本合同额** —— 百分比谈判桌上用不上）、
  `submitSiteAcceptance`（清单由请求带来不是服务端规则，各院不同；
  递进去一律未勾，勾是形式审查的动作）、`planMonitorVisit`（跟进项在
  排期时就写下来 —— 事后补的清单只会写成已经做过的事）；

### 管理员那条路：五处「不报错的错」（2026-09）

反馈是"管理员不能创建账号，有些操作也不正常"。把真库跑起来对着查了一遍：
**接口全对** —— 建号 201、设口令 204、改角色 200、停用/启用 201、
建分组 201、改权限 200，41 个页面逐个打开一个都不崩。

坏的是另外四处，共同点是**都不报错**：

1. **登录名填错时，报的是一串正则。** 契约里写着中文提示

3. **新建的账号没有入口，而自助那条路会假装成功。** 收件地址存在
   `auth_identity`，登记它的唯一途径是 `deploy/login-address.sh`（要能进服务器）。
   没登记时 `POST /v1/auth/magic-link` 照样回 202「登录链接已发送」，
   服务端日志里写的却是「账号没有登记收件地址，未签发链接」。

4. **mock 里根本没有 admin 这个身份。** `MOCK_ROLES` 只有八个 ——

处置：

- 请求 schema 在契约里**命名并导出**，控制器 import 同一个
  （与 `guards.ts` 里动作权限那条规矩对齐：契约是唯一定义源）。
  identity 的 7 处已清零；`arch-check` 新增一条规则盯住其余 79 处，
  **那张待还清单只许变短**，加回一处立刻红。
  OpenAPI 组件名沿用原来的（…Request），所以**零破坏性变更**。
- `ACTION_LABEL` 移进契约、用 `ActionKey` 定型（漏一个编译不过），
  前端删掉副本；矩阵的表头与格子改用同一份 `ACTION_KEYS`。
- 建号表单当场校验登录名，把规则摆在输入框旁边，不合规时按钮不亮。
- 账号台账新增「怎么进来」一列：没登记收件地址的标出来。
  **只报这一条**，不报"设没设过口令" —— 第一版两个都报了，而
  `auth_password` 的行级策略是严格只看得见自己那一行，
  于是那个 EXISTS 对别人一律返回 false，台账上每个人都成了"进不来"。
  查询不报错、页面不报错，只是答案是错的。那条策略是对的，撤的是字段。
- mock 补上 admin 身份（与迁移 0039 逐字同源，arch-check 逐个比对），
  新增 `e2e/admin.spec.ts` 钉住"矩阵上 18 个动作一个不少"。
  顺带发现 `mocks/scenario.ts` 的角色目录是**第三份副本**且自己漂了
  （说 CRA 有 3 个动作，库里给的是 6 个）—— 改成由 `IDENTITIES` 派生。

最后一条（第 3 条的后半截）曾作为安全面决策留给人拍板，**已决定加**：
`POST /v1/accounts/{id}:set-login-address`。判据是这个仓库自己立过同样的
判例 —— 迁移 0026 的文件头写着管理员能给自己加 `subject` 字段权限，
而正确处置**不是拦住他，是让这件事留下时间和人**。管理员本来就能用
「设口令」接管任何账号，所以这不是一类新能力；把它挪进 HTTP 只是让
它从"能进服务器的人在 shell 里改一行"变成"带理由、进审计轨迹的一次操作"。

围着它划的四条边：

- **只写不读。** 契约里只有 `Account.hasLoginAddress`（布尔），
  没有任何端点回得出地址本身。台账要回答的是"这个人自助进不进得来"，
  把一屋子人的邮箱手机号铺在列表页上，是为一个判断付一整页的代价。
- **审计记"谁给谁登记过"，不记地址。**
- **地址已属于别人时拒绝，不悄悄改绑** —— 改绑等于把那个人的入口转走。
- **复用 `app.set_login_address`**（`deploy/login-address.sh` 走的同一个
  `SECURITY DEFINER` 函数），所以形状校验只有一处实现。
  界面上另有一份同口径的即时校验：打错的地址不会报错，
  只会让那个人永远收不到链接，而他会以为是系统坏了。

公开的 `/v1/auth/magic-link` 那句含糊的 202 没动 —— 它含糊是为了防账号枚举。

**开这个端点顺带挖出第五处「不报错的错」，而且这一处是跨租户的。**
`app.set_login_address` 按登录名找账号，可登录名的唯一约束是
`UNIQUE (tenant_id, login)` —— **只在租户内唯一**；函数又是
`SECURITY DEFINER`，不受 RLS 管，那句 `WHERE a.login = p_login` 没有租户条件。
两个租户各有一个 `zhanghm` 时，`SELECT INTO` **取第一行，不报错**：
A 租户的管理员把自己的邮箱登记到 B 租户同名账号上，再去登录页申请链接，
就登进了另一家。而 `app.provision_tenant` 是现成的，第二个租户开得出来。

在此之前不成其为洞 —— 它只有运维脚本一个调用方，
而**能进服务器的人本来就能连库改任意行**。开给 HTTP 那一刻这个前提没了。
0040 因此不只是改注释：函数里补一行

```sql
AND a.tenant_id = coalesce(app.current_tenant_id(), a.tenant_id)
```

HTTP 每个请求都 `SET LOCAL app.account_id`，于是查找钉在调用者自己的租户里；
运维脚本不设会话主体，NULL 让条件恒真，那条路一个字没变。
`db/test/tenant.test.js` 补了两条守卫（同名不串租户、运维那条路没被误伤），
并且**验过它们在改之前的函数上确实是红的** —— 一条在旧代码上也绿的守卫等于没有。
"这个地址是不是已经属于别人"那一条仍然有意跨租户查：链接是按地址反查账号的。

### 非 https 部署下所有写操作都点不动（2026-09）

F12 里是：

```
Uncaught (in promise) TypeError: crypto.randomUUID is not a function
```

**`crypto.randomUUID` 只在安全上下文里存在** —— https、`localhost`、
`127.0.0.1` 有它；`http://192.168.1.20:8080` 没有。而 `client.ts` 给
**每一个非 GET 请求**生成幂等键，所以挂的不是某一个按钮：
建账号、填工时、推进中心、完成访视，整台系统的写操作一个都点不动。

这正是这套系统被装起来之后最常见的打开方式：README 自己写着 TLS 交给
前面那层 ingress、`强制 https 默认关`（"纯 http 的部署会当场打不开"），
`.env.example` 里 `SITEDESK_PUBLIC_ORIGIN=http://localhost:8080` ——
装在一台机器上、同事从别的机器用 IP 打开，那就是个非安全上下文。

**313 条 e2e 一次都没撞上**，因为 Playwright 打的是 `http://127.0.0.1:4173`，
那是安全上下文；本机开发同理。这个 bug 只在"真的装起来给别人用"时出现，
而那条路上没有任何自动化。

处置（`apps/web/src/api/uuid.ts`）：退到 `crypto.getRandomValues` 自己拼
一个 v4 —— 那个函数**在非安全上下文里也有**（被 gate 的是 `randomUUID`
与 `crypto.subtle`），所以退一步就够。**不退到 `Math.random`**：
幂等键撞了的后果是服务端把新命令当成旧命令的重放，原样返回上次的结果、
不做事、也不报错 —— 静默丢活，正是发件箱那一整套要防的东西。
拿不到 `getRandomValues` 就当场抛一个说得清的错。

守卫两条（`apps/web/test/uuid.test.ts`）：把那个上下文**造出来**
（删掉 `randomUUID` 只留 `getRandomValues`）跑一遍版本位/变体位/去重；
以及静态扫 `apps/web/src`，除 `api/uuid.ts` 外不许再出现 `crypto.randomUUID(`。
验过第二条在改之前的 `client.ts` 上确实是红的。

### 建号可以一并给初始口令（2026-09）

原来建号与设口令是两次操作，中间那一格是真的会停在那里的：建完号手头有
别的事，账号在库里、人进不来，**而台账上看不出这两件事没配套** ——
「怎么进来」那一列只报收件地址，报不了口令（`auth_password` 的行级策略
严格只看得见自己那一行，那条策略是对的）。

`CreateAccountRequest` 新增可选字段 `password`（零破坏性变更）。合并成
一次调用顺带买到原子性：**口令不合规时账号不会被建出来** —— 一个请求
一个事务，抛出去整体回滚，不存在"建了号但口令没设上"这一格。

- 可选。外部角色（机构办 / PI）走一次性链接那条路，本来就不该有口令。
- 与 `setAccountPassword` 同一条：标成初始口令，本人第一次登录被要求改掉，
  这个标记翻不回去。新账号没有会话，所以不必 `revoke_sessions`。
- **口令不进审计**，但单独记一条「设置初始口令」而不是并进「新增账号」——
  这样"谁给谁设过口令"按动作查得出来，不管是建号时给的还是后来补的。
- 长度这一档契约挡（带人话），弱口令表那一档只有服务端一处实现。

### `deploy/update.sh` 从来没跑通过（2026-09）

反馈是"docker 更新那个脚本根本就不起作用"。跑一次就看见了：

```
$ ./deploy/update.sh --rollback
./deploy/update.sh: line 33: 现标签=local: command not found
```

**bash 允许中文函数名，不允许中文变量名。** `读取` / `设置` / `死` / `绿`
这些是函数，一直好好的；而 `现标签="$(读取 SITEDESK_TAG)"` 不是一条赋值 ——
`现标签` 不匹配 `[A-Za-z_][A-Za-z0-9_]*`，bash 于是把整个词展开成
`现标签=local` 当作**命令名**去找。那是脚本的第 33 行，在参数解析之后、
一切实事之前：所以 `update.sh` 的**每一条路径**都走不过第三步，
`--rollback` 也一样。这个脚本从写出来那天起一次都没跑通过。

为什么一直没人发现：仓库里 580+ 条 api 测试、304 条 e2e、164 条库测试，
**没有一条会去执行一个 `.sh`**。`bash -n` 也查不出来 ——
`现标签=local` 在语法上完全合法，它是一条命令。

同一次翻出来的另外三处，都是"不报错的错"这一类：

1. **`读取` 在键不存在时会让整个脚本静默退出。** 那条管道是
   `grep … | head -1 | cut …`，而 `lib.sh` 开头是 `set -euo pipefail`：
   grep 找不到返回 1 → pipefail 传给整条管道 → set -e 当场退出，一个字不打。
   于是一台还没更新过的机器（`.env` 里没有 `SITEDESK_PREV_TAG`）跑
   `--rollback`，得到的是"按下去什么也没发生" —— 而下一行那句
   「没有记录上一个标签 —— 这台机器还没更新过」永远没机会打出来。
   **一条写好了的错误提示，被它上面那一行吃掉了。**
   现在 `读取 <键> [默认值]`，取不到就给默认值。
2. **口令校验分不出"口令不对"和"库没在跑"。** `验口令` 用 `dc exec`，
   而 `update.sh` 在它之前从不拉起数据库。机器重启过、或者有人 `down` 过，
   两种情况给的是同一个失败，屏幕上出现的却是"数据卷比 .env 老，
   两条路选一条"，其中②是 `down -v`。
   **一个只是没起来的库，被诊断成要连卷一起删掉。**
   现在验之前先 `起数据库`（幂等，顺带把 deploy.sh 里那段等待循环去重了）。
3. **`--help` 把代码也打出来。** 每个脚本各写一句 `sed -n '2,20p' "$0"`，
   行号是照着当时的文件头数的；文件头后来短了四行，于是 `--help` 连
   `source …`、`PULL=1; ROLLBACK=0`、`while [ $# -gt 0 ]; do` 一起打。
   它照样退出 0，所以没有任何东西会为此报警。
   现在是 `用法 "$0"`：打开头那段注释，到第一行非注释为止。

守卫在 `tools/arch-check.mjs`（CI 里已经在跑）：

- **非 ASCII 变量名。** 查的是取值（`$名` / `${名}`）与 `for 名 in`，
  不查赋值 —— 赋值那侧没法只靠正则和 shell 引号分清，而取值这侧是精确的：
  判据是 `$` 或 `${` **紧跟着**一个非 ASCII 字符
  （`$code，应为 401` 里 `$` 后面是 `c`，不算）。漏不掉：赋了值总要取。
- **`--help` 真的跑一遍**（那条路不碰 docker，CI 上跑得起）：
  要退出 0，且输出里不许出现脚本正文。

验过守卫在改之前的脚本上确实是红的（22 处）—— 一条在旧代码上也绿的守卫
等于没有。

**没能验到的那一段，如实说：** 这个环境拉不下基础镜像
（`production.cloudfront.docker.com` 被网络策略拒，403），所以
`deploy.sh` / `update.sh` 的③迁移、④换服务、⑤验一遍**没有真正跑过**。
跑通了的是它们之前的全部：参数解析、`--help`、未知参数、缺 `.env`、
`--rollback` 的两条失败路径、`.env` 缺键、以及一路走到真正的 `docker build`
（在那里撞上 403 才停）。绕开那个 403 等于关掉网络策略，所以不绕。

### 通读代码翻出来的三个 bug（2026-09）

不是从失败的测试里找出来的 —— 三条都躺在一片绿灯里
（改完之后是 1134 条单测、314 条 e2e，全绿）。它们的共同点是
**失败方式都不出声**：没有异常、没有红灯，只是答案安静地错了一档。
第二条还要更糟一点 —— **有一条测试正因为那个 bug 才是绿的**。

所以每条都配了守卫，而且每一道都验过：**在改之前它是红的**。
一条在旧代码上也绿的守卫等于没有。

**一、每天早上那八个小时，前端的「今天」是昨天。**

`apps/web/src/shell/dates.ts` 原来这么写：

```ts
export const today = () => new Date().toISOString().slice(0, 10);
```

理由写在文件头上：「日期串本来就是 `toISOString()` 切出来的，
两端同源才谈得上相减」。那句话对**服务端怎么序列化**是成立的，
但它把两件事当成了一件 —— 服务端给的 `YYYY-MM-DD` 是一个**没有时区的
日历日**（访视窗口、知情签署日、里程碑达成日），而用户的「今天」
是一个**本地日历日**。绕一趟 UTC 就把两者错开了。

东八区实测：北京 07:59 时 `today()` 给 `2026-09-08`，08:00 才对上。
**也就是每天 00:00–08:00 它返回昨天**，而 CRC 是七点上工的人：

- 十个页面共 18 处调用，其中 **13 处是日期控件的默认值或边界** ——
  早班填的每一张表默认都填成昨天；
- 工时那一栏是 `max={today()}`，所以八点前**根本选不了今天**，
  而界面上不会解释为什么；
- `daysSince(今天)` 返回 **−1** 而不是 0 ——「今天到期」显示成还剩一天。

现在两个函数都取本地日历日（`getFullYear/getMonth/getDate`，
不走 `Date.parse`，后者按 UTC 解析正是要避开的那件事）。

那 13 处里有一处不是靠改 `dates.ts` 修好的：`HandoverPage` 的 `plannedOn`
从来没调过 `today()`，它把那个表达式**自己抄了一遍**，所以改了源头也修不到它。
它是下面那道静态守卫第一次跑就抓出来的 —— 这也正是那道守卫存在的理由。

守卫在 `apps/web/test/dates.test.ts`：
**把 `process.env.TZ` 设成 `Asia/Shanghai` 再跑，并断言它确实生效了**
（偏移必须是 +480）。这一步不能省 —— CI 和本机都在 UTC 上，
只拨时钟不换时区的话，这条测试在出问题的那台机器之外全是绿的，
等于没写。另有一条静态守卫：`apps/web/src` 下除 `dates.ts` 外
不许再出现 `new Date().toISOString().slice(…)`。拦的是**从此刻切出日历日**，
不是 `toISOString()` 本身 —— `createdAt` 那种记的是一个瞬间，
UTC 的 ISO-8601 正是它该有的样子。

**二、敏感动作清单里有三条对不上任何端点。**

`packages/policy/src/action.ts` 的 `SENSITIVE_ACTIONS` 里写着
`changeAccountRole`、`overrideFeasibility`、`updateVisitTargetDate` ——
契约里没有这三个 id。`needsReason()` 是拿 operationId 去 Set 里查，
**查不到就返回 false，不报错**。

最贵的是第一条：真名是 `updateAccount`。于是「谁把谁调成了什么角色」
照常写进了审计轨迹，却没被标成敏感 —— 而审计页默认只看敏感那一档
（`AuditPage` 的 `useState(true)`）。**核查员打开的第一屏里没有它。**
讽刺的是那段注释举的例子（访视目标日）就是三条死名字之一，
而那个端点从来没建过。

为什么测试没拦住：`packages/policy/test/policy.test.ts` 里本来就有一条
断言 `needsReason("updateVisitTargetDate")` 为真 —— 它确实为真，
因为清单里就写着这个名字。**那是拿清单证明清单**：清单写错什么，
测试就跟着确认什么。真正要成立的性质是「它对得上一个真实端点」。

更要紧的是：`updateAccount` 的契约 description 里白纸黑字写着
「写审计且 isSensitive=true —— 「谁把谁调成了什么」是核查必查项」，
`setLoginAddress` 那条也写着「进审计轨迹、标为敏感」，
**而没有任何一条测试去验这两句话**。文档里承诺过的事没人验，
和没承诺是一样的。

一并补上了漏标的两条：`setAccountPassword` 与 `setLoginAddress`。
这两条是**接管别人账号**的两条路，和停用账号同一档 ——
能给别人设口令就能以他的身份进来，能改收件地址就能把他的一次性
登录链接收到自己手里。两者的契约本来就要求写理由，缺的只是
「标成敏感」这一下，也就是核查员第一屏看不看得见。

有一类敏感表达不进这张按 operationId 查的表：「低分入选可行性」是
**按负载判定**的（同一个 `decideFeasibility`，高分入选不必写理由，
低于 65 分入选必须写）。这一类现在由服务在写审计时显式标记 ——
`AuditInput.sensitive`（`apps/api/src/infra/audit.service.ts`）。
不能把 `decideFeasibility` 塞进清单：那会让高分入选那条合法的
`reason: null` 直接 422。

守卫分两层。**清单层**两道，故意重复：`tools/arch-check.mjs` 里那份是
文本解析，跑在**不需要数据库的第一个 CI job** 里，比另一份早失败几分钟；
`policy.test.ts` 里那份是语义的（直接 `allEndpoints()` 比对），
不会因为 `SENSITIVE_ACTIONS` 换个写法就解析不出来。

**端到端层**五条，在 `apps/api/test/audit.test.ts`：真的调一次改角色 /
设口令 / 改地址，然后去 `sensitiveOnly=true` 那一屏上找它 ——
找不到就红。这一层才是症状本身：一条动作**写进了轨迹**不等于
**在核查员打开的那一屏上**，而清单层证明不了后者。
另外两条守的是条件敏感的两个方向：低分入选要在第一屏上，
**高分入选不能被顺手一起标上** —— 把 `decideFeasibility` 整个塞进清单
会让它合法的 `reason: null` 直接 422，那是"修好了一半，弄坏了另一半"。

**三、给服务端设 `TZ=Asia/Shanghai`，每一个日期字段都会少一天。**

服务端有 25 处这样把 `date` 列切成日期串：

```ts
const day = (v: Date | null) => v ? v.toISOString().slice(0, 10) : null;
```

pg 把无时区的 `date` 列解析成**本地零点**的 JS Date（只有 INT8 覆盖了
type parser，1082 用的是默认那份）。实测：库里存 `2026-09-09`，
TZ 未设时 `day()` 给 `2026-09-09`，**`TZ=Asia/Shanghai` 时给 `2026-09-08`** ——
入组日、知情签署日、访视窗口、里程碑达成日、发票到期日全线偏移一天。

更糟的是仓库里同时有两套约定：`atMidnight`（finance / staffing）和
编号年份用的是**本地**，上面那 25 处用的是 **UTC**。UTC 下两者碰巧一致；
换个时区，一半跟着变对、一半跟着变错。

容器默认 UTC，所以今天不触发。但没有任何地方钉死它，而
**「给中国的部署设 `TZ=Asia/Shanghai` 让日志时间正常」是运维会做的第一件事** ——
这类改动的失败方式是安静的：没有报错，只是每个日期少一天。

现在 `apps/api/src/infra/preflight.ts` 直接拦：`TZ` 要么不设，
要么是 UTC / Etc/UTC / GMT，否则**拒绝启动**（拒绝启动发生在部署那一刻，
而不是三个月后有人问"这个日期怎么不对"）。`deploy/docker-compose.yml`
的 migrate / seed / api 三个服务都显式钉了 `TZ: UTC`。
日志要本地时间，在采集侧转换 —— 服务端存的是日历日，不该带时区。

### 又通读了一遍，翻出四个（2026-09）

上一轮那三条修完之后，用六个 Haiku agent 把 48k 行分片再扫了一遍，
报上来的**逐条自己对着原文核过**。这一步不是形式：
六份报告里有三条是假的，其中一条是把文件头里描述**已经修过的**历史 bug
的注释当成了现状，另一条断言「PostgreSQL 的 RLS 策略在 EXISTS 子查询里
不继承父表限制」—— 建个最小复现跑一遍就知道它继承（见下面「排除掉的」）。
两个 agent 报「没发现问题」，其中一个明确列出读过 `SiteDetailPage`，
而那个文件里正躺着下面第二条。**"没发现"这种结论不能采信。**

**一、客户端发了幂等键，十个写端点根本不读它。**

前端给 `L2 || (非 GET && 非 auth)` 的每个端点生成幂等键并发出去
（`api/client.ts`），发件箱用**同一个判据**在断网时收下请求，
重连时原样带着那把键重放（`api/outbox.ts` 的 `QUEUEABLE`）。
client.ts 里那段注释把保证写得很清楚：

> 请求发出去、服务端处理完、响应在回来的路上丢了，也长这个样子。
> 所以入队重发是有可能"发第二次"的 —— **而这正是幂等键存在的理由**：
> 重放带着同一把键，服务端认得它，返回首次的结果，不会产生第二次副作用。
> 安全性来自那把键，不来自"它应该没到"这种猜测。

而 70 个写端点里有 **10 个既没有 `command()` 也没有 `idempotent()`**，
连 `@Headers("idempotency-key")` 都没有 —— 键发过去，服务端根本不读。
实测（改之前）：

```
createBid         同一把键发两次 → 两条投标，两个 id，都是 201
createFeasibility 同一把键发两次 → 第二次 500（撞唯一约束）
```

**一次投标登记变成两条记录。** 可行性调查那条没重复，只是因为撞上了
`feasibility_target_uniq` —— 那不是幂等，是碰巧没重复。

十个里五个是建档类（`createBid` / `createFeasibility` /
`createContractChange` / `createTeam` / `submitSiteAcceptance`），
重放就是多一条记录；另外五个改的是同一个值
（`updateAccount` / `updateRolePermissions` / `updateClient` /
`setAccountPassword` / `setLoginAddress`），重放的代价是**审计轨迹里多一条** ——
而前两个恰好是核查员第一屏上的那种，第一屏里两条一模一样的
「调整账号角色」，读的人只能自己猜是重放还是真做了两次。

十个都包上了 `idempotent()`（键可选，不是破坏性变更）。带 `params` 的那几条
哈希里连 id 一起算 —— 漏掉 id 的话「给 A 改角色」和「给 B 改角色」
会哈希成同一件事。顺带把三处手写 `idem.begin/complete` 的长写法
（`disableAccount` / `enableAccount` / `advanceStudySite`）换成 `command()`：
它们还留着 `command()` 注释里点名修过的那个写死的 `complete(key, 200, out)`。

守卫两层。`tools/arch-check.mjs` 那条查**结构**：凡是客户端会发键的端点
（非 GET 且非 auth），控制器里必须有外壳 —— 它还顺带钉住「auth 里不许出现
L2」，因为那会让判据本身失效。`apps/api/test/outbox-replay.test.ts` 八条查
**行为**：真的用同一把键发两次，看库里是不是还只有一条。两层都要，
因为包了外壳但 body 传错（比如漏了 params 的 id），结构那条照样绿。

写这些测试时还翻出脚手架的一个坑：`test/harness.ts` 的 `patch` **不接收
额外请求头**（只有 `post` 接收）。`patch(url, body, { "idempotency-key": key })`
多传的那个参数被静默丢掉 —— 于是一条「同一把键重放」的测试，
测的其实是「不带键调两次」，而它照样是绿的。

**二、中心详情页把任何一种读取失败都说成「已是最后一个节点」。**

```ts
setGate(await call<Gate>("getSiteGate", { params: { id } }).catch(() => null));
```

注释写的是「终态没有下一节点，后端回 422 —— 这里当作没有闸门」，
但那个 catch 吞的是**全部**：403、500、断网、超时。而 `gate` 为 null 时
画出来的是「「入组中」已是状态机的最后一个节点。」——
**一个正在入组的中心，因为一次网络抖动被告知它已经走到头了。**

和伦理页那条「把"还没到"说成"没有"」是同一类，只是这一句更硬：
它不是含糊，是**断言了一件假的事**。服务端只在真的没有下一节点时回 422
（`site.service.ts` 的 `gate()`），所以只有那一种算「没有」，其余是「不知道」。

闸门状态改成四态：`loading` / `gate` / `terminal` / `unreadable`。
读不到时说读不到，把服务端的原话摆出来，给一个重试按钮。

守卫在 `e2e/siteflow.spec.ts`，两条：读不到时那句假话**不许出现**，
以及 422 时那句正当的说法照常说。为此在 mock 里加了一个最小开关
（`?fail=getSiteGate` / `?fail=getSiteGate:422`，见 `setFailingOps`）——
「读不到」是一条界面上独立的画法，而它在 mock 里本来走不到，
**走不到的分支等于没写过**。开关整个在 `USE_MOCKS` 里面，不进生产包。

**三、契约自称敏感的动作，敏感清单里没有它。**

上一轮补的守卫只查了一个方向：「清单里的名字是不是真端点」。
**另一个方向漏得一模一样地安静** —— `reopenStartupItem` 的契约里
白纸黑字写着「撤销是敏感动作……必须写原因」，原因也确实强制了
（body 是 `WithReason`），唯独"标成敏感"这一下没有：
`needsReason()` 返回 false，动作进得了轨迹，却不在核查员默认那一屏上。

arch-check 现在反向也查。判据取「契约自己说敏感」，**不取**「契约要求写原因」：
后者还包含 `closeQualityEvent` / `closeDataQuery` / `returnDataQuery` /
`chaseDataQuery` / `requestAcceptanceAmend` 这五条**常规流程** ——
它们要写经过，但不是治理意义上的敏感动作。把那五条一并算成敏感，
等于把第一屏灌满，而灌满的第一屏和没有第一屏是一回事。

**四、勾任务时 UPDATE 匹配 0 行，接口照样回 200。**

```ts
await c.client.query(
  `UPDATE subject_visit_task SET done_at = now(), done_by = $3
    WHERE visit_id = $1 AND seq = $2 AND done_at IS NULL`, …);
return { data: await this.visit(visitId), … };
```

`seq = $2` 和 `done_at IS NULL` 都是上面那次读**没有验证过**的条件。
seq 不存在、或这一项已经被别人勾掉了，UPDATE 都匹配 0 行 ——
而接口回 200，调用方分不出"勾上了"和"根本没这一项"。

这正是迁移 0027 点名过的那种失守：那次是管理员改口令的 UPDATE 被 RLS
挡在门外匹配到 0 行，接口回 204，口令没换、旧会话还开着。
同一个形状：**SQL 成功了，事情没发生。**

现在两种情况分开报：没这一项是 404，已经被勾过是 409 ——
它们要采取的行动完全不同（发错了 vs 两个 CRC 同时在勾同一张任务单）。
离线重放那条路不受影响：同一把幂等键走的是重放，仍然返回首次的结果。

前端也得跟着改：`VisitPage` 的 `tick()` 原来**一个 catch 都没有** ——
因为那时服务端对什么都回 200。不接住的话，这个修复只会把"静默成功"
变成"静默失败 + 控制台报错"，勾选框弹回去、页面上一个字都不说。

**排除掉的（报上来但是假的）**

| 报告的问题 | 实际情况 |
|---|---|
| 幂等键能跨端点复用 | 早就修过了。`idempotency.service.ts:58` 就在比 endpoint。agent 把文件头描述历史 bug 的注释当成了现状 |
| `acceptance_doc` 的 RLS 漏了父表检查 | **实测证伪**：建最小复现，父表策略在子表策略的 `EXISTS` 子查询里确实生效（子表只看得到父行可见的那条）。报告说的与 PostgreSQL 的实际行为相反 |
| `getSiteFunnel` 前端从来没调 | 有意的。契约里明写 `listEnrollment` 是它的列表形态，前端用列表形是为了不把 N+1 搬到浏览器上 |
| 筛选期访视完成没排下一次 | `seq >= 1` 是有意的 —— seq 0 的下一次由 `enrollSubject` 排 |

顺带确认干净的：**45 个模块全部有页面**（41 条路由，部分模块共用一页），
`ComingSoon` 目前是死代码；**36 个 `SECURITY DEFINER` 函数全部设了
