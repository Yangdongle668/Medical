# @sitedesk/calc — 业务口径的唯一实现

**界面上出现的每一个业务数字都来自这里，且带口径版本号。**

原型阶段踩过一次：「SAE 24h 及时率」和「Query 平均关闭天数」是写死的常量，
而同一个页面下方就摆着一条超窗的 SAE。演示时没人看得出来，真实系统里
这就是**看板骗人** —— 而质量看板骗人，是要到药监核查时才付账的。

## 三条规矩

| # | 规矩 | 强制方式 |
|---|---|---|
| 1 | 纯函数，不碰 IO | `npm run arch:check`（禁止 import `node:` / `pg` / `@nestjs/*`） |
| 2 | 金额一律**整数分**，所有除法的出口经过 `roundCents` | 黄金测试断言结果全是整数 |
| 3 | 改任何一条算法都要动 `CALC_VERSION` | 报表要能标出「按哪版口径算的」 |

服务层只做三件事：取数、调用本包、写审计。**服务层不出现算术** ——
再算一遍就等于有了第二套口径，而两套口径迟早会分叉，分叉那天没人知道该信哪一个。

## I8' —— 单中心收入，四项缺一不可

```
收入 = 启动费
     + 入组例数 × 单价
     − Σ(1 − 已完成访视数 ÷ 计划访视数) × 单价      ← 脱落扣减
     + 筛败例数 × 单价 × 筛败费率                    ← 筛败费
```

**两处修正方向相反，这是最要紧的一点：**

- 漏算**筛败费** → 高筛败中心的收入被低估，于是把一个本来赚钱的中心算成亏损，然后关掉它。
- 漏算**脱落扣减** → 高脱落中心的收入被高估，于是保住一个实际在亏钱的中心，继续投人。

**只做一个比两个都不做更危险 —— 因为它看起来是对的。**
两个都不做时误差至少同向（整体偏乐观），还能靠经验打折；
只做一个，误差在不同中心之间方向相反，任何整体折扣都救不了。

这一条有黄金测试基线（`test/revenue.test.ts`）。基线数字是**手算的**，
不是从实现里跑出来再贴回去的 —— 把基线改成实现的输出，
正是这类测试开始失效的那一刻。

`enrolled` **包含**已脱落的例数：脱落的人确实入组过，按整例计入，
再由扣减退回未完成的部分。若把脱落从 `enrolled` 里剔除又不做扣减，
一个做完 11/12 次访视才退出的受试者，收入直接归零 —— 那是更狠的一种错。

## I1 / I2 —— 成本

- **I1** `billable` 由工作类型推导后**落库固化**。「内部培训」明年若改成可计费，
  去年的工时不能因此变成可计费的。历史事实不能被今天的配置改写。
- **I2** 成本 = 人天 × **提交时生效的费率卡**，落库快照。只存一个常量的话，
  调价当天所有历史项目的毛利会集体变化，且无法向任何人解释。

`HOURS_PER_DAY` 是口径的一部分，不是常识：按 7.5 还是 8 小时折算，
单例成本差 6%，而 6% 足以让一个中心从盈利变亏损。

## 一处容易忽略的细节

`roundCents` 里的 `+ 0` 把 `-0` 归一成 `0`。`-0` 序列化成 JSON 是 `0`，看不出来，
但 `Object.is(-0, 0)` 是 `false` —— 断言、去重、Map 键都会踩到，
而排查时会发现「明明都是 0 却不相等」。

```bash
npm run test -w @sitedesk/calc
```
