# 临床中心台 SiteDesk — 开发需求与技术架构

> **文档性质**：给研发团队的架构决策与开发需求，不是产品需求清单，也不是接口字典。
> 它回答的是「怎么建，才能三年后还改得动」。
> **读者**：后端、前端、测试、DBA、以及决定预算的人。
> **前置**：[商业分析与系统定位](01-商业分析与系统定位.md)（为什么做、边界在哪）、
> [可交互原型](../prototype/README.md)（长什么样、怎么用）。原型已验证的判断，本文不再论证。

## 0. 先说清楚三件事

**一、这个系统的价值全部押在「数字可信」上。**
它不是一个 CRUD 系统，是一个**算账系统**。人效、单中心毛利、报价基准 —— 一旦某个数被质疑过一次，
整套系统就退化成一个昂贵的 Excel 替代品。所以本文一半的篇幅在讲计算引擎、口径版本与审计，
这不是过度设计，这是这个系统的地基。

**二、它同时是管理系统和干活系统。**
管理层要的数全部来自一线的日常录入，而一线只会认真使用帮他干活的工具。
这条约束会直接决定架构：**CRC 端必须离线可用、必须幂等重放、必须秒级响应** ——
否则收上来的数据是假的，上面所有的算账都没有意义。

**三、坚决不进 GCP 受监管区。**
不做 EDC / eTMF 主库 / eConsent / IWRS / 源数据。碰了就要做计算机化系统验证（CSV），
每次迭代都要变更控制加回归验证，周期以月计 —— 对一个需要持续演进的自建系统是死亡陷阱。
架构上**预留接口层**（状态同步与文件索引），但不自建主库。见 §11.3。

## 1. 架构目标

### 1.1 五条三年后仍然成立的原则

这五条是本文档所有具体设计的来源。任何一次代码评审，都可以拿它们当尺子。

| # | 原则 | 违背它的典型后果 |
|---|---|---|
| **P1** | **口径唯一，且可版本化。** 任何一个业务数字只有一处计算实现，且带版本号与生效日期 | 报价一套账、交付一套账，事后对不上，谁也说不清项目怎么亏的 |
| **P2** | **权限是三维的（行 × 列 × 操作），服务端强制，外部角色默认拒绝** | 新加一个字段，机构办忽然看到了我方成本 —— 一次泄露就被踢出合格供应商名录 |
| **P3** | **跨角色联动走领域事件，不走直接调用** | 「完成访视」的接口里塞进七件事，半年后没人敢改 |
| **P4** | **事实不可变（append-only），派生可重算** | 改一次费率，三年的历史毛利全变了，且无法解释 |
| **P5** | **隐私边界在架构层强制，不靠代码自觉** | 受试者准标识符组合泄露，同时踩个保法、GCP 与保密协议三条线 |

### 1.2 非功能需求（量化，可验收）

| 维度 | 指标 | 说明 |
|---|---|---|
| 规模（3 年） | 200 个项目 · 3,000 个 StudySite · 500 个用户 · 2,000 万条工时与访视记录 | 单库单表足够，不需要分库 |
| 列表接口 | P95 < 300ms（分页 ≤ 50 条） | |
| 聚合接口 | P95 < 800ms（驾驶舱、P&L） | 超过则引入物化视图，而不是加缓存 |
| 可用性 | 99.5%（工作日 8:00–22:00） | 非 7×24 关键系统，不做多活 |
| **离线** | **CRC 端核心录入离线可用 ≥ 8 小时，恢复后自动幂等重放** | 医院信号差是常态，不是异常 |
| 移动端 | 390px 起可用，CRC 端全部核心操作可单手完成 | |
| 数据保留 | 审计日志 10 年，业务数据永久 | 临床试验档案保存要求 |
| 恢复 | RPO ≤ 15 分钟，RTO ≤ 4 小时 | |

### 1.3 技术选型与理由

| 层 | 选型 | 为什么是它（而不是别的） |
|---|---|---|
| 语言 | **TypeScript 全栈** | **唯一决定性理由：计算引擎可以前后端共用同一份编译产物。** 报价滑块在浏览器里实时算、工时提交在服务端算，两者不可能不一致 —— 这直接从架构上消灭了 P1 的最大风险 |
| 后端 | **NestJS**（Node 22 LTS） | 模块边界与依赖注入是现成的，正好承载 §2.1 的限界上下文 |
| 数据库 | **PostgreSQL 16** | `daterange` + GiST 索引直接表达访视窗口；`exclusion constraint` 直接保证费率卡不重叠；行级安全（RLS）可作权限兜底。这三样是这个领域里真正用得上的能力 |
| 前端 | **React 18 + Vite + TanStack Query** | 服务端状态与本地状态分离，离线队列好做 |
| 契约 | **zod** 单一定义 → TS 类型 + 运行时校验 + OpenAPI | 前后端类型对不上这件事，从源头消除 |
| 异步 | **Postgres Outbox + 独立 worker** | 先不引入 Kafka。规模不到，运维成本不值 |
| 认证 | **OIDC**，对接企业微信 / 飞书 | 一线用手机，走企业 IM 免登录是唯一现实路径 |
| 部署 | 单体 + worker，容器化 | 业务复杂度不在并发，在领域模型。**不要一上来微服务** |

### 1.4 仓库结构

```
sitedesk/
├─ packages/
│  ├─ domain/        领域模型、状态机、不变量（纯 TS，零运行时依赖）
│  ├─ calc/          ★ 计算引擎：费率卡 + 纯函数 + 口径注册表（前后端共用）
│  ├─ contracts/     zod 契约 → 类型 / 校验 / OpenAPI
│  ├─ policy/        权限策略（纯函数，前端用于收敛 UI，后端用于强制）
│  └─ ui/            设计系统（令牌 + 组件，见 prototype/README §设计系统）
├─ apps/
│  ├─ api/           NestJS：HTTP + 事务 + 授权 + 审计
│  ├─ worker/        领域事件消费者
│  └─ web/           React
├─ db/migrations/    版本化 SQL 迁移（只进不退，见 §9.5）
└─ tools/            golden-test 数据集、种子数据、口径变更报告生成器
```

**`packages/calc` 与 `packages/policy` 不允许 import 任何 IO。** 这条由 ESLint 规则强制
（`no-restricted-imports`），CI 阻断。纯函数是这两个包能被前后端共用、也能被穷举测试的前提。

## 2. 领域模型

### 2.1 限界上下文

**十个**上下文，模块边界即代码边界。跨上下文只能通过**领域事件**或**明确的只读查询接口**交互，
不允许直接引用对方的实体。

> **修订（Phase 0）**：原为八个。补完 CRC 生命周期与经营预测之后新增两个 ——
> **Identity & Access**（权限规则被所有上下文引用，没有自己的边界就会被复制到十个地方，
> 然后其中一个忘了更新）与 **Regulatory**（伦理批件断档意味着中心必须停止入组与给药，
> 需要自己的状态机与倒计时）。投标 / 客户 / 合同变更并入 Intake & Contract；
> 启动清单 / 交接 / 人才梯队并入 Site & Staffing。完整清单见
> [Phase 0 §3.1](04-Phase0-系统分析与架构.md)。

```
┌──────────────┐   StudyApproved      ┌──────────────┐
│ 立项与合同    │ ───────────────────▶ │ 中心与人员    │
│ Intake       │                      │ Site&Staffing│

                                             │ SiteActivated / StaffAssigned
                                             ▼
┌──────────────┐  VisitCompleted     ┌──────────────┐
│ 工时与成本    │ ◀────────────────── │ 临床作业      │
│ Timesheet    │                     │ ClinicalOps  │

└──────────────┘               │            │ DeviationDetected
                               ▼            ▼ ScreenFailed
┌──────────────┐        ┌──────────────┐  ┌──────────────┐
│ 收入与结算    │ ◀───── │ 分析 Analytics│  │ 质量 Quality │
│ Revenue      │  只读   │ （只读投影）  │  └──────┬───────┘
└──────────────┘        └──────────────┘         │ QCIssued / CAPASubmitted
                                                  ▼
                                          ┌──────────────┐
```

| 上下文 | 聚合根 | 对外发布的事件 |
|---|---|---|
| **Intake 立项与合同** | `Study`, `IntakeRequest` | `StudyApproved`, `StudyRejected` |
| **Site & Staffing 中心与人员** | `StudySite`, `Staff`, `Assignment` | `SiteStateChanged`, `StaffAssigned`, `StaffUtilizationChanged` |
| **ClinicalOps 临床作业** | `Subject`, `SubjectVisit`, `IPBatch`, `Specimen` | `VisitCompleted`, `SubjectScreenFailed`, `SubjectEnrolled`, `DeviationDetected`, `IPDiscrepancyFound` |
| **Timesheet & Cost 工时与成本** | `TimesheetEntry`, `RateCard` | `CostPosted`, `CostVoided` |
| **Revenue & Billing 收入与结算** | `Milestone`, `Invoice`, `Payment` | `MilestoneReached`, `InvoiceIssued`, `PaymentReceived` |
| **Quality 质量** | `QualityEvent`, `CAPA`, `Audit` | `QualityEventOpened`, `CAPAVerified`, `QualityEventClosed` |
| **External 外部协作** | `QCRound`, `StaffRegistration`, `AcceptanceRequest` | `QCIssued`, `StaffAdmitted`, `IntakeAccepted` |
| **Analytics 分析** | 无（只读投影） | 无 |

**为什么把「外部协作」独立成一个上下文**：机构办与 PI 是**医院方**的人，不是我方员工。
他们的数据可见范围、认证方式、生命周期都和内部员工不同。混在同一个上下文里，
迟早会出现「给内部员工加个字段，外部方也看到了」——那正是 P2 要防的事故。

### 2.2 核心聚合根与关键字段

**StudySite —— 系统的最小作业单元。** 收入按中心计、成本按人落在中心上、
进度按中心统计、核查风险按中心暴露。所有报表的交叉点都在这里。

```ts
// packages/domain/src/study-site.ts
export interface StudySite {
  id: StudySiteId;
  studyId: StudyId;
  hospitalId: HospitalId;
  dept: string;
  piStaffId: PersonId;          // 研究者是法定责任人，不是字符串
  state: SiteState;             // 状态机，见 §5.3
  contractedSubjects: number;
  unitPriceCent: bigint;        // 分。系统内不出现 float 金额
  startupFeeCent: bigint;
  ethicsRoute: EthicsRoute;
  acceptanceNo: string | null;  // 机构受理号
  plannedCurve: EnrollmentPoint[];  // 计划入组曲线，用于「计划到今日」
}
```

**Subject —— 有生命周期的对象，不是一个计数。**

```ts
export type SubjectState =
  | 'PRESCREEN' | 'SCREENING' | 'ENROLLED' | 'SCREEN_FAILED' | 'WITHDRAWN' | 'COMPLETED';

export interface Subject {
  id: SubjectId;
  studySiteId: StudySiteId;
  screeningNo: string;          // 仅筛选号
  randomizationNo: string | null;
  state: SubjectState;
  currentVisitSeq: number;
  screenFailReason: ScreenFailReason | null;
  // 明确不存在：姓名、证件、住院号、联系方式、精确出生日期
}
```

### 2.3 必须由代码强制的不变量

这些不是"业务规则文档"，是**必须写进 `packages/domain` 并有单元测试的断言**。
任何一条被绕过，系统的可信度就少一块。

| # | 不变量 | 强制位置 |
|---|---|---|
| I1 | 工时必须归属唯一 StudySite，且 `billable` 由工作类型推导后**落库固化**，此后不随类型定义变更而改变 | `TimesheetEntry` 构造函数 + DB NOT NULL |
| I2 | 工时成本 = 人天 × **提交时生效的费率卡**，落库快照；费率卡变更不回溯历史 | `calc.postCost()` + `rate_card_id` 外键 |
| I3 | 受试者访视完成必须经 PI 确认才进入锁定态；未确认的访视不计入「已完成」统计 | `SubjectVisit` 状态机 guard |
| I4 | 访视实际完成日超出窗口 → **必须**生成方案偏离质量事件，不可跳过 | `VisitCompleted` 事件处理器（事务内） |
| I5 | 药品账面库存 = 接收 − 发放；实盘 ≠ 账面 → **必须**生成严重质量事件 | `IPBatch.reconcile()` |
| I6 | SAE 上报耗时 > 24h → **必须**生成严重质量事件，且 SAE 及时率由台账算出，不可写死 | `SAEReport` 构造 + `calc` |
| I7 | 里程碑开票必须存在证据链引用（批件号 / 签到表 / 随机号 / 锁库函之一） | `Invoice` 创建校验 |
| I8 | 收入 = 启动费 + 入组 × 单价 **− 脱落未完成部分** + **筛败 × 单价 × 筛败费率**；四项缺一不可。脱落扣减 = Σ(1 − 该受试者已完成访视数 ÷ 计划访视数) × 单例单价。**两处修正方向相反：漏算筛败费会砍掉本来赚钱的高筛败中心，漏算脱落扣减会保住实际在亏钱的高脱落中心。只做一个比两个都不做更危险 —— 因为它看起来是对的。** | `calc` 口径注册表 |
| I9 | 立项测算与报价模型必须调用同一个 `CostModel`，禁止各自实现 | 架构测试（依赖图断言） |
| I10 | 任何返回受试者明细的接口必须经过 policy 且写审计；聚合接口只返回计数 | 序列化层 + 审计中间件 |

## 3. 计算引擎（本系统的心脏）

### 3.1 为什么必须独立成一层

原型阶段已经踩过一次：「SAE 24h 及时率」和「Query 平均关闭天数」是写死的常量，
而同一个页面下方就摆着一条超窗的 SAE。演示时没人看得出来，真实系统里这就是**看板骗人**——
而质量看板骗人，是要到药监核查时才付账的。

所以：**任何出现在界面上的业务数字，都必须来自 `packages/calc`，且带口径版本号。**
CI 有一条规则：视图层不允许出现算术运算符参与的业务计算（ESLint 自定义规则 + 代码评审）。

### 3.2 费率卡：生效日期决定历史不被改写

费率会变（2025 年 CRC 人天 0.118 万，2026 年涨到 0.13 万）。如果只存一个常量，
调价当天所有历史项目的毛利会集体变化，且无法解释。

```sql
create table rate_card (
  id             uuid primary key,
  scope          text   not null,              -- 'GLOBAL' | 'ORG:<uuid>'
  role           text   not null,              -- 'CRA' | 'CRC' | 'PM' | 'QA'
  level          text,                         -- '初级'|'中级'|'高级'|null
  day_cost_cent  bigint not null check (day_cost_cent > 0),
  valid_from     date   not null,
  valid_to       date,                         -- null = 至今
  note           text,
  created_by     uuid   not null,
  created_at     timestamptz not null default now(),
  -- 同一 scope+role+level 的生效区间不允许重叠：数据库层直接杜绝歧义
  constraint rate_card_no_overlap exclude using gist (
    scope with =, role with =, coalesce(level,'') with =,
    daterange(valid_from, coalesce(valid_to,'infinity'::date), '[)') with &&
  )
);
```

`exclusion constraint` 是这里的关键 —— **费率区间重叠在数据库层就写不进去**，
不需要靠应用代码小心翼翼。

### 3.3 事实不可变，派生可重算

```
不可变事实（append-only）        派生指标（随时可重算）
──────────────────────────      ────────────────────────
TimesheetEntry.cost_cent   ──▶  单中心成本 / 每例成本 / 人天per例
（提交时按当时费率快照）          单中心毛利 / 毛利率
Milestone.reached_at            利用率 / 不可计费占比
SAEReport.elapsed_hours    ──▶  SAE 及时率
SubjectVisit.actual_date        入组达成率 / 筛败率 / 漏斗转化
```

**工时不能删，只能作废（void）。** 作废写一条新记录并标记原记录，成本反向冲抵。
理由：审计要求 + 「昨天的报表和今天不一样」是信任崩塌的开始。

```sql
-- 作废而非删除
alter table timesheet_entry
  add column voided_at   timestamptz,
  add column voided_by   uuid,
  add column void_reason text,
  add constraint void_complete check (
    (voided_at is null and voided_by is null and void_reason is null) or
    (voided_at is not null and voided_by is not null and void_reason is not null)
  );
```

### 3.4 CostModel：一个纯函数，三处调用

报价模型算「要花多少人天」，立项测算算「这单接不接」，成本归集算「实际花了多少」——
**三者必须是同一套口径**。这是原型里已经验证的判断，架构上用「同一个纯函数」来保证。

```ts
// packages/calc/src/cost-model.ts
export interface CostModelInput {
  sites: number;  subjectsPerSite: number;  months: number;
  visitsPerSubject: number;  complexity: number;      // 方案复杂度系数
  imvIntervalMonths: number; crcOnsiteFte: number;
  screenFailRate: number;                              // ★ 缺了它成本和收入同时算错
}
export interface CostModelOutput {
  enrolled: number; screened: number; screenFailed: number;
  crcManDays: number; craManDays: number; trips: number;
  crcCostCent: bigint; craCostCent: bigint; travelCostCent: bigint;
  overheadCent: bigint; totalCostCent: bigint;
  billableUnits: number;      // 入组 + 筛败 × 筛败费率
}
export function computeCost(i: CostModelInput, rates: RateSnapshot): CostModelOutput;
export function quoteFrom(o: CostModelOutput, targetMargin: number): QuoteBreakdown;
```

调用方：
- `apps/web` 报价模型页 —— 滑块拖动时在浏览器里同步调用，无需往返
- `apps/api` 立项测算 —— 提交时服务端重算并与客户端结果比对，不一致则拒绝（防篡改）
- `apps/worker` 预算 vs 实际 —— 定时重算并写入分析投影

### 3.5 口径注册表：让"数字为什么变了"有答案

```ts
// packages/calc/src/metrics.ts
export const metrics = defineMetrics({
  'site.revenue': {
    version: 3,
    since: '2026-08-22',
    unit: 'cent',
    changelog: [
      { v: 1, note: '启动费 + 入组×单价' },
      { v: 2, note: '修正启动费按里程碑确认而非签约确认' },
      { v: 3, note: '★ 补入筛败费（入组单价 × 筛败费率）。此前系统性低估收入约 14%' },
    ],
    compute: (s: StudySiteFacts, ctx: CalcContext) =>
      s.startupFeeCent
      + BigInt(s.enrolled) * s.unitPriceCent
      + BigInt(s.screenFailed) * s.unitPriceCent * ctx.rates.screenFailFeeRatio / 100n,
  },
  'site.grossMargin': { version: 2, /* … */ },
  'staff.utilization': { version: 1, /* … */ },
  'site.screenFailRate': { version: 1, /* … */ },
});
```

**每个返回业务指标的接口，响应里必须带 `metricVersions`。** 报表导出的 PDF/Excel 页脚也带。
这样当有人拿着上季度的报表说「数字不对」时，能在三十秒内定位是口径改了还是数据错了。

### 3.6 黄金测试（Golden Tests）

计算引擎的测试不是单元测试，是**回归基准**。

- `tools/golden/` 存放定版的输入数据集 + 期望输出快照（JSON）
- 任何 `packages/calc` 的改动，CI 会跑全量黄金测试并输出**差异报告**
- 差异不是失败 —— 差异需要**显式批准**：PR 里必须包含更新后的快照 + 口径版本号 + changelog
- 未升版本号却产生差异 → CI 阻断

```
$ pnpm calc:golden
  ✓ 15 个 StudySite × 8 项指标 = 120 个断言
  ✗ site.revenue 在 SS-04 上从 62.40 万 变为 70.52 万
    → 检测到 metrics['site.revenue'].version 未变更（仍为 2）
    → 阻断。若为预期变更，请升版本号并补 changelog。
```

这一条是 P1 与 P4 的执行装置。没有它，「口径唯一」只是一句口号。

## 4. 权限模型

### 4.1 权限是三维的，不是一个角色列表

大多数系统只做「操作维」，然后在查询里手写 `where` 过滤 —— 三个月后就漏。本系统必须三维齐备：

| 维度 | 含义 | 实现位置 |
|---|---|---|
| **行（Row）** | 你能看到哪些 StudySite | 查询层统一注入 scope，**禁止**在各 service 里手写过滤 |
| **列（Field）** | 你能看到哪些字段 | 序列化层脱敏，**外部角色默认拒绝** |
| **操作（Action）** | 你能做什么 | 守卫（Guard）+ 领域层二次校验 |

### 4.2 行级范围由身份推导，不由用户选择

```ts
// packages/policy/src/scope.ts
export function rowScope(u: Principal): RowScope {
  switch (u.role) {
    case 'EXEC':        return { kind: 'ALL' };
    case 'QA':          return { kind: 'ALL' };                       // 但列被大幅收窄
    case 'PM':          return { kind: 'BY_STUDY',    ids: u.ownedStudyIds };
    case 'CRA': case 'CRC':
                        return { kind: 'BY_SITE',     ids: u.assignedSiteIds };
    case 'INSTITUTION': return { kind: 'BY_HOSPITAL', ids: [u.hospitalId] };
    case 'PI':          return { kind: 'BY_SITE',     ids: u.piSiteIds };
  }
}
```

**PM 的范围是「项目下全部中心」，但线管的人只是其中一部分。** 这是真实的矩阵型组织：
风险要 PM 担，人却不归 PM 调。系统必须如实呈现这条边界（原型里的「跨组」标记），
而不是假装两者一致。

### 4.3 列级脱敏：外部角色默认拒绝

这是 P2 里最容易做反的一条。**内部角色可以「默认允许 + 显式拒绝」，
外部角色（机构办、PI）必须「默认拒绝 + 显式允许」** —— 否则半年后加一个 `costCent` 字段，
机构办忽然就看到了我方成本。

```ts
// packages/policy/src/fields.ts
export const fieldPolicy = {
  EXEC:  { mode: 'ALLOW_ALL' },
  PM:    { mode: 'ALLOW_ALL', deny: ['quote.*'] },
  CRA:   { mode: 'ALLOW_ALL', deny: ['*.marginCent', '*.marginRate', 'quote.*', 'staff.*.utilization'] },
  CRC:   { mode: 'ALLOW_ALL', deny: ['*.marginCent', '*.marginRate', '*.costCent', 'quote.*'] },
  QA:    { mode: 'DENY_ALL',  allow: ['quality.*', 'audit.*', 'site.basic.*', 'subject.count.*', 'funnel.*'] },
  PI:    { mode: 'DENY_ALL',  allow: ['site.basic.*', 'subject.*', 'visit.*', 'quality.*', 'sae.*', 'doa.*'] },
  INSTITUTION:
         { mode: 'DENY_ALL',  allow: ['site.basic.*', 'subject.count.*', 'quality.*', 'qc.*',
                                      'registration.*', 'acceptance.*', 'isf.*'] },
} as const;
```

**配套的强制装置**（缺一不可）：

1. **字段清单快照测试** —— 遍历每个 DTO 的每个字段 × 每个角色，断言可见性，结果落盘为快照。
   新增字段若未在快照里出现，测试直接失败，强制开发者做出决定。
2. **序列化层统一脱敏** —— 拦截器在 DTO 出站前应用 mask，业务代码无权跳过。
3. **数据库行级安全（RLS）兜底** —— 即使应用层出 bug，外部角色的连接也读不到越界的行。

```sql
alter table study_site enable row level security;
create policy institution_scope on study_site for select
  to app_external
  using (hospital_id = current_setting('app.hospital_id')::uuid);
```

### 4.4 审计：谁在什么时候看了/改了什么

```sql
create table audit_log (
  id          bigserial primary key,
  at          timestamptz not null default now(),
  actor_id    uuid        not null,
  actor_role  text        not null,
  action      text        not null,        -- 'READ' | 'CREATE' | 'UPDATE' | 'VOID' | 'EXPORT'
  entity      text        not null,        -- 'subject' | 'timesheet_entry' | ...
  entity_id   uuid,
  study_site_id uuid,
  before      jsonb,                       -- 变更前（UPDATE/VOID）
  after       jsonb,
  ip          inet,
  request_id  uuid        not null
) partition by range (at);
```

**必须写审计的操作**（不是"建议"）：

- 入组数、里程碑达成日期、工时 —— 这三类数据的任何修改（P4 的执行装置）
- **任何返回受试者明细的读取**（I10）—— 聚合计数不写
- 权限变更、角色切换、跨组织数据访问
- 任何导出（Excel / PDF）

审计表按月分区，10 年保留。查询走独立只读库，不影响业务。

## 5. 事件驱动与状态机

### 5.1 领域事件清单

「CRC 完成一次访视」在业务上会触发七件事。如果写成一个 service 方法，半年后没人敢改。

```ts
// 事件：VisitCompleted
{ visitId, subjectId, studySiteId, crcId, actualDate, hours, wasOutOfWindow }
```

| 订阅者 | 动作 | 所属上下文 |
|---|---|---|
| `PostVisitTimesheet` | 按 §3.2 费率卡生成工时与成本快照 | Timesheet & Cost |
| `AdvanceSubjectVisit` | 按访视计划表（SOA）生成下一次访视窗口 | ClinicalOps |
| `QueuePiConfirmation` | 进入 PI 待确认队列（I3） | External |
| `DetectDeviation` | `wasOutOfWindow` → 生成方案偏离质量事件（I4） | Quality |
| `CreateSubjectPayment` | 生成受试者补偿待发放单 | ClinicalOps |
| `MarkEdcPending` | 置 EDC 待录入，起算 5 个工作日及时线 | ClinicalOps |
| `RefreshProjections` | 刷新入组漏斗、单中心 P&L、驾驶舱投影 | Analytics |

### 5.2 Outbox：事务内写事件，事务外投递

```sql
create table outbox (
  id           bigserial primary key,
  aggregate    text        not null,
  aggregate_id uuid        not null,
  event_type   text        not null,
  payload      jsonb       not null,
  occurred_at  timestamptz not null default now(),
  published_at timestamptz,
  attempts     int         not null default 0,
  last_error   text
);
create index on outbox (published_at) where published_at is null;
```

- 业务写入与事件写入**在同一个事务里**，保证不丢
- worker 轮询未发布事件，投递后标记；失败指数退避，超 10 次进死信表并告警
- **事件消费必须幂等**（按 `event.id` 去重），因为投递是 at-least-once

**同步 vs 异步的划线**：
影响用户下一步操作的（PI 待办、方案偏离、下一次访视）→ **同事务内同步执行**；
只影响报表的（投影刷新）→ 异步。宁可牺牲一点接口延迟，也不能让 CRC 提交完访视，
PI 那边三秒后才看到。

### 5.3 状态机显式建模

四个状态机，全部用**显式转移表 + 守卫**，禁止 `if (status === '...')` 散落各处。

```ts
// packages/domain/src/state-machine.ts
export const siteStateMachine = defineMachine<SiteState, SiteEvent>({
  initial: 'DRAFT',
  transitions: [
    { from: 'DRAFT',        on: 'SUBMIT_ETHICS', to: 'ETHICS_SUBMITTED' },
    { from: 'ETHICS_SUBMITTED', on: 'ETHICS_APPROVED', to: 'ETHICS_APPROVED' },
    { from: 'ETHICS_APPROVED', on: 'SIGN_CONTRACT',  to: 'CONTRACTED' },
    { from: 'CONTRACTED',   on: 'HOLD_SIV', to: 'ACTIVATED',
      guard: (s, ctx) => ctx.allStaffAdmitted(s.id),        // 人员未备案不许启动
      effect: (s) => [emit('MilestoneReached', { code: 'SIV', siteId: s.id })] },
    { from: 'ACTIVATED',    on: 'FIRST_SUBJECT_IN', to: 'ENROLLING' },
    { from: 'ENROLLING',    on: 'ENROLLMENT_COMPLETE', to: 'FOLLOW_UP' },
    { from: 'FOLLOW_UP',    on: 'CLOSE_OUT', to: 'CLOSED',
      guard: (s, ctx) => ctx.openQualityEvents(s.id) === 0 }, // 有未关闭事件不许关中心
  ],
});
```

| 状态机 | 状态 | 关键守卫 |
|---|---|---|
| `StudySite` | 立项→伦理递交→伦理批件→合同→SIV启动→入组中→入组完成→随访中→关闭 | 人员未备案不许 SIV；有未关闭质量事件不许关闭中心 |
| `Subject` | 预筛→筛选中→入组/筛败→逐次访视→出组 | 访视任务未完成不许标记完成；PI 未确认不锁定 |
| `QualityEvent` | 待整改→待复核→已关闭 | 机构质控来源的事件，**关闭权在机构**，我方不能自行关闭 |
| `Approval` | 待审批→通过/驳回 | 毛利率低于门槛必须经营层签字 |

**每次转移都写一条事件**（`state_transition` 表），这是「这个中心为什么现在是这个状态」的唯一答案来源。

## 6. 数据模型

### 6.1 命名与类型约定

| 约定 | 规则 | 理由 |
|---|---|---|
| 主键 | `uuid`，**客户端可生成** | 离线创建需要客户端先有 ID（§7.5） |
| 金额 | `bigint`，单位**分**，字段名以 `_cent` 结尾 | 绝不用 float 或 numeric 存钱 |
| 比率 | `numeric(6,4)`，或整数百分点 | |
| 时间 | `timestamptz`，业务日期用 `date` | |
| 软删除 | **不用**。用 `voided_at` 或状态机终态 | 删除会破坏审计与重算 |
| 枚举 | `text` + `check` 约束，不用 PG enum | PG enum 加值要 DDL 锁 |

### 6.2 关键表

```sql
-- ── 访视窗口：用 daterange 直接表达，超窗查询走索引 ──────────────
create table subject_visit (

  window          daterange generated always as (
                    daterange(target_date - window_days, target_date + window_days, '[]')

                    ('PLANNED','IN_PROGRESS','DONE_PENDING_PI','LOCKED','MISSED')),

  contact_status  text not null default 'TO_CONTACT',

);
create index subject_visit_window_gist on subject_visit using gist (window);
create index subject_visit_open on subject_visit (target_date)
  where status in ('PLANNED','IN_PROGRESS');

-- 超窗清单：一个索引扫描搞定，不需要在应用层遍历
-- select * from subject_visit
--  where status in ('PLANNED','IN_PROGRESS') and upper(window) < current_date;

-- ── 工时：不可变事实 ─────────────────────────────────────────────
create table timesheet_entry (
  id             uuid primary key,               -- 客户端生成，离线幂等
  study_site_id  uuid   not null references study_site(id),
  staff_id       uuid   not null references staff(id),
  work_date      date   not null,
  work_type      text   not null references work_type(code),
  billable       boolean not null,               -- 落库固化（I1）
  hours          numeric(4,2) not null check (hours > 0 and hours <= 24),
  subject_id     uuid references subject(id),    -- 访视与工时同次录入
  visit_id       uuid references subject_visit(id),
  travel_cent    bigint not null default 0 check (travel_cent >= 0),
  rate_card_id   uuid   not null references rate_card(id),
  cost_cent      bigint not null check (cost_cent >= 0),   -- 快照（I2）
  status         text   not null check (status in ('SUBMITTED','APPROVED','VOIDED')),
  voided_at      timestamptz, voided_by uuid, void_reason text,
  created_at     timestamptz not null default now()
);
create index on timesheet_entry (study_site_id, work_date) where voided_at is null;
create index on timesheet_entry (staff_id, work_date)      where voided_at is null;

-- ── 筛选漏斗：不存快照，由受试者状态实时聚合 ───────────────────────
create view v_site_funnel as
select ss.id as study_site_id,
       count(*) filter (where s.state = 'PRESCREEN')      as prescreened,
       count(*) filter (where s.state <> 'PRESCREEN')     as consented,
       count(*) filter (where s.state = 'SCREENING')      as screening,
       count(*) filter (where s.state = 'ENROLLED')       as enrolled,
       count(*) filter (where s.state = 'SCREEN_FAILED')  as screen_failed
from study_site ss left join subject s on s.study_site_id = ss.id
group by ss.id;
```

**为什么漏斗用视图而不是计数字段**：计数字段一定会和明细对不上 —— 只是时间问题。
性能不够时的正确做法是把这个视图**物化**并由事件驱动刷新，而不是在业务代码里维护计数器。

## 7. 接口设计

### 7.1 原则

1. **REST + 资源导向**，不用 GraphQL —— 权限的列级脱敏在 GraphQL 里做起来代价高、易漏。
2. **契约先行**：`packages/contracts` 用 zod 定义一次，生成 TS 类型、运行时校验、OpenAPI 3.1。
3. **服务端永不信任客户端的过滤条件** —— 行级 scope 由身份推导后强制注入。
4. **一次往返拿到一屏所需**：为每个主界面提供一个聚合读接口（`/views/*`），
   而不是让前端发七个请求再拼。写操作仍然按资源拆分。

### 7.2 通用约定

```
基址        /api/v1
认证        Authorization: Bearer <jwt>   （OIDC，含 role / siteIds / hospitalId）
幂等        Idempotency-Key: <uuid>       （所有 POST/PATCH 必带，§7.5）
分页        ?cursor=<opaque>&limit=50     （游标分页，不用 offset）
排序        ?sort=-marginCent,hospitalName
筛选        ?state=ENROLLING&studyId=...  （白名单字段，未白名单直接 400）
稀疏字段    ?fields=id,hospitalName,enrolled
请求追踪    X-Request-Id                   （回显，并写入审计）
```

**错误格式**（RFC 9457 Problem Details）：

```json
{
  "type": "https://sitedesk/errors/invariant-violated",
  "title": "访视任务未全部完成",
  "status": 422,
  "detail": "受试者 S-0217 尚有 2 项访视任务未勾选，无法标记完成。",
```

### 7.5 幂等与离线重放（CRC 端的生命线）

医院信号差是常态。CRC 端必须：

1. **客户端生成 UUID** —— 离线时先在本地建记录并渲染，不等服务端
2. **每个写请求带 `Idempotency-Key`** —— 服务端存 24 小时，重复 key 直接返回首次结果
3. **本地队列按依赖顺序重放** —— 「完成访视」必须先于「标记 EDC 已录入」
4. **冲突用「服务端为准 + 显式提示」**，不做自动合并 ——
   临床数据不能猜。冲突时保留本地副本并让 CRC 决定。

```ts
// apps/web/src/offline/queue.ts
type QueuedOp = {
  id: string;               // = Idempotency-Key
  method: 'POST' | 'PATCH';
  path: string;
  body: unknown;
  dependsOn?: string[];     // 依赖的前序操作 id
  attempts: number;
  createdAt: string;
};
```

服务端幂等表：

```sql
create table idempotency (
  key         uuid primary key,
  actor_id    uuid not null,
  request_hash text not null,          -- 同 key 不同 body → 409
  response    jsonb not null,
  status_code int  not null,
  created_at  timestamptz not null default now()
);
```

### 7.6 版本策略

- 路径版本 `/api/v1`，**只在破坏性变更时升版**
- 新增字段、新增可选参数 → 不升版
- 字段删除/语义变更 → 升版，旧版并行 6 个月，响应带 `Deprecation` 与 `Sunset` 头
- **口径变更不是 API 版本变更** —— 走 `metricVersions`（§3.5），因为口径改了但契约没改

## 8. 前端架构

### 8.1 分层

```
apps/web/src/
├─ app/          路由、身份上下文、错误边界
├─ views/        按上下文分目录，一个视图一个文件夹
│   └─ crc-today/{index.tsx, useCrcToday.ts, __tests__/}
├─ features/     跨视图复用的业务组件（访视卡、漏斗、状态机条）
├─ offline/      本地队列、冲突处理、重放
└─ lib/          从 packages/ 引入：ui / calc / contracts / policy
```

**约束**：`views/` 不允许出现业务算术。任何数字要么来自接口，要么来自 `packages/calc`。
ESLint 自定义规则检查 `views/**` 里的算术表达式是否作用于业务字段，违者 CI 阻断（§3.1）。

### 8.2 设计系统作为包

`packages/ui` 承载原型已定版的「Instrument」设计系统：令牌（颜色 / 字体 / 间距 / 圆角 /
动效）+ 组件（表格、指标行、状态药丸、抽屉、弹窗、图表原语）。

- 令牌是**唯一**的颜色来源，组件里不允许出现字面色值 —— Stylelint 强制
- 图表原语（折线 / 条形 / 堆叠 / 双向）从 `packages/ui/charts` 提供，
  **颜色策略内置**：两系列封顶、条形不按类别上色、堆叠色阶按占比自动排名
- 明暗双主题在令牌层完成，组件无需感知

### 8.3 权限收敛 UI，但绝不作为安全边界

前端 import `packages/policy` 是为了**不渲染用户点了会被拒绝的按钮**（体验），
服务端的同一份 policy 才是安全边界。两边共用一份代码，避免"前端藏了后端没拦"。

### 8.4 状态管理

- **服务端状态** → TanStack Query（含离线持久化）
- **本地 UI 状态** → 组件内 `useState` / URL query
- **不引入全局状态库。** 这类系统的复杂度在领域模型，不在前端状态

## 9. 质量保障

### 9.1 测试金字塔与门槛

| 层 | 范围 | 门槛 | 跑在哪 |
|---|---|---|---|
| **黄金测试** | `packages/calc` 全量指标 × 定版数据集 | **差异必须显式批准**（§3.6） | 每次 PR |
| 单元 | `packages/domain` 不变量、状态机、policy | 行覆盖 ≥ 90%，**不变量分支 100%** | 每次 PR |
| 契约 | zod schema ↔ 实现 | 100% 端点 | 每次 PR |
| 字段脱敏快照 | 每个 DTO 字段 × 每个角色 | **100%，新字段必须显式决策** | 每次 PR |
| 集成 | API + 真实 Postgres（testcontainers） | 关键路径 100% | 每次 PR |
| E2E | Playwright，7 身份 × 核心闭环 | 见 §9.2 | 合并到主干 |

### 9.2 必须有 E2E 的八条闭环

这八条是系统的骨架，任何一条断掉，系统就不成立：

1. 立项提交 → 毛利门槛判定 → 经营层审批 → 项目档案生成
2. 中心建档 → 派驻冲突检测 → 状态机推进至 SIV → 里程碑自动生成
3. 完成访视 → 工时同次落库 → 下一次访视生成 → PI 待确认 → PI 签署锁定
4. 超窗完成 → 自动生成方案偏离 → 出现在质量模块与驾驶舱预警
5. 筛败登记 → 漏斗更新 → **收入随筛败费变化** → 单中心毛利变化
6. 机构质控发起 → 生成质量事件并派发 → CRC 提交整改 → 机构复核关闭 → 两侧状态同步
7. 工时提交 → 成本按当时费率快照 → P&L 与驾驶舱同步；作废后成本反向冲抵
8. 里程碑达成 → 证据链校验 → 开票 → 回款登记 → DSO 重算

### 9.3 CI 门禁

```yaml
pr:
  - lint            # 含 no-io-in-calc / no-arith-in-views / no-literal-color
  - typecheck       # tsc --noEmit，全仓
  - test:unit
  - test:contract
  - test:fields     # 字段脱敏快照
  - calc:golden     # 差异需批准
  - test:integration
  - arch:check      # 依赖图断言：见下
main:
  - test:e2e
  - migrate:dry-run # 迁移在生产快照上试跑
```

**架构测试（`arch:check`）** 断言的依赖规则：

```
packages/calc      → 不得依赖 apps/*、不得依赖 IO 库
packages/domain    → 不得依赖 packages/calc（领域不知道钱怎么算）
packages/policy    → 纯函数
apps/web/views/**  → 不得直接 import packages/domain 的实体（只用 contracts 的 DTO）
上下文之间          → 不得跨上下文 import 实体，只能经事件或只读查询接口
```

依赖规则违背是**架构腐化最早的信号**，比任何代码评审都灵敏。

### 9.4 代码规约（只列会伤到这个系统的）

| 规则 | 理由 |
|---|---|
| 金额一律 `bigint` 分，禁止 `number` 参与金额运算 | 浮点误差在钱上是不可接受的 |
| 禁止 `Date` 直接做业务日期比较，统一走 `packages/domain/date` | 时区是临床数据里最隐蔽的 bug 源 |
| 所有枚举来自 `contracts`，禁止字符串字面量比较状态 | 状态机（§5.3） |
| 禁止在 service 里手写 `where studySiteId in (...)` | 行级 scope 必须统一注入（§4.2） |
| 新增 DTO 字段必须同步更新脱敏快照 | P2 |
| 新增/修改指标必须升 `metricVersion` 并写 changelog | P1 |

## 10. 可观测性与运维

| 维度 | 做法 |
|---|---|
| 结构化日志 | 每条带 `requestId` / `actorId` / `role` / `studySiteId`；**日志中禁止出现筛选号** |
| 指标 | 接口 P50/P95/P99、Outbox 积压与死信数、离线重放成功率、黄金测试差异数 |

| 业务看板 | 一线填报及时率、EDC 录入滞后中位数 —— **这是系统健康度的真实指标**（§0 第二条） |

这两件事漏了，代价不是数据错，是核查发现。

## 11. 安全与合规

### 11.1 数据分级

| 级别 | 内容 | 处置 |
|---|---|---|
| **L3 敏感个人信息** | 筛选号 + 访视日期 + 中心 + 科室 + 事件描述的**组合** | 独立 schema；访问必经 policy 且写审计；聚合视图只返回计数；日志与错误上报中脱敏 |
| **L2 商业机密** | 成本、毛利、人天、利用率、报价、费率卡 | 外部角色（机构办 / PI）**默认拒绝**；导出写审计 |
| **L1 一般业务** | 项目、中心、状态、里程碑名称 | 按角色范围 |

### 11.2 隐私红线：不是「不存姓名」，是「不可重新识别」

系统内**不得出现**：姓名、证件号、住院/门诊号、联系方式、精确出生日期、原始病历、ICF 扫描件。

但仅此不够。在只入组 26 例的中心，「S-0217 · 北京协和 · 肝胆外科 · 2026-08-21 ·
3 级肝功能异常 AE 随访」这组**准标识符组合**足以定位到具体患者 ——
按《个人信息保护法》，这已构成"与其他信息结合识别特定自然人"，且属健康信息。

三条可执行的约束：

1. 不采集直接标识符（同上）
2. 准标识符组合按 L3 管理：最小必要、访问留痕、按角色收敛
3. **可见范围按角色硬切**：CRC 只看本人负责的受试者，PI 只看本中心，
   **经营层与 PM 完全不接触单条受试者记录，只看聚合计数**

第 3 条是关键 —— 老板不需要看到任何一个受试者，他只需要知道"这个中心入组 26 例"。
**把可识别风险挡在角色边界上，比挡在字段清单上更可靠。**

### 11.3 与受监管系统的边界

| 我方做 | 我方不做（对接，不自建） |
|---|---|
| 运营管理层：项目/中心、人、工时、成本、收入、质量事件、协作 | EDC、ePRO、eConsent、IWRS/随机化、eTMF 主库、源数据 |

**预留但不实现**的接口层：

```ts
// packages/contracts/src/integrations.ts
export interface EdcAdapter {
  // 只读状态同步，不落源数据
  fetchQueryStatus(siteRef: string): Promise<QuerySummary[]>;
  fetchSubjectCounts(siteRef: string): Promise<{ screened: number; enrolled: number }>;
}
export interface EtmfAdapter {
  // 只存文件索引与状态，不存文件本身
  listRequiredDocs(siteRef: string): Promise<DocIndexEntry[]>;
}
```

一旦自建 EDC，就要做 CSV（URS/IQ/OQ/PQ 全套），每次迭代变更控制加回归验证 ——
**受监管部分出事的代价是"项目死"，运营管理部分出事的代价是"改个数"。**
用有限的研发资源去承担前者的风险，是经营决策错误。

## 14. 明确不做的

写下来，是为了将来有人提议时可以直接翻到这一页。

| 不做 | 理由 |
|---|---|
| EDC / eTMF 主库 / eConsent / IWRS / 源数据 | 受 GCP 监管，需 CSV，迭代锁死（§11.3） |
| 微服务 | 复杂度在领域模型不在并发；单体 + worker 足够 3 年 |
| GraphQL | 列级脱敏代价高、易漏 |
| 全局前端状态库 | 服务端状态用 Query，本地状态用组件内 |
| 自动合并离线冲突 | 临床数据不能猜 |
| 多租户 SaaS 化（一期） | 但数据模型预留 `org_id`，RLS 已按租户设计 |
| 受试者姓名等直接标识符 | 不需要的数据，最好的保护是不采集 |
| 实时协作（多人同编） | 这个领域没有这个场景 |
