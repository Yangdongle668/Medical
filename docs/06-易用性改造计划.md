## 〇、为什么要做这件事

`README` 的第二条设计判断写着：**「管理层要的数全部来自一线的日常录入，
而一线只会认真使用帮他干活的工具。」** 这套系统在权限、审计、离线、闸门上
已经做得很扎实，但一线的使用路径没有被当成主线来设计：

| # | 现状（有代码依据） | 对一线意味着什么 |
|---|---|---|
| 1 | 「今天」页只拉 `status=planned` 的访视，`limit: 50`，与日期无关（`features/today/TodayPage.tsx`） | 首页不是"今天"，也不是"待办"；第 51 条起静默消失 |
| 2 | SAE、待回复质疑、待录 EDC、待登记 PI 确认、交接、ISF 过期都不在首页 | 要自己去 14 个菜单里逐个翻 |
| 3 | CRC 侧栏 14～15 项，按「项目周期 / 现场 / 质量」这类管理职能分组（`shell/modules.ts`） | 先要理解系统怎么拆的，才知道去哪找 |
| 4 | SAE 上报藏在 `质量 → 我的整改 → 选中心 → SAE 面板`（`features/quality/QualityPage.tsx:94`） | 最紧急的事路径最深 |
| 5 | CRA 角色没有 `sched`（日程）、`isf`、`ethics`，却有 `feas`、`screen`（`db/migrations/0026_admin_role.sql:65`） | 监查员最需要的行程和文件核对没有入口 |
| 6 | 界面文字里有 `（I10）`、`I8′` 等内部编号和大段设计论证（`SubjectsPage.tsx:121,244`、`PrescreenPage.tsx:198,203,286`、`PnlPage.tsx:178`、`VisitPage.tsx` 的 `derive` 块等） | 一线看不懂，也不需要懂 |
| 7 | 手机上 `.rail .who { display: none }`（`shell/styles.css:176`），登出与当前身份一并消失；导航是 15 项的横向滚动条 | 共用设备上不知道是谁登着；找页面要左右划 |
| 8 | 完成访视、登记 PI 确认、标记 EDC 是分开出现的三块，完成后不引导下一步，没有「全部勾选」 | 一次访视要来回好几趟 |
| 9 | `NotifyService` 只在派工 / 交接里用（`modules/site/staffing.service.ts`） | 到期、超时都不会有人提醒，大家回到微信群 |
| 10 | 没有全局搜索、没有日历视图、没有导出和批量导入，也没有全局的"当前中心" | 高频的"找一个人""看一个月""交一份表"都靠手工 |

## 一、目标与度量

**目标：让 CRC 和 CRA 在手机和电脑上，用最少的点击完成每天的工作；
系统主动告诉他们该做什么，而不是等他们来找。**

在第一个工作包开工前，找 3～5 位真实的 CRC / CRA 做一次基线测试，
每个阶段结束后用同样的任务再测一次：

| 任务 | 设备 | 记录 | 目标 |
|---|---|---|---|
| T1 找到今天要做的第一件事并打开 | 手机 | 点击数 / 用时 | ≤ 1 次点击，≤ 5 秒 |
| T2 完成一次访视（勾任务 → 完成 → 登记 PI 确认 → 标 EDC） | 手机 | 点击数 / 用时 / 页面跳转数 | 不离开当前页，≤ 60 秒 |
| T3 上报一例 SAE | 手机 | 点击数 / 用时 | 从任意页 ≤ 3 次点击进入表单 |
| T4 回复一条指派给我的质疑 | 电脑 | 点击数 | ≤ 3 次点击 |
| T5 查到筛选号 `S-xxx` 下次什么时候来 | 任意 | 用时 | ≤ 10 秒 |
| T6（CRA）看下个月去哪几个中心、每个中心遗留几条问题 | 电脑 | 用时 | 一页内看全 |

另外两个线上指标，在第三阶段接入提醒后开始对比：
**EDC 5 个工作日及时率**、**SAE 24 小时及时率**（两者系统里已经在算）。

## 二、改造原则（所有工作包都要遵守）

1. **不动安全边界。** 行 × 列 × 动作三维权限、RLS、404 不是 403、字段删除不置 null ——
   全部照旧。新接口一律复用现有的行范围与 `action` 判定。
2. **契约只做增量。** 新端点、新可选字段；不删字段、不改必填性，保证 `contracts:check` 通过。
3. **role_module 只追加、只重排，不删除。** 已开户的租户上管理员可能改过权限，
   迁移不能把他们勾上的模块删掉；"收进『更多』"是前端展示，不是收回权限。
4. **界面文字只回答两件事：现在是什么状态，下一步点哪里。**
   设计理由写在代码注释和文档里；确有必要给用户看的解释，折叠在「为什么？」里。
5. **离线能力不能倒退。** 新的写操作一律走现有 `call()` 与发件箱，带幂等键。
6. **每个工作包独立可上线。** 做完一个就能合并、能部署、能被一线用上。

### P1 · 统一待办首页（约 2.5 周）

#### W5 待办聚合接口 `getMyInbox`（5 天）

- **契约**：`packages/contracts/src/platform/`（或新建 `workbench/`）新增
  `GET /v1/me/inbox` → `{ items: InboxItem[], counts: Record<kind, number>, generatedAt }`

  ```ts
  InboxItem = {
    kind: "sae_clock" | "visit_overdue" | "visit_due" | "pi_confirm" | "edc_pending"
        | "query_to_answer" | "query_stale" | "handover_to_me" | "timesheet_to_approve"
        | "isf_expiring" | "capa_mine" | "mvr_due" | "monitor_visit_upcoming",
    urgency: "overdue" | "today" | "soon" | "later",
    dueAt: string | null,          // 截止时刻，用于排序和倒计时
    title: string,                 // 一句话，例如「S-012 · V3 访视今天到期」
    siteCode: string, studySiteId: string,
    ref: { type: string, id: string },   // 前端据此拼去处
    meta?: Record<string, unknown>
  }
  ```
- **数据来源**（全部是现有表，复用现有列表 SQL 的行范围）：

  | kind | 来源 | 规则 | 需要的动作 |
  |---|---|---|---|
  | `sae_clock` | SAE 事件 | 未上报；`occurredAt + 24h` 为截止 | `subjRead` |
  | `visit_overdue` / `visit_due` | `subject_visit` planned | 超窗 / 7 天内到期 | `subjRead` |
  | `pi_confirm` | `done_pending_pi` | 访视完成后未登记 | `subjRead` |
  | `edc_pending` | `edcStatus = pending` | 5 个工作日截止 | `subjRead` |
  | `query_to_answer` / `query_stale` | 数据质疑 `mine=true` | 待回复 / 挂起 > 7 天 | — |
  | `handover_to_me` | 交接 | 接手人是我、未完成 | — |
  | `timesheet_to_approve` | 工时 | 与「待我审批」同口径 | `approve` |
  | `isf_expiring` | ISF 看板 `status in (expired, due)` | 已过期 / 即将过期 | — |
  | `capa_mine` | 质量事件 | 负责人是我、未关闭 | — |
  | `mvr_due` | 监查访视 `done` 未交报告 | 第 10 天截止 | 监查员是我 |
  | `monitor_visit_upcoming` | 监查访视 | 14 天内，监查员是我 | — |

  没有对应动作权限的来源**整类跳过**，不报错，与字段删除同一个口径。
- **服务端**：新建 `apps/api/src/modules/workbench/`（`inbox.controller.ts`、`inbox.service.ts`），各来源并发查询，每类最多 20 条并返回总数。在同一事务里、同一个会话主体下执行，保证 RLS 生效。
- **性能**：每个来源一条带索引的查询；`db/scripts/check-plans.mjs` 为新查询加计划守卫；目标 P95 < 300ms（种子数据放大 20 倍测）。
- **测试**：`apps/api/test` 为每个角色（CRC / CRA / PM / DM）断言返回的种类；行范围外的中心不出现；缺 `subjRead` 的角色不出现受试者类条目。`packages/policy` 的穷举比对不受影响。
- **mock**：`apps/web/src/mocks/scenario.ts` 增加有状态的 inbox，与现有 CRC 场景联动（勾完任务后 inbox 里对应条目要消失）。
