### 过程中被拦下的两个错误

1. **`role_field.field_key` 外键拒绝了种子数据** —— 原型用简写 `subj`，schema 用 `subject`。
   外键就是干这个的。以 schema 为准，在生成器里做了唯一一次映射。
2. **约束 `account_external_needs_org` 写错了** —— 我原本写成"外部账号必须有 `org_ref`"，
   但 PI 也是外部账号，而他按 `pi` 规则切行，与所属机构无关。
   真正的规则是"`row_rule = 'hospital'` 的账号必须有 `org_ref`"，这是跨表条件，
   `CHECK` 表达不了，改用触发器。**约束的意图对、谓词错，是最难发现的一类错误** ——
   它不会报错，只会让某个人登录后一行数据都看不到。

1. **`packages/policy` 尚不存在，因此「两处实现等价」还无法验证。**

2. **迁移在 Phase 1 内被就地修改过**（0002 的约束改触发器）。这在未发布阶段可接受，

### 数据库变更

**`0006_money_in_cents`：金额统一为整数分。**

这是契约层暴露出来的 Phase 1 不一致 —— 三处口径互相打架：

| 出处 | 口径 |
|---|---|
| 架构文档 §2.2 | `unitPriceCent: bigint`（分） |
| Phase 1 迁移 0004 | `numeric(14,2)`（元） |
| Phase 2 契约 | 整数分 |

原则 9 要求三者一致。**选分**：现实上限 5 亿元 = 5e10 分，
远在 `Number.MAX_SAFE_INTEGER` 之内；而元加小数在 JS 里做乘除迟早出现浮点误差，
且计算引擎要前后端共用，整数运算不需要十进制库。

用**前向迁移**而非就地改 0004：Phase 1 已交付并推送，
改历史迁移会让已经跑过它的环境与迁移记录对不上。

> **这正是 API-First 应该起的作用**：契约先定，把 schema 的不一致提前暴露出来，
> 而不是等 Phase 4 写后端时在转换点埋一个 bug。

契约测试分两组：

**约定组（8 项）** —— L2 一律 POST 且路径带 `:action`；L2 响应必须带 `sideEffects`；
L2 必须要求 `Idempotency-Key`；每个端点都声明 401/403/404；错误一律
`application/problem+json`；受列权限管辖的字段一律 optional 且不可空；
`operationId` 全局唯一；**`openapi.yaml` 与 zod 定义一致（产物不得手改）**。

**门禁组（11 项）** —— 逐条证明门禁真的会响：删除端点、删除字段、类型变更、
请求端可选变必填、请求端新增必填字段、响应端必填变可选、请求端枚举移除取值 → **拦截**；
响应端新增字段、`x-extensible` 枚举新增取值 → **放行**；普通枚举新增取值 → **放行但告警**。

### 过程中被拦下的三个问题

1. **`$ref` 泄漏到 `#/definitions/`** —— 独立转换 query 参数时 zod 会把具名子 schema 提升。
   加了归一化 + **引用完整性自检**（这道自检本该先于第一次生成就有）。
2. **门禁把请求和响应一视同仁 → 假阳性。** 两者的兼容性规则是**相反的**：
   响应加字段无害，请求加必填字段致命。假阳性会让人养成随手 `--allow-breaking` 的习惯，
   **那等于废掉门禁本身**。改为先按用途分类（沿 `$ref` 传递地标记 request / response / both）再判。
3. **示例数据语义错乱** —— `study.shortName` 生成了人名、`study.code` 生成了中心编号，
   因为键名启发式只看叶子节点。改为按**路径**判断。前端拿到语义错乱的 mock 会被误导。

### 当前已知问题

1. **`Idempotency-Key` 只是契约声明，服务端行为尚未实现**（Phase 3/7）。
   契约里写清了「24 小时内同键返回首次结果」，实现必须与之一致。
2. **`bigint` 在 pg 驱动里默认返回字符串**（int8 可能溢出 JS）。
   `apps/api` 启动时需 `pg.types.setTypeParser(20, Number)` —— 已写进迁移注释，Phase 3 兑现。
3. **`packages/policy` 仍不存在**，`app.site_visible()` 与 `rowScope()` 的等价性仍未验证（Phase 3）。
4. **`GET /v1/me` 的 `visibleSiteIds` 在中心数量很大时会变长**。
   当前 15 个中心无碍；超过约 500 个时应改为不下发全集、只靠服务端过滤。已记入风险。

### 数据库变更

`0007_auth`：4 张表 + 4 个 SECURITY DEFINER 函数。

四个函数都是为了解同一类「先有鸡先有蛋」：
带 RLS 的表要求先有身份，而拿到身份恰恰要先读这些表。

| 函数 | 解决什么 | 暴露面 |
|---|---|---|
| `app.resolve_session` | 令牌 → 账号 | 只返回 id |
| `app.resolve_login` | 登录名 → 账号 | 只返回 id |
| `app.consume_login_token` | 兑换链接 | 只返回 id，**原子**标记已用 |
| `app.issue_login_token` | 签发链接 | 只返回布尔 |

`app.issue_login_token` 是过程中改出来的：最初的实现要在未认证上下文里临时把
`app.account_id` 设成目标账号才能插入 —— 那等于给一个未认证请求提权。
收进 SECURITY DEFINER 函数后，会话状态完全不受影响。

### 过程中被拦下的四个问题

1. **闸门看着在把关，实际对每个新中心都放行。** 闸门查的是"阻塞项是否清零"，
   而新建的中心清单为空 —— 这个条件天然成立。补上"建档即铺开标准清单"，
   并加了两条测试锁死它。**一个默认放行的闸门比没有闸门更危险，
   因为它会让人以为已经把住了。**

2. **`INSERT ... RETURNING` 过不了自己的 RLS 策略。** 排查时每个条件单独求值
   都是 `true`，去掉 `RETURNING` 就能插入。根因：`FOR ALL` 策略的 `USING`
   会作用于 `RETURNING` 返回的行，而 `STABLE` 函数用的是命令开始时的快照 ——
   看不到刚插入的那一行。解法是**策略辅助函数接收行的列值，不按 id 回查本表**
   （`app.site_visible()` 一直是这么写的，所以从没撞上）。
   已在 `db/test/rls.test.js` 补三条回归测试。

3. **同一条连接上并发发查询。** 三处 `Promise.all` 让同一个请求事务的连接
   同时有两条语句在飞。pg 只会排队，换不来速度，却让语句在事务里交错 ——
   全部改为顺序执行。（是 pg 的 deprecation 警告先冒出来的，
   跟一次「改前无、改后有」的对照才定位到具体三处。）

4. **两条 DB 断言硬编码表名，每加一张表都要改。** 改测试去迁就实现，
   正是测试开始失效的那一刻。改为自维护规则：

   - 「每张业务表的租户归属都能被推导出来」——
     不再是"每张表都要有 `tenant_id`"，而是允许两类例外且**判定是算出来的**：
     ① 全局枚举表（单列 `text` 主键、不引用任何表）；
     ② 明细表（主键里含指向父表的外键，父表归属已可推导，递归判定）。
     外键必须落在**主键**里 —— 落在普通列上不算，那种列可以 `UPDATE` 到
     另一个租户的父行上，归属就成了可篡改的。
   - 并配一条**反证测试**：故意造三张错表（无父孤儿表 / 外键在普通列 / 父表自己
     也说不清归属），规则必须全部抓到。断言容易写成永远为真而无人察觉。

### 过程中被拦下的五个问题

1. **动作权限有两个来源，其中一个可以静默失守。** 契约里写 `action: "subjRead"`，
   控制器上另写 `@RequireAction("subjRead")` —— 两处各写一份。
   我在 ClinicalOps 里只写了契约那一份，结果 **QA 照样拉得出全院受试者名册**，
   而所有测试都绿的。不是不一致告警，是**没有任何一处会发现两边不一样**。
   改为守卫按 `operationId` 直接从契约查（`ACTION_OF`），并加了一条架构断言：
   控制器上的每个 `@Operation` 必须在契约里有对应端点，反之亦然
   （唯一例外 `devSession` 逐条写明理由 —— 把后门写进公开契约，等于告诉别人有这么个后门）。

2. **迁移里往 `role_action` 插了 0 行，一个错误都不报。** 迁移跑在种子之前，
   此刻 `role` 表还是空的，`INSERT ... SELECT FROM role WHERE ...` 安静地插入 0 行。
   症状是所有角色一律 403 —— 而错误信息里的动作名在权限表里根本查不到，
   排查时很容易误以为是授权没配。授权移回种子（那是租户数据），
   并加了一条断言：**每个 `action_key` 至少被一个角色持有**。
   没人有的权限，等于把那个端点关掉了。

3. **契约里的动作名和 `action_key` 表对不上。** 契约写 `subject.read`，
   表里是 `subjRead`。同样是所有角色一律 403。加了断言：契约声明的每个动作
   都必须在 `action_key` 里存在。

4. **测试辅助函数吞掉失败。** `doVisit()` 去全量访视列表里按 id 捞，
   新建的那次不在第一页 —— 于是"完成访视"根本没发生，
   而后面的断言仍然通过（因为它们对 `planned` 和 `done_pending_pi` 都成立）。
   辅助函数里吞掉的失败，会让后面的断言以「看起来对」的方式通过。
   改为按 `subjectId` 过滤，并在辅助函数里逐步断言。

5. **`overdueDays` 把当天到期算成「逾期 0 天」。** `new Date()` 带着时分秒，
   拿它和 `date` 列直接比，当天到期的项既进了逾期清单又显示 0 天。
   两端先归零点。差一天的错误在访视窗口上就是一次方案偏离。

另有两处小的：`window` 是 SQL 保留字（列名改 `visit_window`）；
`COMMENT ON` 只接受字面量，不接受 `||` 拼接。

### 数据库变更

`0010_timesheet`：3 张表、1 个函数、1 个不可变触发器、2 条 RLS 策略、3 个索引，

- **`EXCLUDE USING gist`** 让费率区间重叠在数据库层就写不进去。重叠时

### 过程中被拦下的五个问题

1. **黄金基线抓住的是我自己的算术。** 我手写的合计 187723333 与逐项之和差了 30 万分 ——
   实现是对的，写错的是我。这正是基线该干的事：**它校验的不是实现，是意图。**
   （正确值 188023333。）

2. **错误信息叫人去做一件 API 做不到的事。** 费率卡区间重叠时提示
   「调价请给旧卡收口，再开新卡」—— 而当时根本没有收口的端点。
   补了 `POST /v1/rate-cards/{id}:close`。**一条指向死路的错误信息比没有信息更糟。**

3. **收口日差一天。** `valid_to` 在 `EXCLUDE` 约束里是右开区间的上界，
   存收口日本身的话，**收口当天填的工时就找不到费率卡了**。存次日，对外仍报收口日。

4. **受列权限管辖的字段返回了 `null`。** `grossMargin` 在收入为 0 时返回 null，
   而它是 `gated(...)` 的字段 —— null 于是有了两种含义（没权限 / 没有值），
   客户端分不清，而"分不清"最后总会被当成"没有值"。改为**值为 null 时省略**，
   与「无权限时消失」用同一种表达。

5. **`-0`。** `roundCents(-0.4)` 得到 `-0`；它序列化成 JSON 是 `0`，看不出来，
   但 `Object.is(-0, 0)` 是 `false` —— 断言、去重、Map 键都会踩到，
   排查时会发现「明明都是 0 却不相等」。`+ 0` 归一。

另有一处测试自身的问题：三条会失败的 SQL 写在同一个事务里，
第一条失败后事务即中止，后两条报的是「current transaction is aborted」
而不是各自的约束名 —— 拆成独立用例。

### 两处对 Phase 0 规划的偏离（先说，不默默改）

1. **client 由契约注册表派生，不由 `openapi.yaml` 生成。**

   少一个代码生成器和它的漂移风险。副产品：`operationId` 打错一个字母，

2. **`packages/ui` 只做令牌，不做组件库。** Phase 5 要交付的是「骨架 + 设计系统」，

   八成会在第一个真页面里被改掉 —— 那种抽象的成本比重复更高。

### 过程中被拦下的四个问题

1. **MSW 匹配不上 L2 命令路径，且一条错误都不报。**
   path-to-regexp 把 `:done` 当成路径参数，于是
   `/v1/subject-visits/{id}/tasks/{seq}:done` 悄悄落到兜底处理器上，
   返回一份静态示例。症状是「点了勾没反应」，控制台干干净净。
   改为把契约路径转成正则再交给 MSW（`pathToRegExp()`）。

2. **MSW 会跟着上生产，而没有任何构建警告。**
   开关写成 `import.meta.env["VITE_USE_MOCKS"]` 不会被静态替换，
   整个分支活着，480 kB 的 msw 进了包。改成点号访问后产物少 484 kB。
   CI 里直接 `grep` 产物兜底 —— **量产物，不是相信那行代码。**

3. **「低饱和」用错了度量。** HSV 饱和度说 `#8A5B00`（深琥珀）是 1.00，
   和 `#FFD600`（信号黄）一样满 —— 因为它只看「离灰多远」，不看亮到什么程度。
   改用 CIELAB 色度 C*：52 对 87，一下就分开了。
   断言也改成**相对**的：语义色必须比对应的信号色沉，强调色必须比语义色亮 ——
   参照点写死在测试里，比一个凭空的阈值说得清。

4. **我把承重的那道防线记错了。** CSS 注释里写「`minmax(0,1fr)` 是关键」，
   实测把它改回 `1fr`，11 项布局测试**全过** —— 真正在受力的是
   `.table-wrap { overflow-x: auto }`，去掉它 390px 上立刻溢出 185px。
   两道都留着，但注释按实测重写了。**不实测就会把功劳记在错的地方，
   然后在某次重构里把真正有用的那道删掉。**

**① API 从来没有真正启动过。** `tsc` 只编译 `apps/api`，而

**② 测试库共用导致的偶发失败，现在按结构解决了。**

**隔离不是靠约定，是靠没有共享的东西。** 本地连跑 4 轮全绿。

## Phase 6b · Site & Staffing 纵切 —— 闸门的两半

### 本阶段完成内容

启动清单、中心状态机、交接三块界面接上真实接口。这一阶段真正在解决的
是一个交互问题，而它背后是一个权限模型问题：

> **一个禁用的按钮只说明「你不能点」，说不出「为什么」和「去哪儿处理」。**

而「不能点」在这套系统里其实有**两个完全不同的原因**，混成一个灰按钮
就都说不清了：

| | 原因 | 是谁的活 | 界面怎么说 |
|---|---|---|---|
| ① | 闸门没过 —— 事没做完 | 当事人自己 | `unmet` 逐条摊开，带模块名，能跳的直接给「去处理」 |
| ② | 没有 `advance` 动作权限 | 别人的 | 明说「推进需要 advance 权限，清单清零后知会 PM」 |

**种子里的 CRC 恰恰没有 `advance`**（只有 boss / pm 有）。也就是说：
CRC 把 16 项启动清单一项项做完，最后那一下仍然不归他按。
让他对着一个永远点不亮的按钮猜是哪种情况，
是把权限模型的复杂度转嫁给了最没空琢磨它的人。

所以 ① 无论有没有 ② 都照常显示 —— 清单是 CRC 的活，
跟谁来按最后那一下无关。集成测试里这条分工是**两个人分两步**走完的。

### 一个 500 挖出来的三方分歧

写「推进到不可逆节点必须写原因」的测试时撞上一个 500。挖下去发现
**同一条规则在三处各说一套**：

| 处 | 说法 |
|---|---|
| 契约 `advanceStudySite` | 「推进到 siv / closed 这类不可逆节点时必填」 |
| 策略 `SENSITIVE_ACTIONS` | `advanceStudySite` **无条件**敏感，一律必填 |
| 实现 `AuditService.write` | 缺了就 `throw new Error(...)` → 出口是 **500** |

三处的分歧本身还不是最糟的，最糟的是它的**症状**：
调用方少填了一栏，被告知「服务内部错误」。
于是他会去重试、去看监控、去找运维 —— 唯独不会去补那一栏。
**把客户端的错说成服务端的故障，比不校验更糟：它把人引向完全错误的方向。**

收口时以**策略为准**，而不是以契约那句话为准 —— 因为反过来是在
放松一条既有的审计规则。中心状态机的每一次推进都是核查会问到的事实，
不该因为「这一步还能走回来」就免于说明。于是：

1. 契约里 `reason` 改为必填（**这是破坏性变更**，见下）；
2. `AuditService` 抛 `ProblemException("validation-failed")`，
   这一改对清单里**全部八个**敏感动作生效，不只是推进；
3. 前端与 mock 跟着改成「每次都要填」。

顺带发现：`idempotency.test.ts` 里「缺 Idempotency-Key → 422」那条
送的是一个**本来就不合法**的请求体。body 的 schema 校验跑在处理函数之前，
所以它一直在验 reason 而不是幂等键 —— 那条规则从未被真正执行过，
而测试照样绿。补上 reason 之后它才第一次验到自己声称在验的东西。

### 集成测试挖出的一个静默丢单

写「接手人收单」那条集成测试时撞上一次失败，挖下去是**三层同一个缺口**，
而且每一层的症状都不一样：

| 层 | 症状 | 原因 |
|---|---|---|
| ① | 交接单显示「已完成」，派工原地不动，`sideEffects` 是空数组，接口 **201** | 以接手人身份查原负责人的派工，行范围不放行 → 查回 0 行 → `continue` 静默跳过 |
| ② | 收单直接 **500**：`new row violates row-level security policy` | `handover_scope` 是 `FOR ALL`，那句「只能发起从自己出去的交接」的 WITH CHECK **同样作用于 UPDATE**，于是只有原负责人能改这一行 |
| ③ | 交接看起来像一笔「不含任何中心」的单子 | 取中心列表时 JOIN 了 `study_site`，接手人不在那些中心的行范围里，JOIN 把行过滤成空 |

三层合起来是同一个设计假设：**交接是原负责人在驱动。**
而真实场景里更常见的是**接手人**确认完清单顺手收单 ——
逐例交底是他在听，清单是他在核，签收当然也该是他。

① 最危险：它不报错。两个人都以为交完了，
接手人一个中心也没拿到，原负责人的账号却已经可以停用了。

**整个 API 套件此前只走过 from 那一侧，所以一直是绿的。**
新增的断言价值全在于它走的是另一侧。

#### 修法换过一次，是等价性测试逼的

第一版给 `study_site_scope` / `site_assignment_scope` 各加了一条
「这个中心在一笔与我有关的交接单上」。功能通了，
`packages/policy` 的等价性测试当场红一条：

```
fengle(assigned) × SS-13：TS=false DB=true
```

本项目有一条硬约束：**行范围的三处实现必须逐一致**（TS 谓词 /
`siteScopeSql` / 数据库 RLS）。放宽 RLS 就要求另外两处也认识「交接」，
而它们是所有中心相关表共用的谓词 —— 那等于交接单一发起，
接手人立刻拿到那些中心的**受试者级**数据。那是一个产品决定，
不该夹带在一次修 bug 里。

**等价性测试没有阻碍修复，它指出了修复的形状错了**：
要放宽的不是「谁能看见中心」，而是「这一个命令能不能做这一件事」。
改成两个窄口径的 `SECURITY DEFINER` 函数（`app.handover_sites` /
`app.transfer_handover_assignments`），授权在函数内部自己判 ——
行范围一个字没动，三处实现继续一致。

服务端同时补上另一半：**不许再无声地跳过。**
一个中心都没转移却把交接标成已完成，抛 `invariant-violated` 让整个请求回滚；
部分跳过则作为 `sideEffects` 说出来，而不是让人从数目对不上里自己发现。

### 一个漏掉的 `-- Up Migration` 标记

0011 第一版忘了写开头那行 `-- Up Migration`。node-pg-migrate
**照样把它记进 `schema_migration`**，然后一句 SQL 也没执行 ——
`Migrations complete!` 打得干干净净，策略却原地不动。

排查时看到的是「迁移已应用、行为没变」，最容易怀疑的反而是业务代码。
**一个记了帐却什么也没做的迁移，比一个报错的迁移危险得多**：
报错会停下来，这个会带着一个错的数据库继续往前走。

已加两条断言（`db/test/migration.test.js`）：每个迁移必须同时带
Up / Down 标记；Up 段去掉注释后不能为空。
故意去掉标记验证过，会红。

### 一个我自己又踩了一遍的坑

`integration/README` 里第 3 条写着「列表是异步取的，`goto` 之后立刻
`allInnerTexts()` 会拿到空数组」。这次换了个壳又踩了一次：

```ts
const boxes = card.locator(".tasks input:not(:checked)");
for (let n = await boxes.count(); n > 0; n = await boxes.count()) { … }
```

`count()` 在列表渲染前返回 **0**，循环一次都不进，然后直接点「完成」——
拿到 422「还有 6 项未确认」。看起来像逐项确认坏了，其实是断言跑在数据前面。

**换成 `count()` 之后这个坑比原来更隐蔽**：空数组一眼看得出不对，
`0` 不会。修法是先 `await expect(...)` 等一个确定的值出现，再开始数。
README 已补上第 3 条的这半段，以及后端那两条（第 4、5 条）。

### 破坏性变更（需要你知道）

`AdvanceStudySiteRequest.reason` 由可选变为必填，门禁如实报了：

所以我没有自行改，留给你决定：是先改门禁再补一次 `--allow-breaking` 的白名单，

> 给一个数字让人回头去问财务，等于成本这一侧什么也没交付。
>
> **② 同一个接口，看得见钱的人和看不见钱的人拿到的不是同一份数据。**

第二句在这一阶段第一次三层同时生效，而且**恰好落在最常见的那个人身上**：

| 角色 | 行范围 | 可见字段 | 于是 |
|---|---|---|---|
| CRC | assigned | subject | **填得了工时（timeWrite），看不到它折成多少钱（无 cost）** |
| PM | team | cost · margin · price · subject | 钱看得全 |
| 经营层 | all | cost · margin · price · staff | 钱看得全，**受试者明细反而看不到** |

界面对「看不到」的处理是**整列消失 + 一句解释**，不是留白也不是 0。
把"没权限"显示成 0，等于给了一个错的数字，比什么都不显示糟得多。

### 推导链

有 `cost` 权限时，每条工时可以展开成：

```
3.5 小时 ÷ 8 = 0.4 人天
× 人天单价 ¥1,298（提交当日生效的费率卡快照，卡号 3f2a…）
+ 差旅 ¥120
= ¥688
```

第二行是 **I2** 的落点：`dayCostCents` 是**提交那一刻**的快照。
费率卡明年调价，这条工时的成本不变 —— 光看一个总数，这件事是看不出来的。

### I8' 四项逐条

损益页把收入摊成四行而不是给一个总数，理由不是好看：

> 两处修正方向相反 —— 漏算筛败费会砍掉本来赚钱的高筛败中心；
> 漏算脱落扣减会保住实际在亏钱的高脱落中心。
> **只做一个比两个都不做更危险，因为它看起来是对的。**

一个总数看不出少了哪一项；四行摆在一起，少一行是看得见的。
方向相反的那两项用**颜色和符号两条线索**标出（只靠颜色，色觉差异下就没了）。

收入为 0 时**毛利率不出现**，并写明"不是 0%"——
把「还没有收入」显示成「一分钱不赚」，会让人去砍一个还没开始的中心。

### 调价是两步

费率卡页把「先收口、再开新卡」做成显式两步：收口的表单里**没有单价那一栏**。
想改数字的人会发现这里没有那个入口，而不是改完之后才发现报表变了 ——
那张卡已经被若干条工时的成本快照引用着，改它等于改写历史成本。

区间重叠由数据库的 `EXCLUDE` 约束直接拒绝，前端不重复判定，只把 422 原样摊开。

### 契约与权限层的一处真漏洞

写这一阶段时发现 `ACTION_KEYS` 只有 8 个，而库里的 `action_key` 表有 13 个 ——
少的正是后来几个模块加的 `subjRead` / `subjWrite` / `piConfirm` /
`timeWrite` / `rateWrite`。

端点上照常写着 `action: "timeWrite"`，守卫也照常在强制，**运行时一切正常**。
裂开的是类型与契约文档那一侧，两个症状：

1. `GET /v1/me` 的响应带着自己 schema 里没有的取值 ——
   拿 OpenAPI 做校验的调用方会判它不合法，而服务端不会报任何错；
2. `updateRolePermissions` 的 `allowedActions` 用同一个枚举，
   于是**这五个动作根本没法通过 API 授予** ——
   权限管理界面少了五行，而不是报错。

为什么一直没被发现：既有断言只查了**一个方向**（端点声明的动作 ⊆ 表）。
而 `packages/policy` 里那个手写的 8 项联合类型，被 guards.ts 的
`as ActionKey` 一路盖住 —— **一个需要强制转换才能用的联合类型，
基本可以断定它已经不对了。**

收口：

- `ACTION_KEYS` 移到 `kernel/actions.ts`（与 `kernel/fields.ts` 对称），补齐 13 个
- 注册表的 `action?: string` 改为 `action?: ActionKey` —— 写错一个字母在
  `define()` 那一行就编译不过，而不是等到运行时全员 403
- `packages/policy` 的 `ActionKey` / `RowRule` 改为从契约派生，删掉手写的第二份
- guards.ts 去掉那个 cast
- db 断言改成**双向**：`ACTION_KEYS` 与 `action_key` 表逐一一致（故意删一个验证过会红）

门禁把它判为「需要留意」而非破坏性 —— 对的：这些取值本来就已经在运行时存在，
错的只是 schema 对它们的描述。

### mock 与真库的口径不再各写一份

两处改动，都是同一条理由：

- **损益的算式来自 `@sitedesk/calc`**，mock 不手搓 I8'。
  手搓等于给系统开第三套口径（服务端 / calc / mock），三套迟早分叉，
  而分叉那天界面在 mock 上是对的、在真库上是错的，最难查。
- **列权限的遮蔽走 `fieldGates()` + `maskFields()`**，与服务端
  `MaskInterceptor` 同一条路径。自己抄一份"哪些字段该删"的清单行不通：
  契约里加一个 gated 字段，mock 不会跟着变。

为此把 `maskFields` 的参数从 `Principal` 收窄成 `Pick<Principal, "active"|"fields">` ——
判定本来只用这两项，收窄之后前端 mock 才能诚实地传它真正拥有的东西，
而不是把半截对象 `as Principal` 硬塞进来。

## Phase 7 · 离线队列与幂等重放 —— 地下室

### 在这之前，地下室里发生的事

CRC 在医院地下室没有信号 —— 这是需求里从一开始就写着的场景。
而在这一阶段之前，它的表现是**最糟的那一种**：

`fetch` 抛出网络错误 → 页面的
`catch (e) { if (e instanceof ApiError) setProblem(...) else throw e }`
把它再抛出去 → 落进一个没人接的 promise。
按钮从"提交中…"弹回来，没有报错，没有提示，**那次访视就这么没了**。

**静默丢失比报错糟得多** —— 报错至少会让人再点一次。

### 三条设计决定

**① 只排 L2。**
L2 命令按契约必须带幂等键，重放是安全的。而 L1 的那几个 POST
（建档、发起交接、填工时、开费率卡）**没有**幂等键 ——
排进队列，一次重放就可能变成两条记录。
这条线不是省事，是契约本来就画好的：**能重放的才排队**。
`enqueue()` 自己按契约判定，不靠调用方自觉。

**② 幂等键在「尝试之前」生成并落盘，重放时用同一把。**

这是整个 Phase 7 的关键一行。原来那把是在拼 headers 时顺手生成的：

```ts
headers["Idempotency-Key"] = opts.idempotencyKey ?? crypto.randomUUID();
```

断网重试就会换一把新键 —— 服务端看到的是两条不同的命令，于是记两笔。
现在先生成、再尝试、入队时连它一起存，重放时原样带上。

**③ 按账号隔离，不是本人就不发，也不丢弃。**

令牌存在 sessionStorage（关掉标签页就断开，因为医院示教室那台机器上
一个人是谁没人说得准），而队列必须活得比标签页久 ——
于是必然出现「A 排了队、A 的会话没了、B 登录了」这一幕。
把 A 的命令用 B 的会话发出去，审计轨迹上就成了 B 做的。
所以每条都记 `accountId`：不是本人就停下等，也不丢弃 ——
丢弃等于把人家的活删了。

### 重放的三条规矩

| 情况 | 处置 | 为什么 |
|---|---|---|
| 网络错误 / 5xx | 留在队头，下次再来 | 服务器还没接住，重发是对的 |
| 4xx | 挪进「需要处理」，后面的继续走 | 一条超窗未填原因的访视永远不会自己变成功，堵在队头会把后面所有的活一起卡住 |
| 成功 | 出队 | — |

**严格 FIFO，不许跳过。**「勾完第 3 项任务」和「完成这次访视」是有先后的：
跳过前者直接发后者，服务端会以为任务没勾完而拒绝 ——
而那次拒绝看起来像业务规则出了问题，其实是顺序被打乱了。

4xx 的那一条也**不能悄悄丢**：那是一次真实发生过的工作，
人得知道它没进系统。所以有一栏「需要处理」，丢弃要人点一下。

### 界面：不替人做主

离线队列最容易做成的样子是「悄悄替你重试」，看起来很贴心 ——
直到有人在核查现场被问「这次访视你什么时候录的」，
而系统里那条记录的时间比他记得的晚了三小时，或者根本不在。

所以侧栏常驻一个「发件箱 N 条待发」的角标，
`/outbox` 逐条列出待发与失败项。**「我到底发出去没有」不该由用户去猜。**

### 一个只有在集成层才试得出来的行为

离线的 e2e 最初写在 `e2e/`（打 mock 那一层），三条**全部失败** ——
而它们失败的方式恰好说明了两层测试各自的边界：

> **MSW 是 Service Worker，它在 fetch 事件里直接应答，根本不碰网络。**
> 于是 `context.setOffline(true)` 对它毫无影响：请求照样成功，
> 队列一条也不会进。

离线行为只有在**真的有网络**的地方才试得出来，所以这一组挪到了
`integration/`（真 API + 真库），用 `setOffline` 真的把网断掉。

最后一条断言才是关键：重放之后**重新拉一次清单，已完成数正好 +2，不是 +4**。
+4 就说明重放换了新的幂等键，服务端把同一件事记了两遍 ——
而队列清空、角标消失这些现象，在两种情况下看起来是一模一样的。

**这条断言第一次跑就红了，而且不是它自己的问题** —— 落库只 +1。
下面两节是它牵出来的两个真问题，一个在前端，一个在后端。

### 幂等键防不住的那种重复

查下去发现"勾第二项"其实勾的还是同一项：

清单行的勾选状态**只来自服务端**（`checked={!!it.doneAt}`）。
断网时那一勾发不出去，`load()` 也就没跑，于是这一行看不出任何变化。
测试里 `:not(:checked)` 重新求值，选中的还是刚才那个框；
而**真人在这里会做的事完全一样：再勾一次**。

两次点击就是两条命令、两把不同的幂等键。

> 幂等键防的是「**同一条命令**发了两遍」，
> 防不了「客户端**生成了两条**命令」。

这次第二条被服务端的 `conflict-version` 挡下了（清单项已完成），
看起来还行 —— 换成一条可以合法重复的命令，那就是实实在在的两笔。
所以修在两处，缺一不可：

* `enqueue()` **折叠重复**：待发队列里已有同一条命令（同人 + 同 operationId
  + 同 params/query/body）时，返回原来那一条连同它原来的幂等键，不新增。
  已挪进「需要处理」的不算 —— 那条要人来决定，重发是一次新的尝试。
* 行上显示「**待发**」且勾不动。这不只是提示：
  看不出变化的人一定会再点一次，**光靠去重是在补救，显示状态才是不让它发生**。

「待发」刻意不等于「已完成」：勾是人的意思，落库还没发生 ——
所以阻塞标记照旧、计数条上那个"已完成"仍然是服务端的数，一动不动。
界面不替服务端把话说满。

### 后端：断线时连接被抽走

同一次集成测试在服务端留下一条日志：

```
ERROR [Problem] error: new row violates row-level security policy for table "audit_entry"
    at AuditService.write ... at StaffingService.completeItem
```

**没有任何一条测试断言到它** —— 24 条全绿，它只是躺在日志里。

根因在请求中间件：

```ts
res.on("close", release);   // ← close 不只在响应发完时触发
```

`res` 的 close **客户端中途断开也会触发**。原来的兜底不分这两种情况，
一律 `ROLLBACK` + `client.release()`，于是断线时发生的是：

> 处理器还在跑，它脚下的连接已经回滚、并且**还进了连接池**。

之后它的每条 SQL 都打在一个没有 `app.account_id` 的连接上
（`SET LOCAL` 随事务一起没了，所以 `app.current_tenant_id()` 返回 NULL，
`audit_entry` 的 `WITH CHECK` 就此不成立）——
更糟的是那条连接**可能已经被下一个请求领走**，两个请求在同一条连接上交错。

而且回滚之后连接处于自动提交模式：
业务 `UPDATE` 有可能落库，它的审计条目没有。
那正是 `AuditService` 自己注释里写着"绝不能发生"的那件事 ——
**业务成功、轨迹丢了**。

复现（`--max-time` 式的中途 abort），修复前后各跑一次：

| | 服务端日志 | SS-13 未完成项 |
|---|---|---|
| 修复前 | `violates row-level security policy` | 11 → 11（活丢了） |
| 修复后 | 干净 | 11 → **10**（活落库了，审计与幂等键同一事务） |

修法是让连接的归属明确：拦截器进入处理器时置 `inFlight`，
兜底释放看到它就什么都不做，交给拦截器按处理结果收尾。
Guard 抛异常导致处理器压根没跑的那种情况，兜底照旧释放 —— 它本来就是为那个而存在的。

**断线不回滚。** 请求已经被授权、活也是真做了，
响应丢在回来的路上是常态；客户端带着同一把幂等键重放，服务端认得它。
这和 `client.ts` 里那段注释是同一个假设：

> 安全性来自那把键，不来自"它应该没到"这种猜测。

回归测试 `apps/api/test/request-lifecycle.test.ts` 用假连接验时序，不碰数据库 ——
真发一个请求再掐掉，掐早了服务端还没开始、掐晚了它已经答完，
两种都会让测试变成"有时候绿"。

### 当前已知问题

1. **冷启动就离线的话，仍然会丢。**
   队列归属由 `/v1/me` 之后设置；如果打开应用时就没有网络，
   `loadMe()` 失败 → 没有归属 → L2 命令无法入队，退回原来的抛错路径。

   要覆盖冷启动，得把身份也缓存下来 —— 那需要先想清楚「缓存的身份
   算不算一次有效登录」，是个权限问题，不是存储问题。
2. **只有 L2 进队列。** L1 的那几个 POST 断网时仍然会失败并报错
   （不再静默，但也没排队）。给它们加幂等键是契约层的改动，
   不该顺手夹带在这一阶段。
3. **没有冲突提示。** 重放时如果服务端状态已经变了（别人先动了同一条），
   4xx 会进「需要处理」，但界面只显示服务端的原话，
   没有"你离线期间这条被别人改过"这种针对性的说明。
4. **只有启动清单这一页显示行内「待发」。** 队列层的去重是全局的，
   但"这一行正在待发"目前只有启动清单画得出来。
   其余写入页（工时、访视、交接）断网时仍然只有那条发件箱提示，
   于是**它们还留着"再点一次"的空间** —— 靠 `enqueue` 折叠兜住，
   而兜住不等于不该发生。铺开是机械劳动，但要一页一页确认"待发"
   在那一页上意味着什么，所以没有顺手全铺。
5. **`apps/web` 没有单元测试框架。**
   队列的折叠逻辑目前只由集成层的行为断言间接盖住 ——
   直接测 `enqueue()` 要先给 web 引一套 vitest + 浏览器存储的替身，
   那是 Phase 8「测试」的事，不该夹带在这一阶段。
6. **处理器卡死时连接仍会泄漏。** 兜底释放现在只在处理器没跑起来时动手；
   如果处理器永远不结束，那条连接就一直被占着。
   原来那版会把它抢回来 —— 但抢回来的代价是本阶段修掉的那个问题。
   正确的做法是给处理器加超时，属于 Phase 8。

## Phase 8a · 现在就不成立的四件事

Phase 8 的清单很长。这一轮只挑**当下就不成立**的：
一个从来没验过的门禁、一个开不出第二户的系统、一条卡死就泄漏的连接，

### 一、破坏性变更门禁：一直绿着，因为它什么都没比

CI 里跑了很多轮的那个门禁，基线取的是 `git show HEAD:openapi.yaml`。

> `actions/checkout` 在 `pull_request` 事件里检出的是**合并提交**。
> 于是 HEAD 里的 `openapi.yaml` 就是这个 PR 自己提议的那一份，
> 而工作区里刚生成的也是同一份 —— **文件在跟自己比**。

比对逻辑本身有 8 条测试盖着，一直是绿的；**取基线这一半一个测试都没有**。
坏掉的恰好是没被测的那一半 —— 这不是巧合，是常态。

还有第二条静默放行：取不到 ref 时 `catch { return null }` 然后 `exit 0`。
浅克隆、ref 写错、git 不在，**任何一种都会让门禁绿着过去**。

修法两边各一半：
* 脚本：加 `--baseline-ref`；**CI 环境下拒绝回退到 HEAD**；ref 取不到就 `exit 2`。
* 工作流：PR 传 `base.sha`，push 传 `HEAD^`，`fetch-depth: 0`（浅克隆里没有 base 那个提交）。

新增 4 条测试，专盯**基线是怎么选的**，包括「给一个契约确实不同的 ref，
必须真的比出差异」—— 比不出来就说明它又在跟自己比。

**补记：第一版的传参方式在 CI 上直接红了，而且红得很好。**

```
> npm run check:breaking -w @sitedesk/contracts --baseline-ref 2586482…
> tsx scripts/check-breaking.ts 2586482…
```

`npm` 把 `--baseline-ref` 这个**名字**自己吃掉了，只把值透传下来
（根脚本外面还套了一层 `npm run … -w`，参数每过一层都可能被重新解析）。
脚本收到一个没有名字的裸 sha，判定"没给基线"，**按规矩 exit 2**。

门禁这次是对的 —— 它宁可停下也不肯拿 HEAD 凑合，
这正是这一轮想要的行为。错的是传参方式。
改用环境变量 `SITEDESK_BASELINE_REF`：它不经过任何一层的参数解析。
并在错误信息里点破这个坑 —— argv 里出现没有名字的裸 sha 时直接说
"这几乎可以肯定是 npm 把参数名吃了"，因为这种失败看起来像"我明明传了"。

顺带印证了门禁真的在干活：把基线指向 Phase 6a 那会儿的 ref，
它报出 `ActionKey 枚举新增取值：piConfirm, rateWrite, subjRead…` ——
那正是 6c 真实发生过的契约扩张，而当时的门禁一个字也没说。

### 二、这个系统开不出第二个租户

角色矩阵（`role` / `role_field` / `role_action` / `role_module`，224 行）
和恒济那 20 个人、15 个中心、598 个受试者躺在同一个 seed 文件里。
问题不只是"混着"：

```
role.id = uuid5('role:' + code)      -- 不含租户
```

两个租户的 `crc` 会算出同一个 UUID，第二个租户直接撞 `role_pkey`。
**不是要多做点工作，是插不进去。** 而这件事没有任何测试盖住 ——
因为从来没有人试过开第二个。

现在：`app.provision_tenant(code, name)` 建租户 + 整套角色矩阵，
角色 id 现生成；seed 只管演示数据，按 `code` 反查角色。

目录写成"授予了什么"而不是逐行 INSERT —— `field_key` / `action_key`
是全局注册表，所以只需要说哪些是给的：

```sql
('crc', '临床协调员 CRC', false, 'assigned',
 ARRAY['subject'],
 ARRAY['ethics','subjRead','subjWrite','timeWrite'],
 ARRAY['crc','mysite','startup','sched','subj', …])
```

一个角色能做什么，现在是三行数组。同样的事实散在 224 行 INSERT 里
要拼很久才看得出来 —— 而权限矩阵恰恰最需要「一眼看得出」。

拆完之后演示租户的矩阵**逐条不变**（8 / 40 / 104 / 72），
新租户与它**完全一致**，重复开户幂等且不换 id（换了的话引用它的账号就断了）。

### 三、卡死则泄漏：超时要下在数据库，不是下在 rxjs

Phase 7 修断线时留了一条：处理器永远不结束的话，那条连接就一直占着。

顺手的写法是给 observable 加 `timeout()`。**那是错的，而且错得眼熟**：
它只让 observable 出错，底下那个 promise 照跑 —— 于是又变成
"连接已经还回去了，处理器还在用它"，正是 Phase 7 刚修掉的问题。

> 取消一个正在跑的请求，只能由**执行它的那一方**动手。

所以下在数据库：`SET LOCAL statement_timeout`（报错的是处理器正在
`await` 的那条查询，于是它真的停下来）＋
`SET LOCAL idle_in_transaction_session_timeout`（处理器卡在数据库之外时，
由数据库把这条连接终结掉，连接池随即丢弃它）。

### 四、"api 测试对负载敏感" —— 记了两个阶段，其实是一行代码

这条已知问题从 Phase 6c 就挂着，一直当成环境问题：单独跑绿，
和别的套件一起跑偶尔红，失败的还每次不一样。

这一轮先用测量排掉了两个猜测：

| 猜测 | 测量结果 |
|---|---|
| 每个测试文件的库名撞了（`testPath ?? "shared"` 兜底） | 逐次记录库名，**7 个文件各不相同**，从没回退到 shared |
| 前面的套件漏了连接 | 跑完 db + policy 后 `pg_stat_activity` 只剩 1 条 |

真正的原因在事务收尾那一行：

```ts
tap({ next: () => void done(true) })   // 发了就不管
```

**COMMIT 还在路上，响应已经发走了。** 于是客户端拿到 201，
紧接着的 GET 从连接池里取到另一条连接 —— 那笔还没提交，读回来的是旧值。

对照失败现象：`POST :edc-entered` 断言 200 通过、紧接着的 GET 读回
`pending`；交接完了看不到中心；该 201 的返回 404。**全是同一个形状。**
平时提交快过一次网络往返，所以大多数时候看起来是对的 ——
"大多数时候是对的"正是这类 bug 最难被认领的原因，它被记成了"负载敏感"。

同一行还吞掉第二件事：**COMMIT 失败没人接**，而客户端已经收到成功了。
人以为录进去了，系统里没有。

改成 `concatMap`：提交完成，值才继续往下走。慢一个 COMMIT 的往返，
换"响应说成功就是真成功"。

回归测试让 COMMIT 慢一拍，断言顺序必须是 `commit → release → response`；
换回原来那行立刻红成 `expected [ 'response' ] to deeply equal
[ 'commit', 'release', 'response' ]` —— 响应确实抢在提交前面出去了。

## Phase 8b · 性能 —— 先造量，再量

性能这一节最容易写成"看着哪里慢就优化哪里"。问题是**开发库上没有哪里慢**：
15 个中心、598 个受试者，什么都是毫秒级的。所以这一轮的顺序是
先装仪器、再造量、最后才动手改。

### 一、把 N+1 变成看得见的数字

N+1 的特征不是"慢"，是**条数随数据量线性增长**：
开发库上 15 个中心跑得飞快，上线之后 1500 个中心就是 1500 条查询。
它不报错、不变红、在任何功能测试里都表现正常。

所以每个请求现在都数自己发了多少条 SQL：

* 业务代码拿到的是一个**只数数的代理**。不直接给 `client.query` 打补丁 ——
  连接会还回池子给下一个请求用，补丁会跟着回去，
  把这一个请求的计数器泄漏给下一个。代理只活在本请求的上下文里。
* 超过阈值（默认 30）打一条 warn 并写出 operationId —— **给它装个响铃**。
* `SITEDESK_QUERY_STATS=1` 时响应带 `X-Query-Count`，供测试断言。

判据刻意选**相对条数**而不是耗时：同一个端点，`limit 1` 与 `limit 50`
必须发同样多的 SQL。这条对机器速度免疫（不会变成 flaky），
却正好卡住 N+1 的定义。

七个列表端点 + `/v1/me` 全部通过 —— **目前没有 N+1**。
验过它不是空的：往中心列表里塞一个按行查库的循环，立刻红成
`expected 17 to be 3`。

### 二、造量：夹具被 schema 拦了四次

`db/scripts/inflate.mjs` 用集合式插入把库灌到
**315 个中心 / 30,598 个受试者 / 180,011 条访视**，9 秒。

写这个夹具的过程本身是个意外的好消息：它被**约束连续拦下四次** ——
入组必须有随机号、筛败原因是受控词表、退出原因也是、
访视状态取值受限且 `done_pending_pi` 必须有实际完成日。

> 这套 schema 的不变量强到**连造假数据都绕不过去**。

绕过约束造出来的数据，量出来的性能是另一个系统的性能。

### 三、48 秒

灌完之后量最普通的那个请求 —— 经营层打开访视列表、不带任何筛选：

```
Seq Scan on subject_visit  (actual rows=180011)
Sort Method: top-N heapsort
Execution Time: 48191.243 ms
```

**48 秒。** 两件事叠在一起：

① 列表按 `upper(v.visit_window)` 排序，那是个**表达式**。
表上已有的两条 `(study_site_id, target_date)` 索引都排不上用场：
既不是按这个键排的，又都带 `WHERE status = …` 的部分条件，
而默认列表恰恰不筛状态。

② **RLS 的行谓词是每行一次函数调用。** 全表扫过 180,011 行就是
180,011 次 `app.site_visible()`，然后才轮到 `LIMIT 51`。
同一个查询限定到一个中心时只扫 600 行、185 毫秒 ——
行数差 300 倍，时间差 260 倍。**开销是按行走的。**

这就是"上了 RLS 之后要格外小心全表扫"的实际含义：
在别的系统里全表扫只是慢，在这里它还要乘上一个函数调用。

修法是按排序键本身建一条表达式索引（迁移 0013），规划器就能顺着索引
取前 51 行即止，RLS 也只判 51 次：

| | 计划 | 实测 |
|---|---|---|
| 修复前 | `Seq Scan` + top-N heapsort，扫 180,011 行 | **48,191 ms** |
| 修复后 | `Index Scan using visit_feed_idx`，取 51 行 | **16 ms** |

**3000 倍。** 而它在开发库上完全看不出来 —— 两种计划都是毫秒级。

```
apps/api/test/query-count.test.ts          8 条：条数不随取回行数增长
db/scripts/inflate.mjs                     性能夹具：集合式插入，尊重全部约束
```

### 四、给那 3000 倍装上守卫

上一节修好了，但**守不住**：既有测试只能断言"索引还在"，
挡不住真正会发生的那种退化 —— 索引还在，查询改了一个字，计划悄悄退回全表扫。
而这件事在开发库上测不出来：小库上两种计划一样快，EXPLAIN 长得都对。

`npm run perf:plans`（新 CI job）自己建库、灌到 18 万行、
**以应用角色（RLS 生效）**量执行计划。判据是「用了哪条索引」，不是「跑了多少毫秒」——
耗时依赖机器，放进 CI 必然变成 flaky；计划形状不依赖机器。

用 owner 量是没有意义的：owner 绕过 RLS，行谓词那一层的开销根本不会出现。

验过它不是空的 —— 把 0013 那条索引注掉，立刻红 2/4，并打出完整计划：

```
Seq Scan on subject_visit v
  Filter: (… AND app.site_visible_by_id(study_site_id) AND (tenant_id = app.current_tenant_id()))
  Rows Removed by Filter: 179410
```

那行 `Filter` 就是「RLS 行谓词是每行一次函数调用」的**直接证据**：
179,410 行被逐行判掉。之前这句话是从耗时倒推出来的，现在它写在计划里。

加一条新的待测路径 = 往 `CASES` 数组里加一项。
于是"其余路径的测量"从一件机械劳动变成了填一行。

过程中又踩了一次已经写在别处的坑：多行 SQL 经 `psql -c` 传过去，
换行变成字面的 `\n`，psql 在那儿报语法错、位置毫无意义。
`apps/api/test/harness.ts` 里早写过这条，我还是踩了 ——
所以这次修在**辅助函数**里压成一行，让调用方没有机会再踩。
顺带把 `execSync` 的失败输出从一屏字节数组改成人话（否则真正的原因埋在 Buffer 里）。

### 五、apps/web 终于有了单元测试

补的不是"再多一层测试"，而是前两层**结构上够不着**的那一条：

> 重复入队会被折叠 —— 这条在 e2e 里根本触发不了。
> 因为界面在第一次入队之后就把那一格变成"待发"且勾不动了，
> **人点不了第二次，测试自然也点不了。**

而判重恰恰不能只靠界面：界面是"不让它发生"，队列这一层是"发生了也不出错"。
两道都要在，所以这一条只能在这一层直接验。

13 条覆盖：只有 L2 进得了队列、折叠（含"不同参数不折叠""不同的人不折叠"
"已进需要处理的不参与折叠"）、FIFO、4xx 挪走后队列继续走、
requeue 保留原幂等键但换新序号、localStorage 坏了退回空队列且不清空存储。

不引 jsdom，只给一个内存 `Storage` 替身：被测的是队列逻辑，不是浏览器。
引一整个 DOM 只为一个 Storage，既慢又会把"这组测试到底在测什么"搅浑。

验过不是空的：去掉 `enqueue` 里的折叠，那条立刻红成
`expected […2 项] to have a length of 1 but got 2`。

顺带修了一处早就存在的漂移：`package-lock.json` 里 apps/api 还挂着一个
它自己 package.json 并不声明的 `tsx`。`npm ci` 要求两者严格一致 ——
这类漂移平时不响，直到某次 CI 上突然装不上。

### 当前已知问题

1. ~~计划退化没有自动守卫~~ —— 已补上（`perf:plans` job）。
   仍然只覆盖 4 条查询路径；加一条是往 `CASES` 里填一行。
2. **工时、审计、损益在同等量级下还没量过。** 仪器与 CASES 表都在了。
3. **没有并发负载实测**（连接池上限、锁等待），属 8c。
5. 其余沿用 Phase 8a 的清单。

## Phase 8c · 安全 —— 两个洞，一个是"写了没读"，一个是"没人拦"

先看清楚现状再动手。已有的底子是厚的：令牌落库存哈希、
`resolve_session` 同时查吊销/过期/账号在职、幂等键按账号隔离、
magic-link 对不存在的账号返回同样的 202（不是账号枚举器）、
生产依赖 `npm audit` 0 漏洞。所以这一轮找的是**它们之间的缝**。

### 一、同一把钥匙，开了另一扇门

`idempotency_key` 的表注释写着：

> request_hash 用于识别「同一把钥匙开不同的门」

但 `request_hash` 比的是**请求体**，而 `begin()` 查行只用 `(key, account_id)` ——
`endpoint` 这一列**记下来了，却从来没有被比对过**。

于是只要两个端点碰巧哈希出同样的载荷，钥匙就真能开另一扇门：

| 端点 | 载荷 | 动作权限 |
|---|---|---|
| `completeStartupItem` | `{ id }` | 无 |
| `completeHandover` | `{ id }` | 无 |

两个都不需要动作权限，同一个人都调得动。把启动清单项的 id 拿去调交接完成、
复用同一把键 —— 哈希一致、已完成，于是 `command()` 里的 `begin()`
**在处理器跑起来之前**就返回了上一次的响应体。

实测：本该 404 的请求返回 **201，body 是那条启动清单项**
（`"item":"伦理初始审查递交…"`，`"doneByName":"凌远"`）。
一个本不存在的操作，报告成功了。

修法是把那一列真的用起来：先比门，再比请求体。顺序有意义 ——
门不对的时候，请求体一致恰恰是最危险的情形。

> 一列只写不读，等于一个没接上的保险丝。
> 而表注释还在替它作保。

顺带记下另一个同类的：`response_status` 也是只写不读 ——
`command()` 存了 200，重放时却直接 `return replay.body`，
HTTP 状态码仍由 Nest 给（POST 缺省 201）。目前无害，但同属"写了没读"。

### 二、一个开关，两个后门，没人拦

`SITEDESK_DEV_LOGIN=1` 同时打开两件事：

1. `POST /v1/auth/dev-session` —— **无凭据换取任意账号的会话**；
2. `POST /v1/auth/magic-link` —— 把一次性登录令牌**回显在响应体里**。

开发时两个都必要，生产上任何一个都足以让整套权限体系失去意义。
而在此之前，没有任何东西阻止它出现在生产环境。

新增启动自检 `preflight.ts`：这些组合下**拒绝启动**。
拒绝启动是最刺耳、也最安全的失败方式 ——
它发生在部署那一刻，而不是三个月后有人翻日志的时候。

同一处还拦下另一条：`APP_DATABASE_URL` 指向 owner 角色。
owner 绕过 RLS，行范围会全面失效，而**所有测试仍然是绿的** ——
这是最难发现的那一类失守，只能在启动时拦。

实测两条都真的退出（exit 1）并写明原因。
另有一条测试专门验"`sitedesk_app` 不会被误判成 `sitedesk`"：
正则写松一点就会把正确配置也拦下来，而那种误报会让人直接把自检关掉，
等于什么都没做。

### 修改 / 新增的文件

```
apps/api/src/infra/idempotency.service.ts  先比端点，再比请求体
apps/api/src/infra/preflight.ts            启动自检（新增）
apps/api/src/main.ts                       建应用之前先自检
apps/api/test/idempotency.test.ts          跨端点复用键的复现与回归
apps/api/test/preflight.test.ts            5 条：纯函数，不碰数据库
apps/api/src/infra/rate-limit.ts           固定窗口计数器（新增，key 数量有上限）
apps/api/src/auth/auth.controller.ts       两个 @Public() 入口接上限流
apps/api/test/rate-limit.test.ts           6 条：注入 now，不 sleep
apps/api/test/gate-and-auth.test.ts        端到端：到上限真的 429
```

### 测试结果

`npm test` **364 passed**（79 + 26 + 22 + 45 + 19 + 160 + 13），
`typecheck` / `arch:check` 通过。

三处修复都验过反向：跨端点复用键 → 修复前实测返回 201 + 错的 body；
启动自检 → 两条组合都真的 exit 1；限流 → 去掉 gate() 立刻红成
`expected 202 to be 429`。

### 三、契约里承诺了 429，实现从来没兑现

`rate-limited` (429) 一直在 `COMMON_ERRORS` 里 ——
**每个端点都声明过自己可能返回 429，而实现一直没有。**
和上面那个 `endpoint` 列是同一种形状：声明在，执行不在。
（好处是：把它做出来不构成契约变更。）

现在两个 `@Public()` 入口都接上了。两个决定值得写下来：

**① 按 `login` 计数，不按 IP。**
IP 是攻击者能换的东西（代理池、`trust proxy` 没配对时伪造 XFF），
login 是他换不掉的 —— **他要刷的就是那一个邮箱**。
挡住"同一个账号被反复发链接"正是这个端点真正要保护的东西。
IP 维度留给网关，那一层才有可信的来源地址。
配一条测试：换个账号照样 202 —— 全局计数的话，一个人被刷就把所有人挡在
门外，那是拒绝服务，不是防拒绝服务。

**② 计数在发送之前。**
放在后面的话，限流拦住的是"记一笔"，而邮件已经发出去了，
被刷的那个邮箱一点也没少收。

**③ 放进程内，不放数据库。**
数据库版本天然跨实例、也扛得住重启，但它有个要命的副作用：
**未认证的流量就此获得了一条写库的路径** —— 限流本身成了打库的手段。
代价写在明面上：多实例部署时实际配额 = limit × 实例数。
要真正跨实例得换共享存储，那是有了负载均衡之后再做的事。

计数器的 key **必须有上限**，否则每来一个新 key 就多一条记录，
限流器自己就成了内存泄漏 —— 而 key 的多少恰恰由未认证流量决定。
测试里灌 1000 个 key 进容量 100 的窗口，断言不超容量。

时间用注入的 `now` 推进，不用真 sleep：靠 sleep 的时间相关测试要么慢、
要么在 CI 上偶尔红，而"偶尔红"会让人把它标成 skip。

### 当前已知问题
1. **限流只在单实例内有效**（见上）。多实例部署前必须换共享存储。
2. **没有安全响应头**（CSP / X-Content-Type-Options / HSTS 等）。
   API 只返 JSON，风险有限；前端上线时必须补。
3. `response_status` 只写不读（见上，目前无害）。
4. 并发负载实测（连接池上限、锁等待）仍未做。

## Phase 9a · 生产构建 —— 那条从来没被走过的路

Phase 6a 就记下的欠账，Phase 9 第一步撞上它。先复现，不猜：

```
$ npm run build -w @sitedesk/api && node apps/api/dist/main.js
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  .../packages/contracts/src/kernel/primitives.js
  imported from .../packages/contracts/src/index.ts
```

`tsc -p tsconfig.build.json` 只编译 apps/api 自己。而 workspace 依赖以
**TS 源码**导出（`"main": "./src/index.ts"`），产物里
`import "@sitedesk/contracts"` 指到那份 `index.ts`，
它内部又写着 `./kernel/primitives.js` —— TS 的 ESM 写法，磁盘上没有对应的 `.js`。

> 这条断了整整五个阶段没人发现，因为**在此之前没有人真的
> `node dist/main.js` 过**：测试走 vitest（有转译），
> 开发走 `@swc-node/register`（也有转译）。
> **一条从来没被走过的路径，不会有任何东西提醒你它是断的。**

### 为什么是"打包"，不是"把每个包也编成 dist"

后者要动四个包的 `exports`，而那四个包同时被 vite、vitest、swc 消费着 ——
一个生产问题不该让开发路径全部改道。
这里只内联 `@sitedesk/*`，其余（`@nestjs`、`pg`、`rxjs`、`zod`）
保持外部依赖照常由 npm 安装。**影响面止于 apps/api。**

### 顺序不能反：先 tsc，再 esbuild

esbuild **不支持 `emitDecoratorMetadata`**，而 NestJS 的依赖注入正靠它。
所以 tsc 先把 apps/api 编成带元数据的 JS，
esbuild 只负责把 workspace 依赖（纯 TS、无装饰器）内联进来。
反过来做，DI 会在运行时报"找不到可注入的类型"。

### 冒烟检查，以及它第一次报错时指错了地方

`npm run smoke -w @sitedesk/api` 在**真产物**上验四件事：

1. 生产配置 + 开发登录 → 拒绝启动（Phase 8c 那道闸，在真产物上再验一遍）
2. 起得来（DI 装配成功 —— 装饰器元数据没在打包时丢掉）
3. 一个真实请求走到底：认证 → 行范围 → 契约
4. 未认证 401（守卫也在产物里）

第 1 条**刻意放在最前**：自检要是根本没被打包进来，后面那个正常启动
也会绿 —— 而那种绿什么都不说明。

验它不是空的时候，出了一个值得记的插曲：把 workspace 内联关掉之后，
检查确实红了，但报的是「拒绝启动了，但没说清原因」——
因为**"被自检拒绝"和"根本起不来"退出码都是 1**。
抓住了，却指向了错的地方。加一条崩溃特征的判别之后，
同样的破坏现在报的是「产物根本起不来（不是被自检拒绝的）」并附上真实错误。

这一整轮反复出现的同一件事：**失败必须指对地方，否则下一个人会照着错的方向查。**

```

apps/api/scripts/smoke.mjs     真产物冒烟：起得来 / 打得通 / 拦得住
apps/api/package.json          bundle / start / smoke
.github/workflows/ci.yml       database job 末尾加冒烟
.gitignore                     apps/api/build/
```

`npm test` **364 passed**；`smoke` 四条全过；`typecheck` / `arch:check` 通过。

1. **只解决了"能跑起来"，还没有部署物**。Dockerfile、健康检查端点、
   优雅停机、日志格式、配置注入都还没有 —— 那是 9b。
2. **前端的生产托管没定**。`vite build` 的产物目前只有 preview 在服务，

3. 其余沿用 Phase 8 的清单。

## Phase 9b · 部署面 —— 把插头拔掉试一次

这一轮的结论几乎全部来自一个动作：**把数据库停掉，再看会发生什么。**

### 一、存活与就绪必须分开，而且方向相反

```
/v1/health        存活 —— 绝不碰数据库
/v1/health/ready  就绪 —— 必须碰数据库
```

存活接上数据库是个很常见、代价很大的错误：数据库抖一下，所有实例的
存活探针一起失败，编排器把它们**全部重启** —— 一次数据库故障就此被
放大成一次全站故障，而重启风暴还让数据库恢复得更慢。
存活只回答"要不要重启我"，那和数据库无关。

反过来，只回 200 的就绪探针等于没有：编排器只看状态码，
它会把一个连不上库的实例照样放进负载均衡。所以就绪**真的探一次库**，
探不通返回 **503**（为此给错误码表补了 `service-unavailable`）。

两个都不返回任何内部细节 —— 它们是公开面。

### 二、第一版把中间件从探针上摘掉，立刻被自己的守卫拦下

```
Error: 不在请求上下文中 —— 说明有代码绕过了请求中间件
    at AuthGuard.canActivate
```

**那句话说得完全正确。** 全局守卫与拦截器都依赖中间件建立的上下文；
要避免的是**依赖数据库**，不是避免上下文。
改成：中间件照常建上下文，但对这两条路径**不取连接、不开事务**（`DBLESS`）。
dbless 请求拿到的"连接"是一个碰一下就炸的代理 —— 给 `null` 的话，
误用只会得到一句 `Cannot read properties of null`，指不出哪里错了。

### 三、把插头拔掉：进程直接死了

```
error: terminating connection due to administrator command
Emitted 'error' event on BoundPool instance
```

`pg.Pool` 在**空闲连接**出错时发 `error` 事件（数据库重启、主备切换、
管理员 `pg_terminate_backend`，都会让空闲连接被服务端掐断）。
EventEmitter 的规矩是：没有人监听 `error` 就当未捕获异常抛出 —— **Node 退进程**。

> 也就是说：**任何一次数据库重启都会杀掉 API 进程。**
> 一次计划内维护，变成一轮崩溃循环。

接住它就够了，池子自己会丢弃坏连接、按需重建。进程要做的只是**活着**，
等数据库回来 —— 那正是存活探针的意思。

### 四、修好之后，完整停机周期实测

| | 存活 | 就绪 |
|---|---|---|
| 库在 | 200 | 200 |
| **库停** | **200** | **503** |
| 库回 | 200 | 200 |

进程活过了整场停机（日志里两条"已丢弃该连接，进程继续"），库回来后自动恢复。

中间还抓到自己一个错：第一版用 `req.path` 判断路径，而中间件经
`MiddlewareConsumer` 挂载之后 `req.path` 是相对挂载点的那一段，匹配不上 ——
探针照样连了库，库停时 `ECONNREFUSED`。改用 `originalUrl`。

### 五、连接池终于有人关了

`{ provide: POOL, useFactory: () => makePool() }` —— 没有任何人负责 `pool.end()`。
`enableShutdownHooks()` 会调 `app.close()`，而 `app.close()` 只调 provider 的
`onModuleDestroy`。滚动发布时旧实例的连接一直挂到 TCP 超时，
每实例 max=10，几轮就能把 postgres 的 `max_connections` 吃光。

### 六、把"不碰库"钉成一个数字

光靠读代码保证不了：中间件默认对**每个**请求取连接，
路径写错一个字母它就悄悄回到依赖数据库的状态，而且**在数据库正常时完全看不出来**。
所以用已有的查询计数器断言：存活探针 `X-Query-Count` 必须是 **0**，
并配一条对照（普通端点 ≥ 1）—— 否则那个 0 可能只是因为计数器没接上。

验过不是空的：把路径匹配改回 `req.path`（就是我刚踩的那个 bug），
立刻红成 `expected 1 to be +0`。

顺带修了这条测试自己的毛病：`SITEDESK_QUERY_STATS` 原本是模块级常量，
在 import 那一刻就定死了，而测试是在 `beforeAll` 里设它的 —— 太晚了。
于是那条测试**只有在命令行预先设了变量时才绿**，跑 `npm test` 是
`expected NaN to be +0`。改成按次读取。
**它一直是靠外部条件通过的，不是靠被测代码。**

### 七、镜像

两阶段 Dockerfile：构建阶段有全部 devDependencies，运行阶段只带
`--omit=dev` 的运行时依赖 + 一个打好的文件 + 迁移脚本（迁移必须和服务同版本）。
非 root 运行，`HEALTHCHECK` 打存活探针。

**本环境没有 docker daemon，镜像构建没能在本地实测。**
所以新增了一个 CI job：真的 `docker build`，真的起容器，
打探针 + 打一个真实请求 + 验未认证 401。
只构建不运行的镜像检查，和"编译通过就算能跑"是同一种自欺。

## Phase 9c · 停机顺序 —— 先摘流量，再关门

### 一、先量：在途请求会不会被拦腰砍断

用一把 `ACCESS EXCLUSIVE` 表锁造了个 8 秒的慢请求，SIGTERM 打在中途：

```
在途请求的结果: HTTP 200
响应前 120 字节: {"studySiteId":"44cb314d-…","siteCode":"SS-01","hospital":"北京协和医院",…
```

**它拿到了 200 和完整 body。** Nest 的 `enableShutdownHooks()` 本来就会把
在途请求做完 —— 这条挂着的已知问题，实测下来是**已经对的**。
量一下比继续记着它便宜。

### 二、但还差一步才是零停机

问题不在在途请求，在**新来的**：监听一关，负载均衡还在转发的连接
直接撞上 connection refused。LB 通常要一两个探测周期才会摘掉实例，
而进程等不了 —— 于是每次发布都漏掉一小撮请求。

正确的顺序是三步：

```
① 收到 SIGTERM → 就绪探针立刻 503（存活仍 200）
② 等一个探测周期，让 LB 把自己摘掉
③ 再 app.close()：停止监听 → 等在途做完 → 关连接池
```

**存活在整个过程中保持 200** 是有意的：这个进程没坏，只是不该再接新活。
此时报存活失败，只会让编排器多做一次无谓的重启。

真产物上实测：

| 时刻 | 存活 | 就绪 |
|---|---|---|
| 停机前 | 200 | 200 |
| SIGTERM 后 1 秒（排空中） | **200** | **503** |
| 排空结束 | 进程已退出 | |

```
[shutdown] 收到 SIGTERM：就绪探针开始返回 503，4000ms 后关闭。
[shutdown] 停止监听，等在途请求做完…
[shutdown] 已关闭。
```

### 三、把顺序钉成测试

退出与信号注册都做成可注入的，否则测试会把自己一起退掉。
5 条：默认不排空、**SIGTERM 一到就绪立刻转红（在 close 之前）**、
SIGINT 同样处理、连发两次信号只关一次、`wait=0` 立刻关。

验过不是空的：把"转红"挪到 `close` 之后（就是那个会漏请求的错误顺序），
立刻红成 `expected false to be true`。

### 修改 / 新增的文件

```
apps/api/src/infra/shutdown.ts             三步停机（新增）
apps/api/src/main.ts                       改用它，不再用 enableShutdownHooks 的信号处理
apps/api/src/modules/platform/health.controller.ts  排空中就绪返回 503
apps/api/test/shutdown.test.ts             5 条：验的是顺序
```

### 测试结果

`npm test` **372 passed**（79 + 26 + 22 + 45 + 19 + 168 + 13），
`smoke` 四条全过，`typecheck` / `arch:check` 通过。

### 当前已知问题

1. **镜像只在 CI 上验**（本环境无 docker daemon）。
2. **日志还是 Nest 的默认格式**，不是结构化 JSON。

## Phase 9d · 结构化日志 —— 把散落的行拼回一条时间线

### 一、默认格式里没有请求 ID，于是最要紧的那件事做不了

Nest 默认的日志长这样：

```
[Nest] 42  - 2026/08/26 10:11:12   WARN [QueryCount] 发了 47 条 SQL
```

人读着舒服。但线上真正要做的事是**按请求把散落在各处的行拼回一条时间线**：
这个 500 是哪个请求打的？它前面那条 N+1 告警是不是同一个请求？
谁、什么角色、在什么范围下打的？

默认格式里一个字段都没有 —— 拼不回时间线，日志就只剩"事后翻着看"的价值。

所以改成一行一条 JSON，固定字段 `ts / level / scope / msg`，
并且**自动带上请求上下文**（`requestId / operationId / accountId / role`），
从 AsyncLocalStorage 里取，调用方什么都不用传。
靠传参的话，迟早有一条路径漏传，而漏传的那条正是要查的那条。

响应体里本来就有 `traceId`（= requestId）。两边现在对得上了：
用户报一个号，日志里就能捞出那一条堆栈。

### 二、日志绝不能抛异常

它经常在异常处理路径上被调用（`ProblemFilter`、连接池的 `error` 事件）。
在那里抛，等于把一个能看见的错误换成一个看不见的崩溃。

两个真会遇到的坑，都兜住了：`bigint`（`JSON.stringify` 直接 TypeError）、
循环引用（往日志里塞一个 request 对象就会撞上）。`toJSON` 自己抛也一样 ——
兜底行只放字符串，保证仍然是一条能 parse 的记录。

### 三、每个请求一行访问日志，包括没走完的那些

挂 `close` 而不是 `finish`：`finish` 只在响应**发完**时触发，
客户端中途断开就一条日志都没有 —— 而"请求打到一半没了"恰恰最需要留痕。

### 四、那层 runInCtx 看着可有可无，去掉之后冒烟检查照样全绿

访问日志靠把回调包在 `runInCtx` 里才能带上 `requestId`。
把它去掉，产物冒烟检查**六条全过** —— 于是量了一下 Node 的真实行为
（真 server + 真 fetch，两种收尾方式各来一次）：

| 收尾方式 | close 回调里还有没有 store |
|---|---|
| 正常收尾 | **有** —— close 发自 `res.end()` 的续体，仍在 `als.run` 作用域内 |
| 客户端断开 | **没有** —— 事件来自 socket 拆除，跟处理器不在一条异步链上 |

也就是说：不包的话，**只有断开的那些请求会丢 requestId**，
而那正是最需要把它捞出来的一类（"点了没反应" 查的就是这些行）。
冒烟检查从不中途断开，所以它看不见这件事 —— 补了一组会断开的测试。

验过不是空的：去掉 `runInCtx`，"断开的请求也带 requestId" 红成
`expected undefined to be defined`，而"正常请求"那条仍然是绿的 ——
正好复现上表。

### 五、在真产物上再验一遍

单元测试验的是 `emit` 这个函数；线上被采集的是**进程写进管道的字节**。
中间隔着 `NestFactory` 的 logger 选项有没有真生效、打包有没有把它替换掉、
有没有哪个依赖偷偷 `console.log` 了一行 —— 任何一条都足以让
"结构化日志"退化成"大部分结构化"，而采集器遇到一行坏的就整条断掉。

冒烟检查因此加了两条（共六条）：

```
✓ 日志一行一条 JSON，字段齐全（67 行，含 Nest 自己那些行）
✓ 响应里的 traceId 在日志里捞得到（84389b20-… → GET /v1/study-sites 401）
```

### 开关

| 变量 | 默认 | 作用 |
|---|---|---|
| `SITEDESK_LOG_FORMAT` | 生产 `json`，其余 `pretty` | 机器读 / 人读 |
| `SITEDESK_LOG_LEVEL` | `info` | `debug` 打开探针访问日志等细节 |

两个都**按次读取**，不做成模块级常量 —— 常量在 import 那一刻就定死了，
测试在 `beforeEach` 里设的变量根本不生效，那样的测试是靠外部条件通过的。

```

apps/api/src/infra/ctx.ts                  ctxOrNull()：请求之外拿不到就返回 null
apps/api/src/infra/request.middleware.ts   每请求一行访问日志（含 aborted）
apps/api/src/infra/problem.ts              未预期异常改走 emit，与 traceId 对得上
```

## Phase 9e · 前端的生产托管 —— 又一条从来没被走过的路

### 一、`vite build` 出来的东西，一直只有开发工具在服务它

在此之前，dist/ 的唯一服务者是 `vite preview`。而 preview 是**开发工具**，
Vite 自己的文档写着不要用于生产。于是"前端怎么上线"这件事一直是空的 ——
和 Phase 9a 之前 `node build/server.mjs` 那条没人走过的路径是同一类问题。

上线真正需要的四件事，preview 一件都不保证，而且**全都不会报错**：

| | 缺了会怎样 |
|---|---|
| SPA 回退 | react-router 用 history 路由。刷新 `/sites/abc` 就是 404 —— 开发环境永远正常，上线之后"一刷新就白屏" |
| 缓存方向 | assets/ 带哈希可以永久缓存，index.html **绝对不能**。反过来做一次，用户手里的旧 index.html 会去要一个已经删掉的哈希文件：白屏，而且**清不掉**，因为那份 index.html 自己就在缓存里 |
| 同源 | 不同源就要处理 CORS，还得把 API 地址编译进产物（换个环境就得重新构建） |
| 安全响应头 | nosniff / CSP / frame-ancestors 是"没有就没有"的东西 |

`apps/web/server.mjs` 把这四件事做齐，另加路径穿越防护、ETag/304、
优雅停机。**运行时零 npm 依赖**（只用 Node 内置模块）——
不存在的依赖不会有 CVE。

### 二、CSP 是照着真实产物写的，不是抄模板

看了一眼构建出来的 index.html：没有内联脚本（单入口、无动态 import，
Vite 不注入 preload 垫片），所以 `script-src 'self'` 成立。
但里面有两个外部域 —— Google Fonts 的 css 和字体。

写死成 `'self'` 会让字体**静默失效**：页面照常显示，只是全部回退到
系统字体，不会有任何报错。所以 `style-src` / `font-src` 明确放行这两个域。

### 三、两层浏览器测试改跑在它上面

`npm run preview` 现在起的就是这个服务器（换个端口而已）。
于是 e2e（44 条，打 mock）与 integration（24 条，打真库）
顺带把上线要走的那条路径也走了一遍 —— CSP 拦错东西、SPA 回退没生效、
反代没通，在那里就是白屏，藏不住。两层都是绿的。

### 四、第一版的穿越测试，两道防线全拆掉照样全绿

这是本阶段最值得记的一条。用 `fetch` 写的穿越测试是**假的**：

```
fetch("/assets/../index.html")   →  线路上发出去的是 /index.html
```

fetch 会先规范化路径，服务端根本见不到那个 `..`。攻击方当然不用 fetch。
改成 `http.request` 直发之后，"immutable 判据必须落在解析后的路径上"
这条立刻能红了。

第二个问题更隐蔽：fixture 把 root 建在 `os.tmpdir()` 下，
而测试去找的是**仓库里**的 package.json —— root 的上一级是 /tmp，
那里什么都没有。把两道防线全拆掉，那组测试仍然全绿：
**它结构上就没有能力发现泄漏**。

修法是在 root 外面放一个哨兵文件，让测试去要一个真的存在的东西。
两道防线一起拆，当场 6 条红，其中一条把 `/etc/passwd` 读了出来：

```
AssertionError: expected 'root:x:0:0:root:/root:/bin/bash\ndaem…' not to contain 'root:x:'
```

顺带量清楚了两道防线的关系：`normalize` 折掉 `..`、落点核对，
**各自都够用**，单独拆掉任何一道都还是绿的。第二道留着是为了让
"有人改了第一道"不至于直接变成一个洞。

### 五、一个请求，两跳，一个号

集成测试跑起来之后，日志里看到同一个请求被记了两次 ——
边缘一条、API 一条，**两个不相干的 requestId**。拼不成一条线，
等于 Phase 9d 做的事在跨进程那一跳断了。

现在边缘发号、经 `X-Request-Id` 带给 API，API 认它。
认之前先校形状（`^[A-Za-z0-9_-]{8,64}$`）：这个值会进日志、
也会回到响应体的 `traceId` 里，半信半疑地用它等于把日志的写入权
交给调用方。形状不对就当没有，重新发一个。两边都把号回显在响应头上，
devtools 里直接能读到报障要用的那个号。

### 六、镜像与 CI

`Dockerfile.web` 两阶段，运行阶段只有 dist/ 和 server.mjs。
CI 的镜像作业现在起**两个**容器，把同源反代真的走一遍 ——

## Phase 10 · 上线清单上的五件事 —— 把「已知问题」当成待办来做

**完成于** 2026-08-26　**产出** 投递通道 + 跨实例限流 + 排空时长 + 预压缩 + HSTS
（514 单测 + 2 支迁移 + 1 支种子）

README 第七节挂着五条已知问题（第六条是指向本文件的指针）。这一轮逐条处理，
而不是再往后放一次。四条做掉了；第二条（单机不是高可用）只解决了**属于代码的那一半**
——限流不再随副本数被放大；另一半（单点数据库、没有真正的负载均衡）
不是代码能解决的，见文末。

处理的方式分两类，值得先分清楚：

- **一、四、五**是"少了一段"：功能本来就该有，只是没写。
- **二、三**是"写了，但代价被写进注释就不管了"：注释诚实，问题依然在。
  这一类更值得动手 —— **一条被记下来的代价，久了会被当成一条已经解决的事。**

### 一、登录链接送不出去：缺的不是一个函数，是半条路

原来的状态是这样的：`POST /v1/auth/magic-link` 签发令牌、写进库，
然后**不告诉任何人**。回显令牌是绝对不行的（那等于把登录接口变成后门），
所以"不回显"从来都是对的 —— 缺的是另一头。结果就是一套刚部署好的系统
没有任何人能登进去，只能由能进服务器的人跑 `login-link.sh` 代发。

#### 通道补上之后，冒出来的那个洞

真正花时间的不是发信，是发之前的那个问题：**往哪发。**

契约里 `sentTo` 字段的说明一直写着"收件地址，仅用于审计留痕"。
通道没做的时候它是惰性的 —— 存进 `login_token.sent_to`，没有人读。
通道做出来之后，如果顺手拿它当收件地址：

```json
POST /v1/auth/magic-link  {"login":"lingyuan","sentTo":"我@攻击者"}
```

这个 `@Public()` 端点就成了**一键账号接管**。而且它不会报错、不会留下
任何异常痕迹 —— 审计轨迹里记的是"凌远登录了"。

所以收件地址只能由服务端解析，而且解析与签发必须是**同一个**调用：

```sql
app.issue_login_link(p_login, p_token_hash, p_ttl_minutes)
  RETURNS TABLE (issued, reason, channel, destination, display_name)
```

应用层拿不到"往哪送"的决定权，它只负责把信送到函数给出的地址。
地址存在 `auth_identity(provider='magic-link')` —— 那个位置从 0007 建表
时就留好了，注释写着"魔法链接则是收件地址（邮箱 / 手机）"，
一直没有人往里写，因为通道还没做。

#### 一个必须说清楚的升级影响

没登记地址就不签发，意味着**从旧版本升上来的部署里，所有人都收不到链接**
（因为没有人登记过）。这不是回退：旧版本签出来的令牌本来也没有任何通道会送，
唯一能用的一直是运维代发 —— 而那条路不看收件地址，完全不受影响。

集成测试当场把这件事撞了出来：`site.spec.ts` 用 `fengle` 走链接登录，
而演示种子只给六个账号登记了地址，于是那一组五条全部超时在
"等 redeem 按钮出现"。服务端日志里写得很清楚：

```
INFO [login-delivery] 账号没有登记收件地址，未签发链接 reason=no-destination
```

修法不是给测试挑一个"有地址的账号"，是把种子改成**给每一个在职账号登记**：
演示环境里只有几个人能登录的话，其余账号看起来就是"登录坏了"，
而唯一的线索在服务端日志里。

#### 第三种账号状态

Phase 8c 立过一条规矩：申请链接时，账号存在与不存在必须返回**同样的 202**，
否则这个接口就是账号枚举器。通道做出来之后多了一种状态：
**存在、但没登记收件地址**。它同样不能被区分出来 —— 于是三种情况一律 202，
差别只写进服务端日志（`reason: no-account | no-destination | ok`）。

没登记地址时**不签发**令牌：签一把没人收得到的令牌只是往库里堆垃圾，
而"什么都没发生"在对外行为上和签发过完全一样。

#### 信必须在 COMMIT 之后才发

在事务里发的话，用户可能在令牌落库之前就点开链接，拿到一句"链接无效"
—— 而库里明明有。这类"偶尔无效"的报障是最难复现的一种。

于是给 `RequestCtx` 加了一个 `afterCommit` 挂钩，由 `TxInterceptor`
在 COMMIT 成功之后触发，**且不 await**：发信慢的是网络，让响应等它
等于把一次 SMTP 往返算进接口耗时，而这个端点返回的是 202 Accepted。
回滚时一件都不做 —— 外部世界不认识回滚。

#### SMTP 客户端为什么是自己写的

这个进程的运行时依赖只有 `@nestjs` / `pg` / `rxjs` / `zod` 四样，
而它要发的信只有一种：一行正文、一个链接、一个收件人。
为这件事引入一棵依赖树，换来的是一份长期要跟的 CVE 清单。

协议里真正会咬人的四处，各有一条测试盯着（用一个进程内的假 SMTP 服务器
真的走一遍）：

| | 不处理会怎样 |
|---|---|
| **多行应答** `250-PIPELINING` / `250 STARTTLS` | 按第一行判会在 EHLO 之后错位，症状是"某些服务器上发不出去" |
| **点开头的行** | 正文里一行单独一个 `.` 是数据结束符，信被截断，剩下的当成 SMTP 命令 |
| **CRLF** | 只发 `\n`，有的服务器认有的不认 —— 于是"在测试环境好好的" |
| **中文主题** | SMTP 头是 ASCII 的，直接塞 UTF-8 会乱码或被拒（用 RFC 2047 encoded-word） |

还有一条不是协议问题，是判断：**服务器不支持 STARTTLS 就拒绝发送**。
登录链接是一次性凭据，明文过网等于把它交出去。真要在内网明文发，
得在连接串上显式写 `?insecure=1` —— 让这个决定留下痕迹。

#### console 通道在生产环境**拒绝启动**

开发环境需要一条"把链接打在自己日志里"的通道，否则本地根本拿不到链接。
但同一条通道在生产环境等于把登录权限授予所有能读日志的人，
而审计轨迹里看到的是被冒用的那个人自己。所以它不是"不推荐"，
是和 `SITEDESK_DEV_LOGIN=1` 一样的待遇：`NODE_ENV=production` 时拒绝启动。

### 二、限流：那条注释是对的，而代价是静默的

Phase 8c 选了进程内的固定窗口，理由写在明面上，今天看仍然成立：

> 数据库版本天然跨实例，但它有个要命的副作用：
> **未认证的流量就此获得了一条写库的路径**。限流本身成了打库的手段。

代价也写在明面上：

> 多实例部署时每个实例各算各的，实际配额 = limit × 实例数。

问题在于**代价是静默的**：扩到 3 个副本，"10 分钟 5 次"变成 15 次，
配置没变、日志没变、监控没变，只有被刷的那个邮箱知道。

这一版没有反驳那个顾虑，而是把它**挡在门外**：

```
① 进程内计数器  每个请求都过。它挡住"随手刷"，更要紧的是 ——
                 它把下一级的写入量限死了：每实例每窗口每 key 最多 limit 次。
② 数据库计数器  只有过了①的请求才走到这里。它是唯一说了算的那个。
```

"未认证流量获得写库路径"这件事仍然成立，但**那条路径的宽度由限流器
自己规定**。测试直接盯着它：50 次请求打到限流器上，到达共享计数的不超过 2 次。

三个细节值得记下来：

**key 先哈希再出门。** key 是登录名和登录令牌前缀。令牌前缀明文落库会
推翻整套认证的前提（库里只有哈希，见 0007）；登录名是个人信息，
而限流表的留存周期没有人管。所以送出去的是 `sha256(scope:key)`。

**计数必须活过业务的回滚。** 兑换端点在令牌不对时会抛 `ProblemException`，
抛错就回滚 —— 如果计数走请求那条连接，猜错的每一次都不算数，
**暴力猜令牌于是完全不受限**。所以共享计数走池子，自己一条连接、自己提交。

**`clock_timestamp()`，不是 `now()`。** `now()` 是事务开始时间，
在一个长事务里它一动不动，窗口永远过不去。这件事只在长事务里才看得出来 ——
平时每个请求一个事务，两者长得一模一样。造了个 `now()` 版本验过：
一个事务里三步（放行 → 拦下 → `pg_sleep(1.1)` → 应当放行），
`now()` 版本第三步仍然是 `f`。

原子性用 `INSERT ... ON CONFLICT DO UPDATE` 一条语句完成。
换成"先查再改"实测：20 个并发、阈值 5，**放行 6 个**。
只多一个 —— 但限流器丢掉的从来就不是"很多次"，而是恰好那一次。

库不可用时退回本地判定并打一条 warn。库挂了的时候这两个端点本来也办不成事，
把它们再变成 500 只是放大故障；但**静默降级不行**，多副本下退回本地
就是阈值被放大，那正是这一节要修的东西。

### 三、5000 是拍的，而 `Number("3o")` 是 NaN

`SITEDESK_DRAIN_MS` 的默认值这条已知问题从 Phase 9c 就挂着。
动手之前先看了一眼那行代码：

```ts
const wait = o.wait ?? Number(process.env["SITEDESK_DRAIN_MS"] ?? 5000);
...
if (wait > 0) await new Promise(r => setTimeout(r, wait));
```

**第二个毛病比第一个严重得多**：`Number("3o")` 是 `NaN`，而 `NaN > 0` 是 `false`。
一个手滑的环境变量（`5s`、`3o`、`5.5`）把三步停机静默降级成"立刻关"——
发布看起来照常成功，只是每次漏掉一小撮请求，而这段代码存在的理由
就是为了不漏那一小撮。没有任何一行日志会提到它。

修法两件：

**畸形的值拒绝启动。** 严格的 `^\d+$` 解析，交给 preflight ——
"配错了反而没声音"正是启动自检该拦的东西。

**把"拍脑袋"换成一次乘法。** 运维知道自己 LB 的探测间隔配的是多少，
但没人算得出"那我该排空几秒"。所以加了一条推算路径：

```
SITEDESK_DRAIN_MS        显式指定，优先级最高
SITEDESK_LB_PROBE_MS     LB 的探测间隔
SITEDESK_LB_PROBE_FAILURES  连续几次失败才摘掉（默认 2）
      → 排空 = 探测间隔 × 失败阈值 + 1 秒余量
```

k8s 默认 10s × 3 = 31 秒，ALB 默认 30s × 2 = 61 秒。**两个都远大于 5 秒**——
也就是说那个默认值在最常见的两种编排器上都是错的。

默认值保留 5000（单机演示够用），但生产环境下没显式配过就打一条告警。
compose 里三个变量**都默认留空**，不再写死 `:-5000`：写死的话进程会认为
"运维显式配过"，那条告警就永远不会出现。

前端那个托管进程有同一套解析，**有意重复**：运行镜像里只有 `server.mjs`
和 `dist/`，为了共用十几行解析而让前端去依赖后端的构建产物，
那个耦合比这点重复贵得多。

### 四、452 kB 的 js → 117 kB

预压缩这条挂了两个阶段，理由一直是"通常由 ingress 压"。
但"通常"不是"一定"：这两个容器可以直接对外跑（演示部署就是），
那时没有任何一层会压，450 kB 的 js 走明文 —— 而它不会报错，
只是每个人首屏多等两秒。

构建期压，不是请求期压：产物是不变的，请求期压等于把同一份 js 压上千次，
每次都占着事件循环（Node 只有一条主线程，压缩期间连探针都答不上）。
构建期压一次，brotli 才敢开到 quality 11。

实测：

```
assets/index-C6sgxJp9.js   452.3 kB → br 117.2 kB   gz 137.1 kB
assets/index-D0mhGdaa.css    8.6 kB → br   2.2 kB   gz   2.5 kB
mockServiceWorker.js         9.7 kB → br   2.7 kB   gz   3.2 kB
合计                        470.5 kB → br 122.1 kB  （省 74%）
```

托管服务器那边有三件事不能少，各有一条测试：

**`Accept-Encoding` 要真的解析。** 写成 `header.includes("br")` 的话，
`br;q=0`（明确拒绝）会被当成接受 —— 发出去的是一堆二进制乱码，
而且只发生在某些客户端上。

**原文那一份也要带 `Vary: Accept-Encoding`。** 只在压缩响应上带，
等于告诉缓存"原文这一份对所有人通用"，于是不支持 br 的客户端会拿到别人的 br。

**ETag 按实际发出去的那份算。** 三种编码三个值。共用一个 ETag 是缓存投毒
的经典形状：中间代理拿 br 那份去回答一个只接受 gzip 的客户端。

另外 `Content-Type` 永远按**原文**的扩展名定 —— 按 `.js.br` 定的话会变成
`application/octet-stream`，而浏览器对 `type="module"` 的脚本强制校验 MIME：
页面白屏，报的话和真正原因毫无关系（这条在 Phase 9e 的 MIME 表注释里
已经写过一次，这里是同一个坑的第二种走法）。

直接来要 `/assets/x.js.br` 一律 404：那是实现细节，不是资源。

### 五、HSTS 不是 TLS

原来的说法是"TLS / HSTS 属于前面那层 ingress，这两个进程不管"。
前半句对，后半句不对：**HSTS 只是一个响应头**，而只有真正发响应的
这一层知道该不该发它。

所以托管进程现在能发 HSTS，条件是这一跳确实在 TLS 后面
（`X-Forwarded-Proto` 的**最左**一段是 https）。取最右或整串比较的话，
"浏览器 https → ingress → 本进程 http"会被判成不安全，HSTS 永远发不出去 ——
一个静默失效的安全头比没有更糟，因为配置看起来是对的。

两个开关都**默认关**，因为打开它们造成的破坏是不可回滚的：
对着一个没有证书的域名发一次 HSTS，浏览器会把它锁到 `max-age` 过期为止。

强制 https 用 **308**，不是 301/302：后两个允许客户端把 POST 改写成 GET，
于是一次写操作会静默丢掉请求体，表现为"提交了但没生效"。

**探针不跟着跳。** LB 的健康检查通常直接打容器端口、不带 `X-Forwarded-Proto`，
跟着 308 的话这个实例会被判成不健康然后摘掉 —— 一个安全开关变成一次停机。

`Host` 头会被拼进 `Location`，所以先验形状：塞进 CRLF 就是响应拆分，
塞进别的域名就是一次开放重定向。

### 顺手修掉的两条测试

**`rate_limit_counter` 撞上了一条不变量。** `db/test/migration.test.js` 里有一条
"每张启用了 RLS 的表都至少有一条策略 —— 启用而无策略等于全部拒绝，会静默出事"。
这张表恰恰就是要全拒的。改法不是给它开例外，是把意图**写出来**：

```sql
CREATE POLICY rate_limit_counter_no_direct_access ON rate_limit_counter
  FOR ALL USING (false) WITH CHECK (false);
```

效果和"开了 RLS 但一条策略都不建"完全一样，区别是后者看起来像**忘了建**。

**破坏性变更门禁的那条自测按字节挑基线。** 它去历史里找"内容不同的
`openapi.yaml`"，然后断言门禁比得出差异。而这一轮只改了 `sentTo` 的**说明文字**——
门禁看不见说明文字，而且**本来就该看不见**（改一句描述不是破坏性变更）。
于是它挑中上一个提交，门禁如实回答"契约无变化"，测试当场红。

红的是测试的挑法，不是被测的门禁。改成按**结构**挑基线
（端点集合 + schema 的字段与必填集合）。

### 当前已知问题

1. **单机 compose，仍然不是高可用。** 这一轮只挪掉了代码层的绊脚石
   （限流不再随副本数被放大）。真正的高可用还差两样，都不是这个仓库能给的：

   compose 内网那点 DNS 轮询遇上 keep-alive 长连接就会粘在同一个实例上。
2. **共享限流在数据库不可用时退回单实例判定**（并打一条 warn）。
   刻意的取舍，代价是那段时间里多副本的阈值仍然会被放大。
3. **短信通道只定了一个最小形状**（POST `{to, text}` + Bearer）。
   真实网关字段名对不上时要在中间摆一个适配器。
4. **SMTP 客户端是最小实现**：纯文本、单收件人、PLAIN / LOGIN。
   没有附件、没有 DKIM、没有连接复用，也不打算有。
5. **收件地址只能由运维登记**，本人不能自助改。自助改要先回答
   "改地址要不要二次确认"—— 那是一个产品决定，不是一个存储问题。
6. **投递失败只进日志，不重试。** 链接 15 分钟就过期了，重试的窗口很窄；
   而一个真的要重试的实现需要队列与去重，那是另一件事的规模。
7. 其余沿用 Phase 9 的清单。

| B2 | 幂等键无清理任务 | 迁移 0016 加 `app.gc_expired()`，`infra/gc.ts` 定时扫 |
| B3 | `response_status` 只写不读 | 重放时比对声明状态码，不一致打 warn 并按声明返回 |
| B4 | `listHandovers` 仍是 N+1 | 抽 `assemble()`，三条 `= ANY($1::uuid[])` + 内存分组 |
| B5 | `GET /v1/me` 下发 `visibleSiteIds` 全集 | 从契约里删掉；范围由后端在每次查询时判定 |
| B12 | 处理器卡死要等 60 秒才收得回连接 | 请求级截止时间，到点收回连接并回 504 |
| E4 | 会话 8 小时 / 链接 15 分钟写死 | 迁移 0016 放宽 TTL 上限到 60 分钟，两者可配 |

两条「写了没读」值得单独说：`response_status` 与 `visibleSiteIds`
都是**写进去了但没有任何人读**的字段。前者是漏了一步校验，
后者是一个会随权限变化而过期的快照 —— 而快照过期时没有任何东西会提醒你。
删掉一个没人读的字段，比留着它等人误用要便宜。

`app.gc_expired()` 用 `pg_try_advisory_xact_lock` 拿锁，
拿不到就返回 `-1` 直接退出 —— 多副本同时到点时只有一个真的在扫，
其余的立刻让开，而不是排队等一把锁。

### W2 · 前端：错误边界、离线队列、以及三处「说不出话」的地方

| 编号 | 问题 | 做法 |
|---|---|---|
| B9 | 前端没有全局错误边界 | `shell/ErrorBoundary.tsx`，两层：路由内层 + Router 外层 |
| B10 | 冷启动就离线的话，仍然会丢 | 登录后把身份缓存进 sessionStorage，离线冷启动也排得了队 |
| B11 | 只有 L2 命令进队列 | 队列条件从「L2」改成「非 GET 且非 auth」，L1 写入也进得去 |
| D8 | 登录页没有「链接已过期 → 重新申请」的引导 | 兑换失败时就地给出重新申请的入口 |
| D9 | 行内「待发」只有启动清单一页 | 抽 `usePending()`，四个写入页共用同一种问法 |
| D10 | 重放没有冲突提示 | 失败项带上 `hint` 与排队时长，说清楚"为什么现在不行了" |

**错误边界当场就抓到了一个真的**。加完之后跑 E2E，
工时页整页白屏 —— 而在此之前，白屏是没有下文的：
控制台一行 minified 报错，用户看到一片空白，没有人会去报这个 bug。
边界一上，它变成了一句可读的话：`Minified React error #310`。

根因是 `usePending()` 被放在了 `if (!rows) return <加载中>` **之后**：
第一次渲染（rows 为 null）走的是 8 个 hook，第二次是 9 个。
React 只认 hook 的调用顺序，数量一变就整棵子树报废。
这类错误在代码里长得非常无辜 —— 「用到它的地方就在下面几行，
放在这里最顺手」—— 所以那一行上留了注释说明它为什么必须待在上面。

`B10` 那条要说清楚它**不是**什么：缓存的身份能替你**排队**，
不能替你**放行**。离线时界面照着缓存的角色画，
但每一条排出去的命令，重放时仍然要过一遍服务端的三维权限；
缓存过期或权限被改了，重放就会失败并带上原因。
把权限判断搬到前端才是真的省事，也是真的漏。

### B6 · 关闭闸门里那四项 unavailable —— 挂了五个阶段的占位

中心关闭有八项前置条件。其中四项从 Phase 4a 起就是占位：

```
ip-imbalance      药品数量不平衡          （clinical，尚未交付）
ip-not-destroyed  回收药品未完成销毁登记  （clinical，尚未交付）
specimen-open     生物样本链未闭环        （clinical，尚未交付）
closeout-report   未向伦理递交结题报告    （regulatory，尚未交付）
```

它们以 `unavailable` 出现在 unmet 里，闸门不放行 —— **fail-closed 是对的**：
把「查不了」当成「通过」，等于允许在质疑挂着、药品差三盒的时候关闭中心。

但 fail-closed 只在**有人真的会去把它变成 ok** 的前提下才是把关。
挂了五个阶段之后，它的现实后果是「没有任何一个中心关得掉」：
闸门看起来在把关，实际是一堵墙 —— 而墙教会用户的是绕过它。

迁移 `0017` 建起三张表，四个占位换成四条真查询：

- **`ip_movement`** —— 只追加的药品流水（到货 / 发放 / 退回 / 退回申办方 / 销毁）。
  在手数量由 `app.ip_balance()` **算出来，不存**：存了就要维护，维护就会错。
  这个函数**刻意不是 `SECURITY DEFINER`** —— 它要跟着调用者的 RLS 走，
  否则它就成了一个绕过行权限的读接口。
- **`specimen`** —— 采集 / 寄出 / 接收 / 销毁。`specimen_one_ending` 约束保证
  「收到」和「销毁」互斥：两个都没有 = 在路上不知去向，
  而中心一关就再也查不清了。**寄出不算闭环**，这正是最该拦的那种。
- **`regulatory_submission`** —— 递交与批复分开记。
  闸门看的是**批复**：递交了不等于批下来了。

三张表都走 `app.site_visible_by_id` 的 RLS 策略，
新增 8 个端点（动作权限复用现成的 `subjWrite` / `ethics`，没有新造 key ——
新造一个 key 按规约 13 要落进每个租户的种子，为两张新表付那个代价不值）。

闸门测试从「断言每一条都说『尚未交付』」改成了五条真流程：
药品发出去没收回来 → 关不掉且说得出差多少（18 份）；
台账记成负数 → 指出是记账错了；样本寄出 → 仍然拦；确认接收 → 放行；
结题报告递交了但没批 → 仍然拦，批复之后**八项全绿**。
这是这套闸门第一次真的能放行一个中心。


### B8 · 「事后失效」的中心 —— 不回退状态机，但要在台账上看得见

撤销一个已完成的启动阻塞项，系统**刻意不自动回退状态机**：
一个已入组 12 例的中心被推回「合同签署」，那 12 例的访视就挂在了
一个不存在的状态上 —— 自动回退比不回退危险得多。

但不回退不等于不记账。在此之前，撤销留下的唯一痕迹是一句
转瞬即逝的 `sideEffect` 文案：关掉页面就再也找不回来了。

`StudySite.startupInvalidated` 补上了这一处：
**已过 SIV，却还挂着未完成的阻塞项**。它是**算出来的，不存**——
存一个布尔位就要在两处维护（撤销时置位、补做完时清位），
漏掉任何一处，台账上就是一笔假账，而假的"没问题"比没有这一栏更糟。
`listStudySites` 上同时开了筛选（三态：不传 = 两种都要）。

### 顺带修掉的：`?flag=false` 在整个仓库里都是 `true`

做这个筛选时才发现的：契约里所有布尔查询参数都写着
`z.coerce.boolean()`，而它走的是 `Boolean(v)` ——
**`Boolean("false") === true`**。于是

```
GET /v1/timesheets?includeVoided=false   # 读成 true，把作废的也带出来了
```

只传 `true` 的地方看不出问题，所以它安静地待了很多个阶段。
新增 `QueryBool` 原语（认 `true/1/yes/on` 与 `false/0/no/off`，
其余一律报错 —— 把 `?flag=ture` 当成 false 也是在猜，
而猜错时同样是安静的），9 处全部换掉，
并加了一条契约测试断言 `src/` 下不能再出现 `z.coerce.boolean()`——
光修一处没有意义，下一个人照着旁边那行写就又回去了。

### B7 · `RefreshProjections` —— 挂了五个阶段，而它一直是成立的

架构文档 §5.1 给「完成一次访视」列了七个订阅者。六个早就接上了，
第七个 `RefreshProjections`（刷新入组漏斗、单中心 P&L、驾驶舱投影）
从 Phase 4c 起就写着 `delivered: false`，在响应的 `pending` 字段里
一路透传到界面上。

查下去才发现：**它其实一直是成立的**。入组漏斗（`getSiteFunnel`）
与单中心损益（`getSitePnl`）都是**读时计算** —— 直接从
`subject` / `subject_visit` / `timesheet_entry` 聚合，
没有物化视图、没有投影表、没有缓存。于是"刷新"这个动作没有对象：
事务一提交，下一次查询看到的就是新数字。

但"一直成立"如果没人验，和一个 pending 标记一样空。所以补了两条测试：

1. **实测**：完成一次访视之后，同一个中心的漏斗多了一个预筛的人，
   损益的成本侧跟着变大（那 4 小时按费率卡折成了成本）。
2. **守住前提**：断言库里没有物化视图。哪天有人为了性能加了一张投影表，
   这一条就重新变成真活 —— 而那时测试会先红，
   不会等到某个月的驾驶舱数字对不上才被发现。

`pending` 这个字段和界面上那一块**都留着**：下一个暂时接不上的订阅者
出现时，它要能立刻说出来，而不是先经历一轮"为什么没人知道还差一件事"。

### D7 · SAE 台账与药品不平衡 —— 计算引擎那段话点名的原罪

`packages/calc/src/kernel.ts` 开头写着计算引擎为什么必须独立成一层：

> 原型阶段踩过一次。「SAE 24h 及时率」和「Query 平均关闭天数」是写死的
> 常量，而同一个页面下方就摆着一条超窗的 SAE。演示时没人看得出来，
> 真实系统里这就是**看板骗人** —— 而质量看板骗人，是要到药监核查时才付账的。

那段话写在 Phase 1，而这个数字一直到这一轮才真的算出来。

**一个能把它做假的算法，以及为什么不那么算。** 最省事的写法是
「已上报的里面按时的占比」：

```
rate = 按时上报数 / 已上报数
```

它有一个致命的后门：**一条 SAE 只要永远不上报，就永远不进分母。**
超时越久的越不影响这个数字，看板反而越好看。

所以 `saeTimeliness()` 把「已经超过 24 小时、但还没上报」的直接算成迟报 ——
它们是最严重的一类，不是还没轮到统计的一类。而「发生不足 24 小时、
还没上报」的是**未决**：既不算按时也不算迟，单独报数，
让人看得见"还有 3 条在计时"。

另外两处不肯让步的地方：

- **不四舍五入**。24.4 小时就是迟报，显示成"24 小时"是在替人开脱。
- **没有 SAE 时及时率是 `null`，不是 0，更不是 100%**。
  显示 100% 是在用一个没有分母的数字给人安全感。

界面上除了及时率，还画**最坏的那一条晚了多久**——
92% 促不成任何动作，"最坏的一条晾了 8 天"能。

I6 的强制部分：上报耗时超过 24 小时，**自动生成一条 `sae_late` 质量事件**，
与登记上报在同一个事务里写（和 I4「超窗必生偏离」是同一个做法）。
它是一条独立记录，不是 SAE 那条的状态位：「这一条晚报了」要走整改与关闭，
而 SAE 本身不需要"关闭"。

药品不平衡（I5）在这一轮同时补上了台账面：`IpPanel` 画出在手数量、
方向（收 +、发 −）与"关不掉中心的理由"，数字来自
`app.ip_balance()`——**算出来的，不存**。

#### 顺带修掉的两个

**① `quality_auto_needs_source` 只认得一种来源。** 迁移 0009 的约束写的是

```sql
NOT auto_generated OR (raised_by = 'system' AND visit_id IS NOT NULL)
```

意图是对的 —— 系统自动生成的事件必须指明来源对象，否则「它为什么存在」
没有答案。但那时唯一的自动事件来自访视，于是"来源"被写死成了 `visit_id`。
`sae_late` 的来源是**另一条质量事件**。
迁移 0018 加 `source_event_id` 并把约束改成「两种来源至少有一个」——
放宽成"允许没有来源"是另一条路，那等于把 0009 的判断作废。

**② 两支 down 迁移跑不动了。** 0017 / 0018 的 down 会把取值收窄回去，
而那时库里已经有靠新取值立住的行，报错是
`is violated by some row` —— 它指不到是谁写进去的。
两支 down 各自补了一条 DELETE，清掉的正是自己的 up 让它存在的那些行。

**③ `listQualityEvents({ limit: 1 })` 取不回刚写的那条。** 排序是
`raised_on DESC`，而 `raised_on` 来自**事件发生的日期**，不是写入时刻：
补录一条三天前的 SAE，它就不在第一页。
`closeQualityEvent` 里同样的写法被一个兜底假对象盖住了 ——
返回的是只有三个字段的残缺响应，前端看到的是"关闭成功但列表没变"。
两处都改成按 id 取回。

### D1 / D2 · 两份模板从常量变成数据

启动清单模板与 SOA 都被同一个问题挡了几个阶段。
`DEFAULT_STARTUP_ITEMS` 的注释把它写得很清楚：

> 模板一旦可配置就要回答「谁能改、改了对在途中心是否生效、历史清单如何追溯」

三个问题的答案是一样的，两处都照着做：

| | 启动清单模板（D1） | SOA（D2） |
|---|---|---|
| 谁能改 | `manage` + 必填原因 + 审计 | 同左（改 SOA = 一次方案修订） |
| 在途的怎么办 | **不生效**：建档那一刻铺开成 `startup_item` 行 | **不生效**：排期那一刻落成 `subject_visit` 行 |
| 怎么追溯 | 版本号只增不改，`study_site.startup_template_version` 盖戳 | `visit_template_change` 存前后快照 |

「不生效」是这两条里唯一不能让步的地方。一个已经做到第 12 项的中心，
模板改一次就多出三项从来没人见过的阻塞，SIV 排期作废；
一个受试者的 C4D1 已经排在下周三，SOA 一改就跳到下周五，
他的行程、床位、伴随用药全部作废 —— **而系统不会知道自己刚做了这件事**。
没有人会把那叫做"配置生效了"。

两条守住闸门的校验：

- 模板里**一个阻塞项都没有**会被拒。那样 SIV 闸门对每个新中心天然成立，
  闸门看着在把关，实际全部放行 —— 而它的表现是"一切正常"。
- 建档时模板是空的，直接 422。同一个道理，只是发生在另一头。

SOA 那边多一条硬约束：**已经排出去的 seq 不能删，锚点也不能改**。
删了，那些 `subject_visit` 行就指向一个不存在的定义 ——
报表里它们还在，SOA 上它们不存在。这条在**数据库层面**拦（触发器），
不只在应用层：应用层会有第二个入口，而这条规则没有例外。

两个实现上的坑，都值得记：

1. **整份替换不能"先删后插"**。触发器拦的是"删掉一个已排出去的 seq"，
   而先删后插会让每一条都经过一次删除 —— 于是**任何一次修订都被
   自己的保护措施拦下**。改成「只删真正被去掉的 seq，其余 upsert」。
2. `UNIQUE (study_id, visit_code)` 会在两条访视**对调编号**时中途撞车。
   先把现有编号统一加一个 `~` 后缀腾位置 ——
   契约里的 `Code` 不允许 `~`，所以它撞不上任何新值。

### E1 / E3 / D5 · 交接这条线上的三处

**E1 —— 接手人在交接完成前看不到那些中心。**
清单里最要命的一项是「在组受试者逐例交底（含联系方式与依从性）」：
哪个依从性差、哪个家属有顾虑、哪个只能周三来 —— 这些不在 EDC 里，
只在上一个 CRC 脑子里。而在此之前接手人连一张名单都对不上：
**他勾「已确认」的时候，确认的是自己听懂了，不是自己核对过。**

迁移 0021 在 `app.site_visible()` 的 `assigned` 分支上加了一段。
三条边界缺一条这件事就变味了：

1. **只在交接进行中**（`status = 'pending'`）。它**自己会过期** ——
   不需要谁记得回收。
2. **只到接手人本人**（`to_account_id`），不是"参与交接的人"。
3. **看的每一眼都进审计**（I10 本来就写）。这正是它可以被接受的原因：
   事后查得出"谁在交接期间看了哪些人"。

为什么不做成第六条行规则：行规则是**角色**的属性，写在 `role` 表上；
交接是**一个人在一段时间里的状态**。做成规则等于说"接手中的 CRC 是
另一种角色"，会让角色矩阵多出一行只在几天内为真的东西。

三处实现（DB 函数 / `rowScope()` / `siteScopeSql()`）必须同时改 ——
`packages/policy` 的等价性测试当场抓到了漏掉的那一处：
`fengle(assigned) × …：TS=true DB=false`。这条测试的价值就在这里。

**E3 —— 发起交接的表单不筛在职状态。** 修的时候发现它比记录的更糟：
`listStaff` **根本没有**按账号状态过滤，只是种子里碰巧没有任何一个
停用账号有 `staff` 行 —— 没有任何一条测试会因为它坏掉而红。
所以三件事一起做：加 `activeOnly` 查询参数、`Staff` 上暴露
`active`/`disabledReason`、**在种子里给已离职的周琦补一行 staff**，
让这条路径真的被走到。

离职的人**留在名册里**是对的：「谁离职了、他的中心谁接的」
是交接台账要回答的问题，把人从名册上抹掉等于抹掉那段历史。

**D5 —— 交接不发通知。** 交接是发起人单方面做的动作：他填表、勾清单、
点发起。接手人在此之前完全不知道有这回事 —— 系统里多了一笔单子，
界面上多了几个中心，但没有任何人告诉他。
**于是"交接"实际发生在微信群里，系统只是事后记账。**

Phase 10 建的投递通道（SMTP / 短信 webhook / console）本来只服务登录链接。
这一轮把 `Transport` 的入参从 `LoginLink` 抽象成 `Message`，
两种通知共用同一批通道 —— 分成两套必然漂移，
而漂移的表现是"有的通知发得出去，有的发不出去"，且只有收不到的那个人知道。

`NotifyService.queue()` 有一处不是优化而是**必须**：
收件地址在**事务里**就查好，`afterCommit` 钩子里只剩"发"这一件事。
钩子跑的时候连接已经归还了，在里面查库拿到的是一个不属于自己的 client——
而那种错只在通知这条路径上出现，日志里看到的是"提交后的动作失败"，
指不到是谁写错了。（这个坑是写的时候踩进去的，测试当场红了。）

### D6 · 损益的时间维度 —— 累计口径回答不了「这个月比上个月差在哪」

**分月不是把累计除以月数。** 每一笔钱按**事件发生的那个月**归属：

```
启动费   → SIV 当月（还没 SIV 就还没确认）
入组收入 → 每一例的入组月      筛败费 → 每一例的筛败月
脱落扣减 → 每一例的退出月      成本   → 工时的**工作日期**所在月
```

按录入时间归属会让补录的工时落在错误的月份 ——
**那是月度对不上最常见的来源**，也是这条口径唯一真正的分歧点。
测试里专门有一条：补录上个月的工时，上个月的成本要涨，本月不能动。

月份轴是**连续的**，不是"有数据的那几个月"：
中间空掉的月份必须画出来，"那个月一分钱收入都没有"正是要看见的事。

界面画的是**毛利一根柱**，从零轴两边长出去：
负毛利是这一页最该被看见的东西，而折线画负值要么截断在 0（谎），
要么整条线往下挪（一眼看不出正负）。不画收入与成本两条线 ——
它们的交叉点没有业务含义，而人会去找它。

页面上写明「各月加起来不一定等于累计」：累计里的脱落扣减按**当前**
访视完成度算，而它会随时间变化。有人问"为什么加起来对不上"时，
这句话是唯一的答案。

### D4 · 工时审批 —— 全部价值在于「第二个人」

在此之前：填了就进成本，`approve` 权限只用来作废别人的填报。

**先要回答的是：未审的工时算不算成本。** 两条路都说得通，但只有一条是对的：

- 不算 —— 损益里只有已审的成本。**这条不行**：人已经把活干了，成本已经发生。
  不算进去，毛利就比实际好看；等审批补上又突然掉一截，
  而那时没有人说得清是经营变差了还是审批积压了。
- 算，但**标出来有多少还没审**（`unapprovedCostCents`）。

走后者。于是 `approved_at` 不影响任何金额，它只回答一个问题：
**这笔工时有没有被第二个人看过。**

因此有一条不能让步的规则：**不能审自己填的**。
自审等于没有审批流，只是多了一次点击 —— 而多出来的那次点击
会让人以为这里已经有把关了。这条规则同时写在**数据库**里
（`timesheet_no_self_approve`）：应用层会有第二个入口
（批量审批、脚本、以后的定时结算），而这条规则没有例外。

顺带把 `timesheet_immutable()` 补了一刀：**审过不能撤回**。
那两列不在 0010 那份守卫名单里，于是把 `approved_at` 改回 NULL 是通的 ——
而那等于把"我看过了"这件事抹掉重来。改错了要往前走：作废，重报。

界面上审批状态是一个**角标**而不是一句话：它和成本无关，
画成一段文字会让人以为它影响那个数字。而"这是你自己填的，得由别人审"
是**说出来**的，不是把按钮藏掉 —— 藏掉的话人会以为是自己没有权限。

### D3 · 开户不止到角色为止

`provision_tenant` 给的是权限模型。开完之后新租户能登录、能看见界面，
但**一件事也做不了**：建中心会因为启动清单模板是空的被拒（迁移 0019 之后），
填工时会因为没有生效的费率卡被拒。
「开户成功」和「可以开始干活」之间隔着一段没有人负责的距离，
而它只在第一个人试着干活时才暴露。

拆成两个函数，因为**维护者不同**：
`provision_tenant_roles` 是权限模型，由迁移维护（改它要动代码）；
`provision_business_config` 是业务配置，由客户改（改它是日常操作）。
写在一起的话，「重新开一次户会不会把客户改过的费率覆盖掉」
就成了一个每次都要重新读代码才能回答的问题 —— 现在答案写在函数边界上。

费率卡是**占位，不是推荐值**：`note` 里写死「必须按实际人力成本改掉」。
每家受托方的成本口径都不一样，我们没有立场替客户定这个数；
而一个不带说明的数字会被当成"系统给的标准"一直用下去，
成本口径错了，这个系统在钱这一侧输出的每一个数都是错的。

**SOA 不在开户里**：它挂在 `study` 上，新租户还没有项目，没有东西可挂。
硬塞一份编出来的访视计划比没有更危险 —— 它看起来是真的。

#### 三个顺带修掉的

**① 契约里的路径带着 NestJS 的转义。** 装饰器里 `:` 要写成 `\:`，
而顺手把那个反斜杠抄进契约的话：

```
契约说       /v1/timesheets/{id}\:approve
服务器服务   /v1/timesheets/{id}:approve
```

两边永远对不上。`arch:check` 只比 operationId，后端测试用的是自己写死的
路径字符串 —— 于是整条链路全绿，只有走契约生成客户端的前端会 404，
而那个 404 在界面上表现成「上游不可用」，指不到任何地方。
加了两条契约测试：没有一条路径带反斜杠，每条路径都长得像 URL。
（`replaceStartupTemplate` 与 `replaceSoa` 也带着同样的错，一并修掉 ——
破坏性变更门禁如实报了这两条路径变更，那是它该做的。）

**② 迁移 0024 的 down 在半途失败的状态下跑不动。** 与 0017 / 0018 同一类：
`ALTER FUNCTION ... RENAME` 在函数不存在时报一句指不到原因的话，
把整个 `down 99` 卡住，连带拖垮没关系的迁移。改成先查存在再改名。

**③ 开户的占位费率卡会和演示种子撞在排他约束上。**
迁移总是跑在种子之前，于是演示租户先拿到 5 张占位卡（开区间），
种子再插自己的（也是开区间）—— `rate_card_no_overlap` 当场拒绝。
那条约束是对的（区间重叠时"当天用哪个费率"没有答案），
所以让路的是占位的那一份：新增 `db/seeds/000_clear_provisioned_placeholders.sql`，
只删带占位标记的行。生产不跑种子，占位卡留在那儿等运维改掉，
正是它存在的意义。

### G7 / G6 · 两个默认值，和一次重试

**G7 —— HSTS 与强制 https 都默认关。** 修的时候发现这两条不该绑在一起：

- **HSTS 改成默认开**（两年）。它只在 `X-Forwarded-Proto` 的最左段是
  `https` 时才发得出去 —— 纯 http 的部署**永远走不到那一行**，
  默认打开伤不到它。而默认关的代价是真实的：绝大多数部署不会去读一遍
  `.env.example`，于是一个已经在 TLS 后面的系统白白少了一层保护。
- `includeSubDomains` 拆出来做成 opt-in。它锁的是这套部署**并不拥有**的
  那些子域名，是 HSTS 里唯一会误伤别人、且无法回滚的部分。
- **强制 https 保持默认关**，而且应该一直保持。它把明文请求 308 走，
  纯 http 的部署（README 的快速开始就是）会当场变得打不开 ——
  这条的失败方式是"整个站点无法访问"，不能靠默认值去赌。

**G6 —— 投递失败只进日志，不重试。** 原来的记录写着"真要重试得有队列
与去重，那是另一件事的规模"。那句话论证的是**不做持久队列**，
不是**不做重试** —— 而最常见的失败恰恰是一次性的：
网关正在重启、DNS 抖了一下、短信厂商限流了三秒。
那种失败下用户看到的是"申请了但没收到"，而系统看起来一切正常。

进程内的有界重试（3 次，退避 1s / 5s）盖住的就是这一类。两条边界：

1. **只重试暂时性失败。** SMTP 4xx 重试，5xx 不重试（"查无此人"、
   "拒绝转发"是确定的拒绝）；网关 429 / 5xx 重试，其余 4xx 不重试
   （那是我们把请求发错了）。重试一个确定的拒绝，只是把同一条错误日志
   推迟三十秒，同时让人以为系统还在努力。
2. **不能超过内容自己的有效期。** 登录链接的重试窗口取 TTL 的三分之一 ——
   在第 20 分钟送到一条第 15 分钟就过期的链接，比彻底失败更糟：
   用户点开它看到"链接无效"，然后不知道该怪谁。

### F1 / F2 · 种子

**F1 —— 种子依赖 `prototype/index.html`。** 这个依赖是**对的**：
原型是冻结的需求基线，不是运行时依赖。错的是它**漂了没有人知道** ——
改一次原型而不重跑生成器，种子就和需求基线悄悄分了家，
而分家的表现是几个月后有人问"系统里这个数为什么和当初谈的不一样"。

`node tools/gen-seed.mjs --check` 把那件事变成一次 CI 失败，并直接说出
该跑哪条命令。它**不自动重跑**：重新生成会覆盖 `001_demo.sql`，
那应该是一次看得见的提交，不是构建的副作用 —— 那次提交本身就是
"需求变了"的记录。

**F2 —— 只有具名受试者有访视行**（10 条 / 598 例）。
漏斗是真的，访视清单是空的：演示里"今天要做什么"永远只有十来行，
谁也看不出这一页在几百例的中心上长什么样。

现在按 SOA 铺开（601 条）：入组日 + offset 落在今天之前的是做完的，
第一个落在今天之后的是"下一次"。写的时候被数据库的约束拦了三次 ——
`locked` 必须有 PI 的签字与时间（I3）、`entered` 必须有录入日、
清单项的完成必须有人。**这是好消息**：演示数据不能比真实数据更宽松，
否则界面在演示上走得通、在真库上走不通。

没有 PI 账号的中心只留最近一次做完的（停在 `done_pending_pi`）：
全铺的话演示库里会有一千多条卡着的访视，而「待 PI 确认」是一个**信号**——
85% 都是它的时候，它就什么也不说明了。

### C1 / C3 / C2 · 量过的和没量过的

**C1 / C3 —— 性能夹具只有访视与受试者，计划守卫只覆盖 4 条路径。**
于是"目前没有 N+1、计划也没退化"这句话被当成了对**全部**查询的结论，
而它当时只对量过的那三条成立。

夹具补上工时、审计、补偿、质量事件四张表（各自是完全不同的读法），
计划守卫从 4 条加到 9 条。写夹具时又被约束拦了三次
（`payment_paid_needs_receipt`、`quality_closed_needs_resolution`、
参数类型推断）—— 同上，那是这套 schema 的不变量强到连造假数据都绕不过去。

守卫本身也验了一遍**它会不会响**：把一条用例的 `mustUse` 改成一个不存在的
索引名，它当场报 `✗ 1/9 条查询的执行计划退化了`。
一个不会失败的守卫比没有守卫更糟。

**C2 —— 没有并发负载实测。** 这里量的**不是吞吐**（耗时依赖机器，
放进 CI 必然 flaky，与计划守卫同一条道理），而是**并发下的正确性**。
五条用例，当场抓出两个真的 bug：

1. **同一个幂等键并发打进来 → 500。** `begin()` 先 SELECT 再 INSERT，
   两个请求都查到"没有这把键"然后都去插，后到的撞主键，
   而那次撞击是个未捕获异常。500 对客户端的含义是"服务端坏了，可以重试"——
   **于是它再重放一次**。改成 `ON CONFLICT DO NOTHING`：插不进去
   就说明别人正在做，回 409。
   这条路径正是离线重放最真实的形状：CRC 恢复网络的那一刻，
   发件箱里同一条命令被重发几次，而它们几乎同时到达。
2. **同一个清单项并发完成 → 两个都 201。** 判定是读出来的，写是另一次往返；
   两个请求都读到"还没完成"，然后都写。清单项被"完成"了两次，
   审计里也有了两条说同一件事的记录。
   把条件挪进 `UPDATE ... WHERE done_at IS NULL`：谁抢到谁写。

另外两条守的是连接池：并发数打到上限的三倍应当**排队而不是报错**，
一阵并发之后连接要全部还回去（泄漏是慢慢发作的）。
这两条用例走**真实端口**而不是 supertest —— supertest 每次调用新起一个
临时监听器，三十个并发就是三十个监听器，那时的 ECONNRESET
量的是它，不是这个系统。

### C4 · 镜像仍然只在 CI 上验，但原因和记录的不一样

原来记的是"本环境无 docker 守护进程"。这一轮把守护进程跑起来了
（`dockerd --iptables=false --bridge=none`），于是真正的原因才露出来：

```
registry-1.docker.io            → 401（正常，需要认证）
production.cloudfront.docker.com → 403（网络策略拒绝）
```

元数据取得到，**层数据取不到** —— 基础镜像 `node:22-slim` 拉不下来。
这不是可以绕过去的事情（绕过 = 关掉网络策略），所以 C4 仍然只能在 CI 上验。
但记录改成准确的那一句：**不是没有守护进程，是镜像仓库的 CDN 被策略挡住**。
两者的处置完全不同 —— 前者是"换个环境"，后者是"找管理员放行一个域名"。

## Phase 11 收尾 · 33 条的账，和它们教了什么

### 结果

| | 条数 |
|---|---|
| 十个阶段末尾累计登记 | 61 |
| 其实早就做掉、只是没人回头划掉 | 21 |
| 逐条判过「修 / 不修」 | 40 |
| **判为要修** | **33** |
| **本轮交付** | **31** |
| 按要求推迟（B1 · OIDC 接真实 IdP） | 1 |
| 环境挡住（C4 · 镜像仓库 CDN 被网络策略拒绝） | 1 |

测试从 514 条涨到 **616 条**（+102），E2E 44 → **57**，
执行计划守卫 4 → **9** 条，端点 51 → **68** 个，迁移 0013 → **0024**。

### 三件反复出现的事

**① 「刻意的取舍」和「没人回头看」长得一模一样。**
关闭闸门那四项 `unavailable` 是刻意的 fail-closed，写得清清楚楚 ——
但它挂了五个阶段，效果是没有任何一个中心关得掉。
`RefreshProjections` 登记在册五个阶段，而它其实**一直是成立的**，
只是没有人去确认。
两者都不是"忘了"，都是"记着但没有人对它负责"。
所以这一轮的验收标准不是"修了多少条"，是**台账上不能有假账**。

**② 一半的欠账，修的时候发现比记录的更糟。**

- E3 记的是"发起交接的表单不筛在职状态"。实际是
  `listStaff` **根本没有**按账号状态过滤 —— 只是种子里碰巧没有停用账号
  有 staff 行，没有任何一条测试会因为它坏掉而红。
- C1 记的是"工时、审计、损益没在同等量级下量过"。实际是性能夹具里
  这四张表**一行都没有**，于是"目前没有 N+1"这句话被当成了对全部查询的结论。
- C2 记的是"没有并发负载实测"。跑起来当场抓出两个真的 bug：
  幂等键并发插入撞主键回 500（而 500 让客户端**再重放一次**），
  以及同一个清单项并发完成两个都成功。

**③ 数据库的约束反复拦下我，而每一次都是好消息。**
写性能夹具被拦了三次、写演示访视被拦了三次：
`locked` 必须有 PI 的签字与时间、`entered` 必须有录入日、
补偿的 `paid_on` 与 `receipt_ref` 必须同时有或同时没有、
关闭质量事件必须同时有时间人与整改说明。

**造假数据都绕不过去的不变量，才是真的不变量。**
反过来说：如果夹具能轻松造出一批真实系统里不可能存在的数据，
那么量出来的性能是另一个系统的性能，跑出来的测试是另一个系统的测试。

### 顺带修掉的、不在台账上的六个

1. **`?flag=false` 在整个仓库里都是 `true`**（`z.coerce.boolean()` 走
   `Boolean(v)`）。9 处全部换成新的 `QueryBool` 原语，并加了一条契约测试
   断言 `src/` 下不能再出现它 —— 光修一处没有意义，下一个人照着旁边那行写
   就又回去了。
2. **契约里两条路径带着 NestJS 的转义反斜杠**，与服务器实际路径永远对不上，
   而 `arch:check` 只比 operationId、后端测试用写死的路径 —— 全链路绿，
   只有走契约生成客户端的前端会 404。加了两条契约测试守住路径形状。
3. **`listQualityEvents({ limit: 1 })` 取不回刚写的那一条**（排序按
   `raised_on`，而补录一条三天前的 SAE 就不在第一页）。
   `closeQualityEvent` 里同样的写法被一个兜底假对象盖住了 ——
   返回的是只有三个字段的残缺响应，前端看到的是"关闭成功但列表没变"。
4. **`quality_auto_needs_source` 只认得一种来源**（`visit_id`），
   于是自动生成的 `sae_late` 插不进去。加 `source_event_id` 把"来源"补全，
   而不是放宽约束把 0009 的判断作废。
5. **三支 down 迁移在半途失败的状态下跑不动**（0017 / 0018 / 0024）。
   down 跑不动的迁移是**假的可回滚**，而它只在真的要回滚时才暴露。
6. **开户的占位费率卡与演示种子撞排他约束**（迁移总在种子之前跑）。
   让路的是占位的那一份，不是约束 —— 区间重叠时"当天用哪个费率"没有答案。

### 剩下的两条

- **B1 · OIDC 从未接过真实 IdP** —— 按要求推迟，不是判定不做。
- **C4 · 两个镜像仍然只在 CI 上验** —— 这一轮把 docker 守护进程跑起来了，
  于是原因从"没有守护进程"订正成了准确的那一句：
  `production.cloudfront.docker.com` 被网络策略拒绝（403），
  基础镜像的层数据拉不下来。绕过去等于关掉网络策略，所以不绕。
  两个原因的处置完全不同 —— 前者是"换个环境"，后者是"放行一个域名"。

## Phase 12 · 装完了没人打得开门

### 报障

用户拿 `--demo` 那条一次性链接登进去，看到的界面和原型对不上：
「管理者的界面跟原来 prototype 里面的 UI 完全不一样」。
顺带说了一句更要命的：**没有一个预设的管理员账号。**

第二句话不是抱怨，是一个 P0。查了一遍：

| | |
|---|---|
| 角色 | boss / pm / cra / crc / dm / qa / inst / pi —— **没有 admin** |
| `app.provision_tenant()` | 建租户、建八个角色、灌业务配置，**建零个账号** |
| `deploy.sh` | 种子只在 `--demo` 时灌 |
| `createAccount` | 要求调用方已登录且持 `manage` |
| `deploy/` | 没有任何 bootstrap 脚本 |

也就是说：**一次不带 `--demo` 的正式部署跑完，库里有一个租户、
八个角色、一整套业务配置，和零个账号 —— 而建账号要求先登录。**

要登录得先有账号，要有账号得先登录。装完了，没有任何人进得去。

这条不在那份 61 条的清单上。清单是按阶段末尾累积的，
每一阶段都在演示租户里干活，而演示租户的账号是种子灌的 ——
**没有人真的从零装过一次。**

### 补的是口令，不是把链接那条放宽

魔法链接那条路的每一环都有它的理由：不回显、不枚举账号、
单次使用、短时效、收件地址只认登记过的。为了"第一天能进去"
去松其中任何一环，松掉的是**所有人**的登录安全，
换来的只是那一次。

所以加的是另一扇门，门自己带锁：

- 迁移 0025：`auth_password`（scrypt，N=16384 r=8 p=1）、
  递增锁定、`is_initial` 单向标记
- 迁移 0026：第九个角色 `admin`，出厂账号 `admin` / `admin`
- 迁移 0027：`app.revoke_sessions()`
- `POST /v1/auth/password-session`、`POST /v1/auth/password`

出厂口令弱到不能再弱 —— 所以配套的三件事一件都不能少：

1. 库里记着它**还是出厂值**；
2. API 每次启动对着这样的账号打 WARN，界面顶上挂一条**关不掉**的红条；
3. 改密就在那条红条上，一步。

`is_initial` 做成**只能从 true 变 false**（触发器）。
理由只有一句：能被重新点亮又能被熄灭的报警灯，等于没有报警灯。

### 三个"看起来在工作，其实没有"

**① 失败计数活不过回滚。**
口令错了要抛 401，而抛错就回滚 —— 记在请求那条连接上的
`failed_count` 跟着一起没掉。于是猜错的每一次都不算数，
锁定永远不会生效，而库里那一列一直是 0，
看上去像"从来没有人猜错过"。

`PgSharedCounter` 的注释里写着同一句话（"限流的计数必须活过业务的回滚"）——
**这是第二次**。计数走池子，不走请求那条连接。

**② 管理员那句 `UPDATE auth_session` 匹配到 0 行。**
`auth_session` 的策略是「只看得到自己那些」。管理员给别人重设口令时
也要断开对方的会话，而那句 UPDATE 以管理员的身份跑 ——
策略把它限在管理员自己的会话上，**一个错都不报**。
口令换了、旧会话还开着，接口返回 204，界面显示成功。

RLS 最难发现的失败不是拒绝，是**安静地少做**。
补法不是给管理员放宽策略（那会让他从此读得到所有人的会话令牌哈希），
而是一个 SECURITY DEFINER 函数：把"一个动作"和"一片数据"分开。

**③ 待确认的权限改动看不见。**
权限矩阵那些复选框是受控的，`checked` 读的是服务端给的那份角色；
点一下只是记下一个待确认的改动、并不改它 —— 于是复选框自己弹回原位，
界面上唯一的变化是下面多出一张确认卡。
人会以为没点中，再点一次（把改动翻回去），
然后对着一张写着"获得"的卡片确认一个"失去"。

（这一条是 e2e 抓出来的，报错原文是
`Clicking the checkbox did not change its state`。）

### 界面：从写死的六项到按库里的授予出

原型定义 **45 个模块**。改之前：

- 侧栏是六项写死的数组
- 经营层在库里有 19 个模块，界面上给 6 个
- 45 个模块里 33 个没有任何入口
- 契约 76 个端点，前端调 31 个

而"老板在组织与权限里勾掉一个模块，导航立刻少一项"这件事，
原型里成立，这边不成立 —— 因为这边根本没读 `role_module`。

现在侧栏由 `/v1/me` 的 `permissions.modules` 生成，
按原型的 `MOD_GROUP` / `GROUP_ORDER` 分组，45 个模块全部有导航、有路由。
其中 10 个模块（6 张页面）已经建好，35 个点进去是一张**说明页**。

那张说明页写的是**这一页建出来之后要回答什么问题**，不是"敬请期待"。
一句"功能开发中"对用户没用，对接手的人更没用 ——
他要知道的恰恰是这一页该有什么，而那件事只有现在写得出来。

至于为什么不把没建好的藏起来：导航按库里的授予出，
那么"库里给了这个模块"和"界面上有这个入口"就必须一致。
藏起来的话，管理员勾上一个模块，界面上什么也不会发生，
而他没有任何办法知道为什么。

### 组织与权限：五个端点凑不出一张能用的页

`identity` 原来有五个端点：`listAccounts` / `createAccount` /
`disableAccount` / `listRoles` / `updateRolePermissions`。
照着原型 `26-org.html` 铺一遍才发现它们凑不出一张能用的管理页：

- 建了账号**改不了角色**（`updateRolePermissions` 改的是角色的权限，
  不是某个人的角色）
- **看不到有哪些分组** —— 而 `createAccount` 要求传 `teamId`
- 停用之后**启用不回来**
- 新建的内部账号**没有任何进得去的办法**
  （一次性链接要先登记收件地址，那要有人上服务器跑脚本）

也就是说：管理员建得出人，建出来的人用不了。
补了 `listTeams` / `createTeam` / `updateAccount` /
`enableAccount` / `setAccountPassword` 五个。

`setAccountPassword` 设出来的口令**标成初始口令** —— 本人登录后
顶上挂红条，改掉才消失。"管理员知道别人的口令"是个短期状态，
这个标记是让它保持短期的唯一办法。它也**不能对自己用**：
那等于绕过改密时验旧口令那道门，而会话被偷走时那是唯一的一道。

### admin 默认拿不到受试者字段

`admin` 有 45 个模块、13 个动作、行范围 all，
唯独 L3 的 `subject`（受试者筛选号）默认不给。

不是因为他绕不过去 —— 他拿着 `manage`，在「组织与权限」里点两下
就能给自己加上。**那两下会进审计轨迹**，而这正是全部的差别：
不是拦住他，是让这件事留下时间和人。

### 顺带修掉的两个真 bug（CI 上那两条红的）

Phase 11 的 F2 把种子访视从 10 条涨到 601 条，暴露出两处
"先取一页再在客户端找"的写法：

1. **今天页**拉 50 条回来再 `filter(status === "planned")`。
   列表按窗口升序，最早的 50 条全是做完的历史访视 ——
   于是"今天要做什么"这一页**空着**，而且看起来完全正常
   （没有报错、没有加载中）。
2. **访视详情页**拉 200 条再 `.find(v => v.id === id)`。
   找不到返回 `undefined`，而 `undefined` 就是"还没加载完"的那个值 ——
   页面**永远停在「加载中…」**，没有报错，请求还是 200。
   这是最难报障的一种坏法。新增 `GET /v1/subject-visits/{id}`。

一个先截断再过滤的列表，**过滤条件越常见它越安全**；
而这两条恰恰都是最不常见的那种（未完成的访视永远是少数，
你点开的那一条永远只有一条）。

## Phase 12b · 经营层的四页

45 个模块里，经营层占 19 个。上一段之后建好的是 4 个
（我的中心 / 工时 / 质量 / 组织与权限），还差 15 个。
这一段挑了后端已经有数、或者只差一条端点的四个：

| 模块 | 后端 |
|---|---|
| 入组进度 `enr` | 新增 `GET /v1/enrollment` |
| 筛选漏斗与筛败 `screen` | 同上（一条端点，两页共用） |
| 派工与产能 `staff` | `listStaff` 现成 |
| 审计轨迹 `trail` | `listAuditEntries` 现成 |

### 为什么要新增一条端点，而不是让前端打 15 次

`getSiteFunnel` 是按中心的。「入组进度」和「筛选漏斗」要的都是
**全部中心的同一组数** —— 让前端按中心逐个去打，那是把 N+1
从服务端搬到浏览器上，不是消灭它。15 个中心时看不出来，
1500 个时那一页永远打不开。

`listEnrollment` 一条查询出全部中心（拆解另走一条聚合 ——
把筛败原因 join 进主查询会让每个中心多出几行，分页游标就没法算了）。
和 `getSiteFunnel` 一样**只返回计数、不返回受试者明细**，
所以不需要 `subjRead`（I10）。

### 一致性测试抓到的第一件事

「逐条与 getSiteFunnel 相等」那条测试第一次跑就红了 ——
差的不是数字，是**顺序**：两边的原因拆解都只按 `count DESC` 排，
计数相同的两行谁先谁后是随机的。同一个请求两次可能给出不同结果。

三处 SQL 各补了一个第二排序键。这不是为了让测试变绿：
一个每次返回顺序都不同的接口，缓存、快照测试、
"和上次比有什么变化"全都建不起来。

### 三个界面上的判断

**① 入组进度不按中心代号排。**
按代号排的表，读的人要自己从十五行里找出哪几行不对劲 ——
而那正是这一页唯一要回答的问题。按**缺口**排：
两个中心都是 50% 达成，一个缺 10 例、一个缺 2 例，
达成率说不出这个差别。

**② 筛选漏斗的合计是总量之比，不是各中心比率的平均。**
一个预筛 2 例全败的中心，会把二十个中心的均值拉得看不懂。

顺带：没有分母时显示「—」而不是 0%。一个还没预筛的中心，
它的筛败率不是零，是**没有** —— 排序上也不一样，
没分母的排最后，因为它们不是表现好，是还没开始。

**③ 审计轨迹默认只看权限类变更。**
全量轨迹里绝大多数是日常写入（填一条工时、勾一项任务）。
和「谁给谁开了什么权限」混在一起按时间倒排的话，
后者永远在第三页之后 —— 而后者才是有人来查这一页的原因。

前后两份 JSON **原样铺开，不做差异高亮**：这两份是任意形状的
（角色的三维授予、账号的归属、中心的状态），
猜一套通用的差异算法出来，猜错的那几次正好落在最需要看清楚的地方。

### mock 里也修了一处

`listStaff` 的 mock **忽略 `activeOnly`**。真后端认它（E3 那条欠账
修的就是"交接发起表单不筛在职状态"），而 mock 不认 ——
于是开发环境里那个下拉又会出现已停用的人，选中之后是一次白跑。

**mock 忽略一个筛选参数，等于把已经修好的行为在开发环境里退回去。**
