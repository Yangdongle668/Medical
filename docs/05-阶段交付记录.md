### 过程中被拦下的两个错误

1. **`role_field.field_key` 外键拒绝了种子数据** —— 原型用简写 `subj`，schema 用 `subject`。
   外键就是干这个的。以 schema 为准，在生成器里做了唯一一次映射。
2. **约束 `account_external_needs_org` 写错了** —— 我原本写成"外部账号必须有 `org_ref`"，
   但 PI 也是外部账号，而他按 `pi` 规则切行，与所属机构无关。
   真正的规则是"`row_rule = 'hospital'` 的账号必须有 `org_ref`"，这是跨表条件，
   `CHECK` 表达不了，改用触发器。**约束的意图对、谓词错，是最难发现的一类错误** ——
   它不会报错，只会让某个人登录后一行数据都看不到。

### 当前已知问题

1. **`packages/policy` 尚不存在，因此「两处实现等价」还无法验证。**

2. **迁移在 Phase 1 内被就地修改过**（0002 的约束改触发器）。这在未发布阶段可接受，

### 数据库变更

**`0006_money_in_cents`：金额统一为整数分。**

这是契约层暴露出来的 Phase 1 不一致 —— 三处口径互相打架：

| 出处 | 口径 |
|---|---|
| 架构文档 §2.2 | `unitPriceCent: bigint`（分） |
| Phase 1 迁移 0004 | `numeric(14,2)`（元） |
| Phase 2 契约 | 整数分 |

原则 9 要求三者一致。**选分**：现实上限 5 亿元 = 5e10 分，
远在 `Number.MAX_SAFE_INTEGER` 之内；而元加小数在 JS 里做乘除迟早出现浮点误差，
且计算引擎要前后端共用，整数运算不需要十进制库。

用**前向迁移**而非就地改 0004：Phase 1 已交付并推送，
改历史迁移会让已经跑过它的环境与迁移记录对不上。

> **这正是 API-First 应该起的作用**：契约先定，把 schema 的不一致提前暴露出来，
> 而不是等 Phase 4 写后端时在转换点埋一个 bug。

契约测试分两组：

**约定组（8 项）** —— L2 一律 POST 且路径带 `:action`；L2 响应必须带 `sideEffects`；
L2 必须要求 `Idempotency-Key`；每个端点都声明 401/403/404；错误一律
`application/problem+json`；受列权限管辖的字段一律 optional 且不可空；
`operationId` 全局唯一；**`openapi.yaml` 与 zod 定义一致（产物不得手改）**。

**门禁组（11 项）** —— 逐条证明门禁真的会响：删除端点、删除字段、类型变更、
请求端可选变必填、请求端新增必填字段、响应端必填变可选、请求端枚举移除取值 → **拦截**；
响应端新增字段、`x-extensible` 枚举新增取值 → **放行**；普通枚举新增取值 → **放行但告警**。

### 过程中被拦下的三个问题

1. **`$ref` 泄漏到 `#/definitions/`** —— 独立转换 query 参数时 zod 会把具名子 schema 提升。
   加了归一化 + **引用完整性自检**（这道自检本该先于第一次生成就有）。
2. **门禁把请求和响应一视同仁 → 假阳性。** 两者的兼容性规则是**相反的**：
   响应加字段无害，请求加必填字段致命。假阳性会让人养成随手 `--allow-breaking` 的习惯，
   **那等于废掉门禁本身**。改为先按用途分类（沿 `$ref` 传递地标记 request / response / both）再判。
3. **示例数据语义错乱** —— `study.shortName` 生成了人名、`study.code` 生成了中心编号，
   因为键名启发式只看叶子节点。改为按**路径**判断。前端拿到语义错乱的 mock 会被误导。

### 当前已知问题

1. **`Idempotency-Key` 只是契约声明，服务端行为尚未实现**（Phase 3/7）。
   契约里写清了「24 小时内同键返回首次结果」，实现必须与之一致。
2. **`bigint` 在 pg 驱动里默认返回字符串**（int8 可能溢出 JS）。
   `apps/api` 启动时需 `pg.types.setTypeParser(20, Number)` —— 已写进迁移注释，Phase 3 兑现。
3. **`packages/policy` 仍不存在**，`app.site_visible()` 与 `rowScope()` 的等价性仍未验证（Phase 3）。
4. **`GET /v1/me` 的 `visibleSiteIds` 在中心数量很大时会变长**。
   当前 15 个中心无碍；超过约 500 个时应改为不下发全集、只靠服务端过滤。已记入风险。

### 数据库变更

`0007_auth`：4 张表 + 4 个 SECURITY DEFINER 函数。

四个函数都是为了解同一类「先有鸡先有蛋」：
带 RLS 的表要求先有身份，而拿到身份恰恰要先读这些表。

| 函数 | 解决什么 | 暴露面 |
|---|---|---|
| `app.resolve_session` | 令牌 → 账号 | 只返回 id |
| `app.resolve_login` | 登录名 → 账号 | 只返回 id |
| `app.consume_login_token` | 兑换链接 | 只返回 id，**原子**标记已用 |
| `app.issue_login_token` | 签发链接 | 只返回布尔 |

`app.issue_login_token` 是过程中改出来的：最初的实现要在未认证上下文里临时把
`app.account_id` 设成目标账号才能插入 —— 那等于给一个未认证请求提权。
收进 SECURITY DEFINER 函数后，会话状态完全不受影响。

### 过程中被拦下的四个问题

1. **闸门看着在把关，实际对每个新中心都放行。** 闸门查的是"阻塞项是否清零"，
   而新建的中心清单为空 —— 这个条件天然成立。补上"建档即铺开标准清单"，
   并加了两条测试锁死它。**一个默认放行的闸门比没有闸门更危险，
   因为它会让人以为已经把住了。**

2. **`INSERT ... RETURNING` 过不了自己的 RLS 策略。** 排查时每个条件单独求值
   都是 `true`，去掉 `RETURNING` 就能插入。根因：`FOR ALL` 策略的 `USING`
   会作用于 `RETURNING` 返回的行，而 `STABLE` 函数用的是命令开始时的快照 ——
   看不到刚插入的那一行。解法是**策略辅助函数接收行的列值，不按 id 回查本表**
   （`app.site_visible()` 一直是这么写的，所以从没撞上）。
   已在 `db/test/rls.test.js` 补三条回归测试。

3. **同一条连接上并发发查询。** 三处 `Promise.all` 让同一个请求事务的连接
   同时有两条语句在飞。pg 只会排队，换不来速度，却让语句在事务里交错 ——
   全部改为顺序执行。（是 pg 的 deprecation 警告先冒出来的，
   跟一次「改前无、改后有」的对照才定位到具体三处。）

4. **两条 DB 断言硬编码表名，每加一张表都要改。** 改测试去迁就实现，
   正是测试开始失效的那一刻。改为自维护规则：

   - 「每张业务表的租户归属都能被推导出来」——
     不再是"每张表都要有 `tenant_id`"，而是允许两类例外且**判定是算出来的**：
     ① 全局枚举表（单列 `text` 主键、不引用任何表）；
     ② 明细表（主键里含指向父表的外键，父表归属已可推导，递归判定）。
     外键必须落在**主键**里 —— 落在普通列上不算，那种列可以 `UPDATE` 到
     另一个租户的父行上，归属就成了可篡改的。
   - 并配一条**反证测试**：故意造三张错表（无父孤儿表 / 外键在普通列 / 父表自己
     也说不清归属），规则必须全部抓到。断言容易写成永远为真而无人察觉。

### 过程中被拦下的五个问题

1. **动作权限有两个来源，其中一个可以静默失守。** 契约里写 `action: "subjRead"`，
   控制器上另写 `@RequireAction("subjRead")` —— 两处各写一份。
   我在 ClinicalOps 里只写了契约那一份，结果 **QA 照样拉得出全院受试者名册**，
   而所有测试都绿的。不是不一致告警，是**没有任何一处会发现两边不一样**。
   改为守卫按 `operationId` 直接从契约查（`ACTION_OF`），并加了一条架构断言：
   控制器上的每个 `@Operation` 必须在契约里有对应端点，反之亦然
   （唯一例外 `devSession` 逐条写明理由 —— 把后门写进公开契约，等于告诉别人有这么个后门）。

2. **迁移里往 `role_action` 插了 0 行，一个错误都不报。** 迁移跑在种子之前，
   此刻 `role` 表还是空的，`INSERT ... SELECT FROM role WHERE ...` 安静地插入 0 行。
   症状是所有角色一律 403 —— 而错误信息里的动作名在权限表里根本查不到，
   排查时很容易误以为是授权没配。授权移回种子（那是租户数据），
   并加了一条断言：**每个 `action_key` 至少被一个角色持有**。
   没人有的权限，等于把那个端点关掉了。

3. **契约里的动作名和 `action_key` 表对不上。** 契约写 `subject.read`，
   表里是 `subjRead`。同样是所有角色一律 403。加了断言：契约声明的每个动作
   都必须在 `action_key` 里存在。

4. **测试辅助函数吞掉失败。** `doVisit()` 去全量访视列表里按 id 捞，
   新建的那次不在第一页 —— 于是"完成访视"根本没发生，
   而后面的断言仍然通过（因为它们对 `planned` 和 `done_pending_pi` 都成立）。
   辅助函数里吞掉的失败，会让后面的断言以「看起来对」的方式通过。
   改为按 `subjectId` 过滤，并在辅助函数里逐步断言。

5. **`overdueDays` 把当天到期算成「逾期 0 天」。** `new Date()` 带着时分秒，
   拿它和 `date` 列直接比，当天到期的项既进了逾期清单又显示 0 天。
   两端先归零点。差一天的错误在访视窗口上就是一次方案偏离。

另有两处小的：`window` 是 SQL 保留字（列名改 `visit_window`）；
`COMMENT ON` 只接受字面量，不接受 `||` 拼接。

### 数据库变更

`0010_timesheet`：3 张表、1 个函数、1 个不可变触发器、2 条 RLS 策略、3 个索引，
外加 `study` 上的两个合同条款列。

- **`EXCLUDE USING gist`** 让费率区间重叠在数据库层就写不进去。重叠时
  「当天用哪个费率」没有答案，而应用层的检查总有绕过去的路径。
- **工时不能删，只能作废。** 触发器同时拦住 `DELETE` 和任何会改动成本的 `UPDATE`。
  理由有两个，第二个更要紧：核查要求可追溯；「昨天的报表和今天不一样」
  是信任崩塌的开始 —— 一旦一线发现报表会变，他们就不再照着它做决定了。
- **外部方看不到任何工时与费率卡。** 机构办知道我们在他们医院投了多少人天，
  等于知道我们的报价底线。

### 过程中被拦下的五个问题

1. **黄金基线抓住的是我自己的算术。** 我手写的合计 187723333 与逐项之和差了 30 万分 ——
   实现是对的，写错的是我。这正是基线该干的事：**它校验的不是实现，是意图。**
   （正确值 188023333。）

2. **错误信息叫人去做一件 API 做不到的事。** 费率卡区间重叠时提示
   「调价请给旧卡收口，再开新卡」—— 而当时根本没有收口的端点。
   补了 `POST /v1/rate-cards/{id}:close`。**一条指向死路的错误信息比没有信息更糟。**

3. **收口日差一天。** `valid_to` 在 `EXCLUDE` 约束里是右开区间的上界，
   存收口日本身的话，**收口当天填的工时就找不到费率卡了**。存次日，对外仍报收口日。

4. **受列权限管辖的字段返回了 `null`。** `grossMargin` 在收入为 0 时返回 null，
   而它是 `gated(...)` 的字段 —— null 于是有了两种含义（没权限 / 没有值），
   客户端分不清，而"分不清"最后总会被当成"没有值"。改为**值为 null 时省略**，
   与「无权限时消失」用同一种表达。

5. **`-0`。** `roundCents(-0.4)` 得到 `-0`；它序列化成 JSON 是 `0`，看不出来，
   但 `Object.is(-0, 0)` 是 `false` —— 断言、去重、Map 键都会踩到，
   排查时会发现「明明都是 0 却不相等」。`+ 0` 归一。

另有一处测试自身的问题：三条会失败的 SQL 写在同一个事务里，
第一条失败后事务即中止，后两条报的是「current transaction is aborted」
而不是各自的约束名 —— 拆成独立用例。

### 跨上下文的接法（先说，不默默做）

「完成访视要顺带记一条工时」跨了两个限界上下文。直接 import 对方的 service
是最省事的写法，也是最贵的：半年后想把成本核算拆出去时，会发现两边已经缠在一起。

做法是 `modules/clinical/ports.ts` 只声明**需要什么**，装配在 `app.module` 完成，

调用方必须把这件事说出来，不能当作成功 —— 悄悄跳过的那条成本，最后是从毛利里出的。

### 两处对 Phase 0 规划的偏离（先说，不默默改）

1. **client 由契约注册表派生，不由 `openapi.yaml` 生成。**
   `openapi.yaml` 本身就是由同一份注册表生成的，直接读注册表等于读同一个源，
   少一个代码生成器和它的漂移风险。副产品：`operationId` 打错一个字母，
   `tsc` 立刻报错，而不是运行时 404。

2. **`packages/ui` 只做令牌，不做组件库。** Phase 5 要交付的是「骨架 + 设计系统」，
   而组件的形状要由 Phase 6 的真实页面决定。现在抽出来的组件，
   八成会在第一个真页面里被改掉 —— 那种抽象的成本比重复更高。

### 过程中被拦下的四个问题

1. **MSW 匹配不上 L2 命令路径，且一条错误都不报。**
   path-to-regexp 把 `:done` 当成路径参数，于是
   `/v1/subject-visits/{id}/tasks/{seq}:done` 悄悄落到兜底处理器上，
   返回一份静态示例。症状是「点了勾没反应」，控制台干干净净。
   改为把契约路径转成正则再交给 MSW（`pathToRegExp()`）。

2. **MSW 会跟着上生产，而没有任何构建警告。**
   开关写成 `import.meta.env["VITE_USE_MOCKS"]` 不会被静态替换，
   整个分支活着，480 kB 的 msw 进了包。改成点号访问后产物少 484 kB。
   CI 里直接 `grep` 产物兜底 —— **量产物，不是相信那行代码。**

3. **「低饱和」用错了度量。** HSV 饱和度说 `#8A5B00`（深琥珀）是 1.00，
   和 `#FFD600`（信号黄）一样满 —— 因为它只看「离灰多远」，不看亮到什么程度。
   改用 CIELAB 色度 C*：52 对 87，一下就分开了。
   断言也改成**相对**的：语义色必须比对应的信号色沉，强调色必须比语义色亮 ——
   参照点写死在测试里，比一个凭空的阈值说得清。

4. **我把承重的那道防线记错了。** CSS 注释里写「`minmax(0,1fr)` 是关键」，
   实测把它改回 `1fr`，11 项布局测试**全过** —— 真正在受力的是
   `.table-wrap { overflow-x: auto }`，去掉它 390px 上立刻溢出 185px。
   两道都留着，但注释按实测重写了。**不实测就会把功劳记在错的地方，
   然后在某次重构里把真正有用的那道删掉。**
